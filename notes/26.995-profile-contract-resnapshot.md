# Feature 26.995 — Re-snapshot OpenAPI for profile-edit, stats, game results + review

**Feature ID:** `profile-contract-resnapshot` (from `feature_list.json`)

**Status:** done

---

## What we built

A pure-codegen enabler, the fourth of its kind (mirrors 20.1
`auth-openapi-resnapshot`, 21 `backend-contract-resnapshot`, and 26.8
`social-contract-resnapshot`). The backend deployed the profile bundle to
prod — edit-profile (`PATCH /api/me`, `PUT /api/me/password`), me-stats
(`GET /api/me/stats`), game results (a `result` field on `MyGameSummary`),
and game review (`GET /api/me/games/{id}` → `MyGameDetail`). We re-snapshotted
`openapi.json` from the **deployed prod** backend and regenerated
`src/api/generated/schema.ts`. No feature code, UI, routes, or even an
`errors.ts` mirror ship here — this only makes the new profile paths and
schemas type-available for the upcoming `me-stats` / `game-reviews` /
`edit-profile` features. It is the **simplest** of the four re-snapshots:
the contract grew (paths + schemas + one additive field) but the
`ErrorResponse.error` enum did **not** change, so the hand-written
exhaustiveness-guarded `errors.ts` needed no edit at all.

## The contract delta (verified prod vs committed snapshot, 2026-06-26)

The re-fetched snapshot matched the leader's pre-verified delta exactly:

- **New paths (3):** `/api/me/games/{id}`, `/api/me/password`,
  `/api/me/stats`.
- **New method on an existing path:** `PATCH /api/me` (the path previously
  exposed only `GET`).
- **New schemas (4):** `ChangePasswordRequest`, `MyGameDetail`,
  `MyStatsResponse`, `UpdateProfileRequest` (27 → 31 schemas).
- **Additive field:** `MyGameSummary.result` — a nullable enum
  `WHITE_WIN | BLACK_WIN | DRAW` (null for legacy archived games whose
  winner was unknown at backfill time). It also appears on the new
  `MyGameDetail`.
- **New error codes:** **NONE.** The `ErrorResponse.error` enum is
  byte-identical before and after (21 codes, verified by `diff`). Unlike
  20.1 (3 new codes), 21 (1 new code, `INVALID_JOIN_TOKEN`), and 26.8 (8
  new codes), this snapshot adds **zero**, so `errors.ts` is untouched and
  there is no `mapError` test to extend.
- **Removed/renamed schemas or paths:** NONE. No `components['schemas'][...]`
  alias retarget (contrast 20.1's `Player` → `PlayerView` rename).

**One harmless deviation from the leader's hand-listed delta:** the leader's
note framed "GET on `/api/me/games`" as newly added. It was in fact already
present in the committed snapshot since feature 21 (`MyGameSummary` /
`MyGamesPage` shipped then). So `/api/me/games` is unchanged here; only its
item-detail sibling `/api/me/games/{id}` is new. This is purely additive and
changes nothing about the outcome — flagged for accuracy, not as a blocker.

## TS / React concepts that appear

- **OpenAPI → TypeScript codegen (`openapi-typescript`)** — the
  `openapi:generate` npm script feeds `openapi.json` into
  `openapi-typescript`, emitting one `schema.ts` that exports a
  `components['schemas'][...]` namespace and a `paths` map. Our
  hand-written wrappers (`errors.ts`, `games.ts`, `rooms.ts`, …) alias
  into that namespace, so a contract change surfaces as a **compile**
  error rather than a runtime surprise. Generation is deterministic:
  re-running it on an unchanged spec yields a byte-identical file
  (verified idempotent here via `diff` — second `generate`, no diff).

- **Additive (optional) field vs exhaustiveness** — `MyGameSummary.result`
  lands as an **optional** property (`result?: 'WHITE_WIN' | 'BLACK_WIN' |
'DRAW'`) because the backend's `@Schema` does not mark it required (it is
  nullable for legacy rows). Optional additive fields are the safest kind of
  contract change for a structurally-typed consumer: no existing read site
  breaks, because nobody is forced to handle a field they never referenced.
  The typecheck stayed green precisely because **no code consumes `result`
  yet** — there is no `switch` over it, so there is no exhaustiveness guard
  to fall behind (contrast 21's `TIMEOUT`, which joined `GameStatus` and
  forced `isTerminalStatus`/`narrowStatus`/`terminalMessage` to grow a new
  arm at typecheck). The first feature to actually narrow on `result`
  (`game-reviews`) is where any exhaustiveness obligation appears, not here.

- **Indexed access + `NonNullable` deriving a literal union** —
  `errors.ts` derives `ServerErrorCode =
NonNullable<components['schemas']['ErrorResponse']['error']>`. Because the
  `error` enum did not change, that derived union is identical post-generate,
  so the `Exclude<A, B> extends never` exhaustiveness assertion in `errors.ts`
  stayed satisfied with no manual edit. This is the mechanism that _would_
  have forced a mirror (as in 26.8) had the enum grown — it simply did not
  fire this round.

## Decisions taken

- **Decision:** Snapshot from **prod**, not local, for this re-snapshot.
  - **Alternatives considered:** run the backend on `localhost:8080` and use
    the `openapi:fetch` script (which targets localhost); spin up a local
    instance.
  - **Why this one:** the profile-bundle commits are **deployed to prod**
    (verified live by the leader minutes before this session), so prod
    `/v3/api-docs` carries the full delta; `localhost:8080` is not running.
    Reproduce with:
    `curl -fsSL https://chess-backend.duckdns.org/v3/api-docs | jq . > openapi.json`.
    The `openapi:fetch` script's localhost URL was **not** rewritten — a
    configurable-URL script remains a separate polish item, deliberately out
    of scope (same call as 21 and 26.8).

- **Decision:** ship **no `errors.ts` change** and **no new test**.
  - **Why:** the `ErrorResponse.error` enum is byte-identical pre/post
    (confirmed by `diff`), so the const object, `KNOWN_CODES` set, and
    `errorMessages` map are already exhaustive against the regenerated
    `ServerErrorCode`. Adding a placeholder test for unchanged behaviour
    would be noise. This is the cleanest re-snapshot of the four: the entire
    deliverable is `openapi.json` + the regenerated `schema.ts`.

- **Decision:** ship **no feature code** for `result` / the new schemas.
  - **Why:** the plan scopes this as a pure enabler. Consuming `result`,
    `MyStatsResponse`, `MyGameDetail`, `UpdateProfileRequest`, and
    `ChangePasswordRequest` is the job of the three now-unblocked features
    (`me-stats`, `game-reviews`, `edit-profile`). Touching them here would
    blur the commit boundary the user keeps per-feature.

## How this compares to what I know

- **In tapir / circe this would be...** regenerating client stubs from the
  server's `Endpoint` definitions. `openapi-typescript` is the client-side
  equivalent of deriving a typed client from an OpenAPI document — except the
  "codec" is structural typing plus `JSON.parse`, not a derived `Decoder[A]`.
  The generated types are erased at compile time, so a wire payload that lies
  about its shape type-checks and only blows up where you touch a missing
  field. That is why `errors.ts` keeps runtime guards (`isServerErrorBody`,
  `KNOWN_CODES.has(...)`) alongside the types.

- **An additive optional field is the structural-typing equivalent of...**
  adding a field with a default to a circe-decoded case class: existing
  decoders/consumers keep working because they never demanded the field.
  Where Scala would express the nullability as `Option[GameResult]`,
  `openapi-typescript` expresses it as `result?: 'WHITE_WIN' | ...` — the `?`
  is the `Option`. The difference: in Scala you'd be forced to handle the
  `None` case at the first `match`; in TS nothing forces you until you write
  a narrowing `switch`, at which point the `Exclude<...> extends never` trick
  (or a `default: assertNever`) is how you re-introduce the sealed-trait
  exhaustiveness the language doesn't give you for free.

- **Codegen idempotency** is the `scalapb`/guardrail property: running the
  generator twice on the same input is a no-op. Verified explicitly here
  (regenerate, `diff`, expect empty) so the committed `schema.ts` is
  reproducible from the committed `openapi.json`.

## Gotchas / things I learned the hard way

- None this round. The delta matched the leader's pre-verification (3 paths
  - PATCH /api/me + 4 schemas + `MyGameSummary.result` + zero error codes +
    zero renames). The one nuance — `GET /api/me/games` was already present
    since feature 21, not newly added — is cosmetic and additive, so it
    changed nothing. Worth re-stating the standing lesson from 20.1/21/26.8
    anyway: for a codegen change, let `tsc` enumerate the full blast radius
    rather than trusting a hand-listed set of call sites. Here `tsc` had
    nothing to say, which is exactly the signal that the change is purely
    additive.
