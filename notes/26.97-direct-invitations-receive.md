# Feature 26.97 — Direct invitations (receive)

**Feature ID:** `direct-invitations-receive` (from `feature_list.json`)

**Status:** in progress

---

## What we built

The first (infra-heavy) half of direct game invitations: the **receive**
side. A signed-in user now holds an app-level, JWT-authenticated STOMP
connection to their personal `/user/queue/invitations` queue. When a friend
invites them to a room, a badged "Invitations" control in the Header lights
up; opening it shows a push-style panel listing each inviter and time
control with **Accept** (joins the room and navigates to `/play`) and
**Reject** (declines) actions. The list is seeded from REST on connect and
reconciled live by `INVITATION_RECEIVED` / `INVITATION_CANCELLED` pushes.

Out of scope (→ `direct-invitations-send`, 26.98): sending/cancelling
invitations, the friend picker on Play, and the inviter-side
`INVITATION_DECLINED` toast.

## TS / React concepts that appear

- **An app-level provider with a self-owned effect connection.**
  `InvitationsProvider` (mounted in `App.tsx` inside `UserContextProvider`)
  runs a `useEffect` keyed on the authenticated `userId`. The effect builds
  a STOMP client, connects, subscribes, seeds from REST, and returns a
  cleanup that unsubscribes + disconnects. The dependency `[userId]` makes
  the whole connection a function of identity: guest → no effect body runs;
  sign-in → connect; logout → cleanup. This is the same lifetime idiom as
  `useGameStomp`, but at session scope instead of per-game.

- **Discriminated unions + exhaustive `switch`.** The three invitation
  events share a `type` literal (`InvitationQueueEvent`); the provider's
  `applyEvent` narrows on it and ends with `const _exhaustive: never =
event` so a future fourth variant fails to compile until handled. Same
  pattern the game-topic events already use.

- **A const-object discriminant (`InvitationQueueEventType`).** Values ARE
  the wire literals (`'INVITATION_RECEIVED'` …) so equality checks and
  narrowing work without a parallel `enum`, while call sites read
  `InvitationQueueEventType.Received` (go-to-definition friendly).

- **`Readonly<T>` / `ReadonlyArray<T>` at the boundary.** `Invitation`,
  every event shape, and the context's `invitations` are read-only — the
  compiler stops a consumer from mutating the list in place; reconciliation
  goes through `setInvitations` with fresh arrays.

- **A factory seam for testability.** The provider takes an optional
  `clientFactory` (and `listInvitations`) prop defaulting to the real
  implementations, so tests inject a `MockStompClient` and a stub seed with
  zero real I/O — the exact seam `useGameStomp` established.

## Decisions taken

- **A SEPARATE STOMP connection from the per-game one.**
  - _Alternatives:_ multiplex both subscriptions on one shared client.
  - _Why this one:_ the two connections differ on every axis — auth (a
    `Authorization: Bearer <jwt>` CONNECT header vs. a `playerId` SUBSCRIBE
    header), destination (a personal `/user/queue/...` vs. a public
    `/topic/games/...`), and lifetime (the whole session vs. one game).
    Coupling them would entangle two independent lifecycles. The cost is a
    second socket per signed-in user, which is negligible.

- **`connectHeaders` added to the STOMP wrapper config, not a bespoke
  auth path.** `@stomp/stompjs` forwards `client.connectHeaders` on the
  CONNECT frame natively, and the backend's `StompAuthInterceptor` reads
  `Authorization` there to resolve the session Principal. Threading it
  through `StompClientConfig` keeps the wrapper the single seam and lets the
  per-game connection keep omitting it. A unit test asserts the header
  reaches the underlying client.

- **Seed-from-REST first, then reconcile by push.** The subscribe is set up
  _before_ the `listInvitations()` await so a push that races the GET is not
  dropped; `applyEvent` de-dupes by `roomId`, and the seed merge skips
  roomIds already present. Simpler and more robust than trying to order the
  two sources.

- **Push UX, not a modal.** Per the `inline-status-over-modals` memory,
  incoming invitations are a state the user did NOT cause, so they surface
  as a passive badge + dropdown panel rather than interrupting with a modal.

- **The `INVITATION_RECEIVED` push synthesizes `side`/`createdAt`.** The
  push event carries neither field (only the REST `InvitationResponse`
  does). The panel renders inviter + time control only, so the synthesized
  defaults are never shown; a later REST refresh would supply the real
  values. Documented in the provider so a future reader isn't surprised.

- **MSW over hand-rolled fetch mocks.** The API tests register handlers at
  `TEST_API_BASE_URL` and exercise the real `openapi-fetch` client +
  `mapError` discipline — same pattern as `friends.test.ts` / `rooms.test.ts`.

## How this compares to what I know

- **In Cats Effect this would be…** the provider's `useEffect` +
  cleanup is `Resource.make(connect)(disconnect)` whose scope is the
  component's mounted lifetime. Re-keying the effect on `userId` is like
  re-acquiring the `Resource` when an input changes — the old resource is
  released (disconnect) before the new one is acquired. The `cancelled` flag
  guarding post-await `setState` is the manual analogue of a fiber
  cancellation check (`F.canceled`/`guarantee`).

- **In http4s/circe this would be…** the `narrowInvitation` /
  `narrowSide` / `narrowTimeControl` functions are the hand-written
  equivalent of a circe `Decoder` that fails with a typed error
  (`ApiError(UnknownError)`) on a missing required field. openapi-typescript
  types every field optional (Spring's `@Schema` doesn't mark them
  `required`), so the boundary narrows optional → mandatory, exactly like a
  `Decoder[A]` turning a loose JSON into a case class.

- **In tapir this would be…** `InvitationQueueEvent` is a sealed-error /
  sealed-output ADT discriminated by a string tag. Tapir narrows on the type
  via `oneOf`; here we narrow on `event.type` and the `never` default is the
  compile-time exhaustiveness check tapir gives you from the sealed trait.

- **The const-object + derived-type pattern** is what you'd reach for in
  Scala 3 with an `enum` whose cases have stable string encodings — except
  TypeScript keeps value and type in separate namespaces, so
  `InvitationQueueEventType` is simultaneously a runtime object and a type.

## Gotchas / things I learned the hard way

- `UserContextProvider`'s `initialIdentity` is read in a **lazy `useState`
  initializer**, so it only applies on first mount. A test that tried to
  flip identity → guest by re-rendering with a new `initialIdentity` was a
  no-op; the logout test had to drive the real `logout()` op from context
  instead.
- The `GET /api/me/invitations` OpenAPI snapshot types the 200 body as a
  single `InvitationResponse`, but the backend returns a JSON **array** —
  Spring's `@Schema` flattened the list. The wrapper re-casts at the
  boundary (documented), the only escape hatch in the module.
- An authenticated identity with **no persisted token** (degraded storage)
  must skip the connection — without a Bearer header the broker can't
  resolve the Principal and would reject the CONNECT. The provider guards on
  `readToken() === null`.
