# Feature 06.8 — Play page UX polish

**Feature ID:** `play-ux-fixes`

**Status:** in progress (pending reviewer + user sign-off)

---

## What we built

Four small UX fixes layered onto `Play.tsx`, all surfaced by the manual
two-browser smoke against the live backend in feature 6.7:

- **A.** A "not your turn" Snackbar fires when chess.js detects the
  local player tried to move on the opponent's turn. Previously the
  drag silently failed because the server-side `NOT_YOUR_TURN` error
  was the only path that fired a Snackbar — and we never reached the
  server.
- **B.** Opponent pieces are no longer draggable. We pass the
  `canDragPiece` callback to `react-chessboard` v5, which short-circuits
  the drag-start handshake when the piece's first character of
  `pieceType` (`'w'`/`'b'`) does not match the local player's `Role`.
  The user sees no grab cursor on enemy pieces.
- **C.** Dropping a piece on its source square (changing your mind) no
  longer surfaces a Snackbar. We early-return `false` from `onDrop`
  when `sourceSquare === targetSquare`, before chess.js sees the
  malformed `from === to` move.
- **D.** The terminal-status `CustomDialog`'s "Continue" button now
  navigates to `/new` instead of dismissing the modal and leaving the
  user stranded on a frozen board. The label stayed as "Continue" to
  avoid touching the shared `CustomDialog` API; the action is the
  load-bearing change.

No new dependencies. No backend coordination. Two files touched:
`src/pages/Play/Play.tsx` and `src/pages/Play/Play.test.tsx`.

## TS / React concepts that appear

- **The react-chessboard v5 callback contract.** v5 funnels its
  configuration through a single `options` prop on `<Chessboard />`.
  `options.canDragPiece` is `(args: PieceHandlerArgs) => boolean`,
  where `PieceHandlerArgs.piece.pieceType` is the camel-cased FEN code
  (`'wP'`, `'bK'`, ...). Returning `false` blocks the drag at its
  source. Compare with `onPieceDrop`, which can also return `false`
  but only after the drag has already happened — the visual feedback
  is different.
  [react-chessboard v5 docs](https://www.npmjs.com/package/react-chessboard).
- **Client-side validation as UX, server-side as authority.** Bugs A
  and C are both client-side gates: chess.js sees the move before the
  server does and refuses it. The cleanest pattern is to keep the
  server authoritative on legality (the backend's `ChessRules` is the
  source of truth) while letting the client _surface_ the same user
  experience cheaply when it can. Bug A reuses the existing
  `messageFor(ApiErrorCode.NotYourTurn)` string so the client and
  server paths render identically.
- **`useNavigate()` for programmatic navigation in react-router v7.**
  The hook returns a function with signature `(to: To, options?) =>
void`. Bug D wires it into the `handleContinue` of a `CustomDialog`
  to leave the page on click. Mocking it in the test is a
  `vi.mock('react-router-dom', async () => ({ ...actual, useNavigate:
() => navigateMock }))` shim that preserves the rest of the router
  API (we still wrap with `MemoryRouter` so other hooks behave).
- **Mocking a component with `vi.mock` to capture props.** The Bug A
  and C tests cannot drive the real chessboard's drag-drop through
  jsdom — the library uses pointer events that jsdom does not
  faithfully simulate. The workaround is to replace `<Chessboard />`
  with a stub that captures the `options` object into a module-level
  ref (`lastChessboardOptions`). Tests then call
  `lastChessboardOptions.onPieceDrop(...)` directly, asserting against
  the component's behaviour rather than the library's rendering.
  Reset in `beforeEach` to keep test isolation honest.

## Decisions taken

- **Decision:** reuse `errorMessage` state + the existing Snackbar
  surface for Bug A instead of adding a parallel `turnError` state.
- **Alternatives considered:** a separate `turnError: string | null`
  state with its own Snackbar JSX. The plan flagged either as
  acceptable.
- **Why this one:** the visual treatment is identical (red `Alert`,
  `filled` variant, bottom-center), and the messaging vocabulary is
  identical (`messageFor(ApiErrorCode.NotYourTurn)`). Adding a second
  state would have duplicated the Snackbar JSX without changing what
  the user sees. The semantic distinction (client-side validation vs
  server-side error) lives in the comment next to the `setErrorMessage`
  call. If we later want to style turn-mismatch differently — perhaps a
  warning instead of an error, or auto-dismiss faster — splitting
  state is a 5-minute refactor.

- **Decision:** keep the dialog button label as "Continue" rather
  than renaming to "New Game".
- **Alternatives considered:** (1) rename in-place — but `CustomDialog`
  is shared with the promotion dialog and hardcodes the label. (2) Add
  an optional `continueLabel?: string` prop. (3) Two buttons: "New
  Game" and "Home".
- **Why this one:** the plan ranks the alternatives "single button
  renamed" as recommended, but renaming requires a new prop on
  `CustomDialog` (the label is hardcoded today). The action is the
  load-bearing change; the label is cosmetic. Keeping the label means
  zero churn in the shared dialog component, which is the right
  trade-off at this scope. Two-button design is overkill — the drawer
  already exposes Home navigation, and "new game" is what the user
  almost always wants next.

- **Decision:** mock `react-chessboard` globally in `Play.test.tsx`
  rather than rendering the real board.
- **Alternatives considered:** drive Bug A/C with a real
  pointer-events simulation; assert Bug B by reading from the DOM
  cursor style.
- **Why this one:** jsdom does not faithfully simulate the
  pointer/drag events react-chessboard relies on, and asserting on
  CSS cursor state would couple the test to library internals. The
  mock makes the contract between `Play.tsx` and the library
  observable directly: tests verify the right callbacks are passed,
  not the library's drag-drop mechanics. The library is its own
  vendor with its own tests; we test the integration.

## How this compares to what I know

- **In Cats Effect this would be...** the client-side validation
  pattern (Bug A, Bug C) is the React equivalent of a `Validated`
  short-circuit before an HTTP `Resource.use`. The `Resource` is the
  "send the move" effect; the `Validated` rejects bad inputs before
  the resource acquires anything. In React the "resource" is the
  fetch and the "validation" is a function in the component body —
  but the shape (reject early, never enter the IO) is the same. The
  client doesn't replace the server's check; it pre-empts it for UX.
- **In http4s this would be...** the Bug B `canDragPiece` callback is
  what you would get from a `Middleware` that filters requests before
  they reach the route. The `Middleware` short-circuits with a
  `Forbidden` response when the caller does not own the resource. In
  the chessboard, returning `false` from `canDragPiece` is the same
  shape: short-circuit at the source, never let the "request" (drag)
  reach the "route" (drop handler).
- **In Refined this would be...** `pieceType[0] === expected` is a
  string-prefix predicate. The Scala/Refined idiom would lift it into
  a refined type like `OwnedPieceType` with a `Refined` constraint
  that the first character matches the player's color. TypeScript's
  type system can't express "first character of a string" elegantly,
  so the predicate stays at the runtime layer.
- **Compared to Tagless Final**: the `useNavigate()` hook is the React
  equivalent of injecting a `Navigation[F]` algebra into the component.
  The mock in the test (`navigateMock`) is the test-time interpreter;
  the real `useNavigate()` is the production interpreter. Same
  pattern, different vocabulary — React calls it "hooks", FP calls it
  "tagless final".

## Gotchas / things I learned the hard way

- The `vi.mock('react-router-dom', async () => ...)` factory must
  preserve the rest of the module via `vi.importActual`. Forgetting
  this strips `MemoryRouter` and the existing tests immediately
  break with "useSearchParams undefined". The pattern is identical
  to the `vi.mock('../../utils/ws', ...)` shim already in the file.
- `pieceType` is a string typed as `string` in the library's d.ts,
  not a literal union. Indexing `[0]` to get `'w'` or `'b'` is fine
  but unverifiable at compile time — runtime payload is trusted. If
  the library ever ships a non-camelCase variant the predicate would
  silently allow everything. Acceptable for now; the inverse test
  (opponent pieces returning `false`) is the regression net.
- The existing Play tests dispatch over the mocked STOMP client to
  drive the page; they do not interact with the chessboard's drag
  mechanics. That made the global Chessboard mock safe to add — no
  existing test queries inside the board's DOM.
