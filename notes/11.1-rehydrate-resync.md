# Feature 11.1 — Rehydrate resync

**Feature ID:** `rehydrate-resync` (from `feature_list.json`)

**Status:** in progress

---

## What we built

A single small effect on the Play page that re-fetches authoritative
game state from `GET /api/games/{gameId}` every time the live-updates
client transitions back into `Connected` after a drop — covering tab
restore, wake-from-sleep, and any STOMP reconnect window during which
moves may have happened that the client was not subscribed to. The
existing initial-load effect handles the first GET; the new effect
handles every subsequent reconcile. Two compounding race gaps in
feature 10's rehydrate design (one-shot initial GET; silent
`prev === null` drop in `applyOpponentMove`) collapse into one: the
resync IS the chokepoint, the backend Postgres state is the source of
truth, and any temporarily-divergent local state is restored on the
next transition into Connected.

## TS / React concepts that appear

- **`useRef` for tracking previous values across renders** —
  ([React docs — `useRef`](https://react.dev/reference/react/useRef))
  React effects observe the _current_ value of every dependency, not
  the _change_. Reacting to a transition (Disconnected → Connected)
  means manually carrying the previous value across renders. A
  `useRef<ConnectionState | null>` is the React-idiomatic place: the
  ref's `current` field is mutable, doesn't trigger re-renders, and
  survives every render of the same component instance. The `null`
  initialiser doubles as a sentinel for "we have not yet observed a
  Connected state on this mount" — guarding against the duplicate
  fetch on the initial Disconnected → Connected pass that the
  initial-load effect already issues. The Scala/Typelevel analogue
  is `fs2.Stream.scan` or `zipWithPrevious`: you fold the current
  value with the previous to drive a transition-aware downstream.

- **The "deferred-correctness" anti-pattern** — Feature 10 left a
  comment in `applyOpponentMove` promising "the next GET (or the next
  event) will catch up" when an opponent's MoveEvent arrived before
  the initial REST snapshot. The promise was hollow: no next GET was
  ever scheduled, and a quiet opponent left the client stuck at the
  initial position. The Scala/Typelevel analogue is a
  `Future.flatMap(_ => ???)` chain where the next stage is never
  enqueued — the type system says "I will get there", but the
  runtime never does. The fix here is the same fix you would apply
  in Scala: make the "next stage" an explicit, observed effect
  (the resync `useEffect`), not a comment promising a future
  state-change that nobody actually triggers.

- **`useEffect` observer vs `useReducer` state machine** —
  ([React docs — `useEffect`](https://react.dev/reference/react/useEffect),
  [React docs — `useReducer`](https://react.dev/reference/react/useReducer))
  Connection lifecycle is a small ADT (`Connecting | Connected |
Disconnected | Error`) with well-defined transitions. A single
  `useEffect` plus a `useRef<previous>` is enough at this surface
  because the only behaviour that depends on the transition is the
  resync fetch — there is no UI state that needs to fan out from
  multiple transitions, no orthogonal cross-cutting state, no
  guard-on-other-state ceremony. Once a feature requires multiple
  observers gating on the same transitions, or a transition table
  with action effects (think feature-11's grace-period countdown +
  opponent-status chip + abandon banner), `useReducer` with named
  actions (or XState if the machine gets complex) becomes the right
  tool. The threshold is "more than one observer depends on the
  same transition" or "guarded transitions whose source of truth
  is the machine itself".

- **`useState` lazy initialiser vs `useRef` initial value** — Both
  accept an initial value; both run it once per mount. The
  difference: `useState`'s value drives re-renders and lives on the
  React fiber's commit slot, while `useRef`'s value is a mutable
  cell that does not trigger re-renders. For "track the previous
  value of a state for transition logic" the ref is the right tool
  — we don't want re-renders cascading from the bookkeeping itself.

## Decisions taken

- **Decision: Guard approach B (`useRef<ConnectionState | null>`)
  over approach A (`useRef<boolean> hasFetchedOnce`).**
  - **Alternatives considered:** approach A — flip `hasFetchedOnce`
    in the initial-load effect's success path; the transition effect
    gates on it.
  - **Why this one:** decoupling — approach A couples the
    initial-load effect to the transition effect via a shared ref,
    so a future refactor that splits or rewires the initial load has
    to remember to flip the flag at the right moment. Approach B
    keeps both effects single-purpose: the initial-load owns its
    GET; the transition effect owns every subsequent reconcile via
    its own private ref. The ref's `null` sentinel doubles as the
    "initial transition" marker, so the transition effect needs
    nothing from outside itself.

- **Decision: Keep the `prev === null` early-return in
  `applyOpponentMove` instead of also fixing it.**
  - **Alternatives considered:** also fix the early-return — when
    `prev === null` and we have a `MoveEvent`, fabricate a partial
    `gameState` from the event (FEN + status + turn + a singleton
    moves array) so the page renders the latest position even if
    the initial GET has not resolved yet.
  - **Why this one:** single-chokepoint principle. The resync covers
    the same ground (and more — it also covers transient drops
    where the early-return path never runs because the event was
    lost on the wire entirely). Defence-in-depth would mean two
    independent fix-up paths racing each other and writing the same
    state slot; we prefer one path that is easy to reason about and
    test. The comment in `applyOpponentMove` now points at the
    resync effect by name so a future reader follows the link
    instead of re-rediscovering the "is this missing a fallback?"
    question.

- **Decision: Wire `stompjs`'s `onWebSocketClose` and post-handshake
  `onConnect` through to `StompClientConfig` so `useGameStomp`'s
  `connectionState` actually reflects production reconnect transitions.**
  - **Alternatives considered:** leave the hook as-is (only cycles
    on mount / gameId change). The resync effect would still cover
    the user-reported tab-restore case via the fresh initial-load
    GET, but the other listed scenarios (network drop + recovery,
    wake-from-sleep on a still-mounted page) would never fire the
    resync because `connectionState` would never transition.
  - **Why this one:** the resync effect should reflect the actual
    underlying connection state, otherwise the abstraction lies.
    Surfacing every transition into `Connected` via the existing
    `StompClient`/`StompClientConfig` seam keeps the change scoped
    to the wrapper module — no new infrastructure, no XState, no
    parallel observer plumbing. Reconnect-after-drop subscription
    re-issuing is a separate concern explicitly deferred (the
    backend is the source of truth for game state, and the resync
    GET is the chokepoint that pulls it down again).

- **Decision: Mock `useGameStomp` for the resync-specific Vitest
  tests instead of driving the real hook through the existing
  `createStompClient` mock seam.**
  - **Alternatives considered:** drive `connectionState` transitions
    via the existing test seam — e.g. by changing `gameId` in
    context to force the hook's effect teardown + rerun cycle.
  - **Why this one:** simplicity. The resync effect's behaviour is
    entirely about reacting to a `connectionState` value;
    re-routing context changes to fake reconnects coupled the test
    to a lot of unrelated lifecycle. Mocking the hook gives the
    test a precise lever (`setConnection(...)` in `act()`) and
    leaves the production hook tested independently in
    `useGameStomp.test.ts` and end-to-end in `e2e/resync.spec.ts`.
    The resync-specific tests live in a separate file
    (`Play.resync.test.tsx`) so the `useGameStomp` mock doesn't
    leak into the existing `Play.test.tsx` suite that relies on the
    real hook.

- **Decision: New `e2e/resync.spec.ts` instead of extending
  `e2e/abandonment.spec.ts`.**
  - **Alternatives considered:** add the resync scenario as a
    second test case in `abandonment.spec.ts`.
  - **Why this one:** the abandonment scenario asserts a
    single-page disconnect-UX flow (chip + banner + redirect); the
    resync scenario asserts a reconnect-and-reconcile flow. Two
    distinct user journeys with no shared setup beyond the broker
    mock. Separating the specs keeps each file's name a faithful
    summary of the journey it covers — a reviewer looking at
    "abandonment" should not have to scroll past resync tests.

## How this compares to what I know

- **In Cats Effect this would be...** a `fs2.Stream[IO, ConnectionState]`
  with `zipWithPrevious`, filtered to `(prev, curr) =>
prev =!= Connected && curr === Connected`, mapped to an `IO[Unit]`
  that runs `getGameState >>= syncFromServer`. The `useRef<previous>`
  pattern here is the React-idiomatic spelling of `zipWithPrevious`:
  carry the previous value, fire on edges, not on values. The
  `null` sentinel is the "skip the first edge" filter — in fs2 you
  would `.tail` the resulting stream or filter on
  `prev.isDefined`.

- **In Cats Effect this would also be...** a `Resource[IO, Unit]`
  bound to the Play page's lifetime that subscribes to the
  connection-state signal and runs the resync on each
  `Connected` re-entry. `useEffect` + `useRef` is the React
  analogue of `Resource.make(acquire)(release)` carrying a
  closure-scoped state cell.

- **In tapir this would be...** unchanged on the wire — `getGameState`
  is the same `Endpoint[GameId, ApiError, GameState, Any]` we already
  call. The interesting bit is _when_ we call it. tapir doesn't
  prescribe a "call when connection state changes" pattern; that
  would be downstream of an `fs2.Stream` of connection events
  derived from the WS client's own lifecycle hooks.

- **The "next GET will catch up" anti-pattern compared to
  `Future.flatMap`** — the Scala version would be a chain like
  `fetchInitial.flatMap(applyMove(_, event))` where `event`
  arrived but `applyMove` is never invoked because nobody actually
  scheduled the `.flatMap`. The TypeScript version was a comment.
  Both fail the same way: the type system / docstring claims a
  future stage; the runtime never honours it. The fix in both
  ecosystems is to make the stage explicit and observed.

- **`useRef` vs `Ref[IO, A]`** — both are mutable cells. `useRef`
  is synchronous and React-idiomatic; reads are O(1) at any point
  in render, writes don't trigger re-renders, lifecycle is
  bounded to the component instance. `Ref[IO, A]` is referentially
  transparent (every read is an `IO[A]`), bounded to the resource
  scope that constructed it, and integrates with concurrent
  effects via `update` / `modify`. The semantics are the same
  ("mutable cell with no reactivity ceremony"); the integration
  story is what differs.

## Gotchas / things I learned the hard way

- The `null` sentinel only works if you do NOT advance the ref on
  non-Connected passes. My first draft set
  `previousConnectionState.current = connectionState` unconditionally
  at the top of the effect, which burned the `null` sentinel before
  the first Connected ever arrived. The fix was branch-local
  advancement: only flip the ref from `null` inside the Connected
  branch (so the very first Connected becomes the "initial" pass
  the effect suppresses), and only record non-Connected states
  AFTER the sentinel has been flipped (so a mid-mount drop doesn't
  burn the sentinel either).

- `@stomp/stompjs`'s steady-state `Client.onConnect` is replaced
  during the wrapper's `connect()` promise plumbing — the original
  handler resolves the promise on the first CONNECTED, then the
  hook never sees subsequent re-connects. Fixing this required
  re-wiring the handler to call `config.onConnect?.()` from the
  resolve path AND for every subsequent CONNECTED frame stompjs
  surfaces on auto-reconnect.

- Subscriptions issued via `Client.subscribe()` are NOT re-issued
  on stompjs's auto-reconnect — they belong to the prior socket.
  This is genuinely out of scope for this feature (the resync GET
  is the chokepoint, and the backend state is the source of truth),
  but it means a fully-correct long-running session would need
  either a re-subscribe step on `onConnect` or a different STOMP
  client. Captured for a future feature.

- Playwright's `WebSocketRoute.close()` triggers the browser-side
  `WebSocket`'s close event, which stompjs handles via its
  reconnect timer (default 5s). The e2e test waits ~5s for the
  reconnect; the spec sets `test.setTimeout(60_000)` to keep
  headroom. Faster reconnection would require either configuring
  `reconnectDelay` per-environment (production = 5s, test = 100ms)
  or a different transport-level mocking strategy — neither is
  worth it for one test.
