# Feature 20.9 — Clear devDep audit CVEs via overrides

**Feature ID:** `deps-audit-overrides` (from `feature_list.json`)

**Status:** done

---

## What we built

`npm audit --audit-level=moderate` went red while verifying feature 21,
reporting four transitive devDependency advisories that landed in the
~3 weeks since the last green run. None of them reach the production
bundle (they live under jsdom, openapi-typescript, and
eslint-plugin-react-hooks — all build/test/codegen tooling). We cleared
them by extending the `overrides` block in `package.json` (the same
mechanism feature 0.5 used for `ws`/`esbuild`), pinning patched versions
of the three offending leaf packages. The audit gate now exits 0, the
production bundle is byte-for-byte unchanged, and `./init.sh` is green
end-to-end again — which also unblocks feature 21, whose only failing
gate was this audit.

## The four CVEs and why `npm audit fix` couldn't clear them

| Package                 | Severity | Vulnerable range                  | Reached via                                              |
| ----------------------- | -------- | --------------------------------- | -------------------------------------------------------- |
| `undici`                | high     | `7.0.0 - 7.27.2`                  | `jsdom` (Vitest's DOM env)                               |
| `js-yaml`               | moderate | `<= 4.1.1`                        | `openapi-typescript` → `@redocly/openapi-core` (codegen) |
| `@redocly/openapi-core` | moderate | (depends on vulnerable `js-yaml`) | `openapi-typescript`                                     |
| `@babel/core`           | low      | `<= 7.29.0`                       | `eslint-plugin-react-hooks` (lint)                       |

That is the "4 vulnerabilities (1 low, 2 moderate, 1 high)" the report
counts. `@redocly/openapi-core` is not a separate root cause: it is a
_via_ node flagged only because it depends on the vulnerable `js-yaml`,
so pinning `js-yaml` clears it transitively. The real override targets
are three leaf packages: `undici`, `js-yaml`, `@babel/core`.

`npm audit fix` (the non-`--force` form `init.sh` would tolerate) does
not touch any of them. The reason is the same one documented in feature
0.5's note: the direct devDeps (`jsdom@29`, `openapi-typescript@7`,
`eslint-plugin-react-hooks@7`) still declare semver ranges that resolve
to the _vulnerable_ transitive versions, and `audit fix` will not bump a
transitive past the range its parent permits without a major bump of the
parent — which it refuses to do silently. The lockfile had also drifted:
it pinned `undici@7.25.0` even though a reinstall had pulled `7.28.0`
into `node_modules`, so the audit (which reads the lockfile) reported a
version no longer on disk. Regenerating the lockfile under explicit
overrides fixes both the drift and the advisories in one pass.

## The chosen override versions + rationale

```jsonc
"overrides": {
  "esbuild": ">=0.25.0",   // pre-existing (feature 0.5)
  "ws": ">=8.20.1",        // pre-existing (feature 0.5)
  "undici": ">=7.28.0",    // first patched version above 7.0.0-7.27.2
  "js-yaml": ">=4.2.0",    // patched minor; stays on the 4.x line
  "@babel/core": ">=7.29.1" // patched; resolves to 7.29.7
}
```

Resolved lockfile pins after `npm install`: `undici@7.28.0`,
`js-yaml@4.2.0`, `@babel/core@7.29.7`.

Each pin is the **minimal** non-vulnerable version, deliberately staying
on the same major as the consuming tool so the override is a pure
patch/minor lift with no API surface change:

- **`undici >= 7.28.0`** — `7.28.0` is the only published version above
  the vulnerable `7.0.0 - 7.27.2` range. It stays on the 7.x major that
  `jsdom@29` expects.
- **`js-yaml >= 4.2.0`** — `4.2.0` is the patched minor on the 4.x line.
  `5.0.0`/`5.1.0` exist but are a major bump (and too recent — see
  min-release-age below), so the conservative 4.x pin is the right one
  for a transitive of a codegen tool.
- **`@babel/core >= 7.29.1`** — resolves to `7.29.7`, the patched
  version already in `node_modules` before the lockfile was regenerated.
  `8.x` exists but is a major; the 7.29.x patch is sufficient.

### min-release-age=7 compliance (the load-bearing constraint)

`.npmrc` sets `min-release-age=7`: npm refuses any version published
less than seven days ago. Verified each pin against publish date with
today = 2026-06-22:

- `undici@7.28.0` — published 2026-06-15 15:51 UTC → **7.29 days old**.
  This is the tightest one: it cleared the window by roughly seven
  hours. Had `7.28.0` been the _only_ fix and still inside the seven-day
  quarantine, the correct move per the plan would have been to STOP and
  report rather than weaken `.npmrc`; it was not, so the override stands.
- `js-yaml@4.2.0` — published 2026-05-31 → ~22 days old. (`5.x` was
  rejected partly for being a major, partly because `5.0.0`/`5.1.0` were
  published 2026-06-20/06-22, well inside the quarantine.)
- `@babel/core@7.29.7` — published 2026-05-25 → ~28 days old.

`npm install` completed without a `min-release-age` rejection, which is
the runtime confirmation that every resolved version is old enough.

## Production-bundle-zero confirmation

The three overridden packages are transitive dependencies of
**devDependencies only**:

- `undici` ← `jsdom` ← Vitest's jsdom environment (test-time DOM).
- `js-yaml` ← `@redocly/openapi-core` ← `openapi-typescript` (the
  `openapi:generate` CLI; emits `schema.ts` at author time).
- `@babel/core` ← `eslint-plugin-react-hooks` (lint-time only).

None of them is imported by any module under `src/` that Vite bundles.
Concretely: `npm run openapi:generate` was re-run after the override and
`src/api/generated/schema.ts` was **byte-identical** (sha256
`696c04b8…` before and after) — the `js-yaml` bump did not change the
codegen output, so even the generated source the bundle _does_ compile
is unchanged. The `./init.sh` `vite build` step produced the same chunk
set it always does (`Play`, `context`, `index`, the lazy auth chunks).
The override delta is confined to `node_modules` tooling; the shipped
JavaScript is unaffected.

## TS / React concepts that appear

This is a harness/supply-chain feature — no React or TS source changed —
so the concepts are npm resolution mechanics.

- **`overrides` (npm 8.3+).** Forces the resolution of a _transitive_
  dependency without forking it or declaring it at the top level. A
  range value (`">=7.28.0"`) means "no version below this may appear
  anywhere in the tree". It is the only clean lever for a CVE that lives
  three levels down under a devDependency whose own semver range still
  permits the vulnerable version. Documented in
  [npm docs — overrides](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#overrides).
- **`overrides` cannot target a direct dependency.** npm errors
  `EOVERRIDE` if you try to override a package you also list in
  `dependencies`/`devDependencies`. All three packages here are purely
  transitive, so they are legal override targets — had a CVE required
  bumping `jsdom`/`openapi-typescript`/`eslint-plugin-react-hooks`
  themselves (a direct major), that would have exceeded this
  mini-feature's scope and triggered a STOP-and-report.
- **`min-release-age` and the override interaction.** An override pins a
  _minimum_ version; `min-release-age` independently filters out
  versions _too new_. The two can collide: if the only patched version
  is younger than the quarantine window, the override becomes
  un-installable and the honest answer is to wait or escalate, not to
  lower the floor. `undici@7.28.0` sat right on that boundary (7.29 days
  old) and squeaked through.
- **Lockfile is the audit's source of truth.** `npm audit` reads
  `package-lock.json`, not `node_modules`. A drifted lock (here pinning
  `undici@7.25.0` while disk had `7.28.0`) makes audit report a version
  that is not even installed. `npm install` reconciles the lock to the
  resolved tree, which is why the override + a fresh `npm install` (never
  a hand-edit; the `package-lock.json` Edit hook blocks that anyway) is
  the correct sequence.

## Decisions taken

- **Decision:** pin three leaf packages (`undici`, `js-yaml`,
  `@babel/core`) rather than four, and pin minimal patched
  versions on the existing major line.
  **Alternatives considered:** (a) also add an explicit
  `@redocly/openapi-core` override; (b) jump `js-yaml` to `5.x` and
  `@babel/core` to `8.x` to "stay current"; (c) `npm audit fix --force`.
  **Why this one:** `@redocly/openapi-core` is only flagged for
  depending on vulnerable `js-yaml`, so pinning `js-yaml` clears it — a
  fourth override would be redundant. Major bumps (`js-yaml@5`,
  `@babel/core@8`) carry API-break risk for no security benefit over the
  patched minor/patch, and `js-yaml@5` was inside the seven-day
  quarantine anyway. `--force` would have done exactly what feature 0.5
  warned against: silently downgrade or break a direct dep to satisfy
  the resolver.

- **Decision:** verify `min-release-age` compliance by hand against
  publish dates before relying on `npm install` not to reject.
  **Alternatives considered:** just run `npm install` and trust the
  failure mode.
  **Why this one:** `undici@7.28.0` was within hours of the quarantine
  edge. Confirming the exact age up front (and that no _older_ patched
  `undici` existed) meant the plan's "if the only patched version is too
  recent, STOP and report" branch was consciously evaluated, not
  stumbled past.

## How this compares to what I know

- **In sbt / Coursier this would be...** a `dependencyOverrides +=
"org" % "name" % "x.y.z"` plus Coursier's transitive eviction — you
  force a single coordinate's version across the whole resolution graph,
  exactly like npm `overrides`. The difference: sbt's threat model is
  "vulnerable bytecode at runtime", so an override there is purely about
  what executes in your JVM. Here, two of the three overridden packages
  (`js-yaml` under codegen, `@babel/core` under lint) never run in the
  shipped artifact at all — they are _build-tool_ dependencies, the
  equivalent of overriding a version inside an sbt _plugin's_
  dependencies rather than the application's. npm's `devDependencies`
  vs `dependencies` split is doing the work `Compile` vs `Test`/plugin
  scope does in sbt.
- **In OWASP Dependency-Check terms...** `npm audit` is the same
  CVE-database-cross-reference, but with npm you additionally control
  resolution declaratively in the manifest (`overrides`), whereas in
  Maven you'd reach for `<dependencyManagement>` to force a transitive
  version. The `min-release-age` quarantine has no Maven/Coursier analog
  — it is npm-specific defense against the compromised-account
  patch-publish vector.
- **Compared to a `Resource`-sequenced pipeline:** `./init.sh` is still
  the `acquire(install) >> rebuild >> audit >> lint >> typecheck >> test >> build`
  chain from feature 0.5's note; this feature just made the `audit` step
  in the middle stop short-circuiting the rest.

## Gotchas / things I learned the hard way

- **The lockfile and `node_modules` had drifted before I started.** The
  lock pinned `undici@7.25.0`; `npm ls` reported `7.28.0`. The audit
  read the lock and flagged a version that was not actually installed.
  Lesson: when `npm ls` and `npm audit` disagree, the lock is stale —
  regenerate it, don't chase the discrepancy.
- **`undici@7.28.0` cleared `min-release-age=7` by about seven hours.**
  If this feature had been attempted a day earlier, the only `undici`
  fix would have been quarantined and the right call would have been to
  STOP and report rather than ship. Worth re-checking the math rather
  than assuming "the patch exists" means "the patch installs".
