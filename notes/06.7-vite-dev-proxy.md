# Feature 06.7 — Vite dev server proxy

**Feature ID:** `vite-dev-proxy`

**Status:** in progress (pending reviewer + user sign-off)

---

## What we built

A dev-only same-origin shim so the frontend at `http://localhost:5173`
and the Spring Boot backend at `http://localhost:8080` look like one
origin to the browser. Vite's `server.proxy` forwards `/api/*` and
`/ws` to the backend; `config.default.ts` resolves `backendUrl` to the
empty string in dev mode (when `VITE_BACKEND_URL` is unset), which
turns every REST call into a path-relative URL and turns the STOMP
endpoint into `/ws`. The browser sees same-origin requests and skips
the CORS preflight entirely. Production builds are unchanged: the
deploy workflow sets `VITE_BACKEND_URL` to the duckdns origin and the
SPA talks to the backend directly over CORS.

Also new: `docs/local-e2e.md`, a step-by-step runbook for the
two-browser smoke procedure (create room, join, play, observe live
updates), including a troubleshooting block for the common failure
modes (port conflicts, stale `VITE_BACKEND_URL`, STOMP not
upgrading).

## TS / React concepts that appear

- **`server.proxy` in `vite.config.ts`.** Vite's dev server is a
  Node-side reverse proxy implemented on top of `http-proxy`. A
  proxy entry has shape `{ target, changeOrigin?, ws?, ... }`.
  `changeOrigin: true` rewrites the outgoing `Host` header to match
  the target — defensive against any host-name check on the backend
  (Spring's `forward-headers-strategy`, Nginx-style virtual hosts,
  etc.). `ws: true` is the load-bearing flag for WebSocket: without
  it, the proxy serves the initial HTTP request but does not perform
  the protocol upgrade, and the STOMP handshake fails.
  [Vite docs · server.proxy](https://vitejs.dev/config/server-options.html#server-proxy).
- **`import.meta.env.DEV` as a compile-time discriminator.** Vite
  replaces `import.meta.env.DEV` with the literal `true` or `false`
  during the build, identical to how it inlines `VITE_*` env vars.
  This is not a runtime check — the production bundle contains
  `false` literally and dead-code elimination drops the dev branch
  entirely. We use it to pick between the empty same-origin string
  (dev) and the localhost fallback (prod, intentionally noisy if the
  deploy env var slips).
  [Vite docs · env variables](https://vitejs.dev/guide/env-and-mode.html).
- **Path-relative URLs as the same-origin trick.** `openapi-fetch`'s
  `createClient({ baseUrl: '' })` produces request URLs like
  `/api/rooms`. The browser resolves the leading slash against the
  current page's origin (`http://localhost:5173`), not against any
  configured backend. The same applies to WebSocket: `new WebSocket('/ws')`
  resolves to `ws://localhost:5173/ws`. The proxy then makes the
  Vite origin look like the backend's. There is no JavaScript
  involved — it's all standard URL-resolution semantics specified by
  RFC 3986.
- **`vi.stubEnv` for boolean env keys.** Vitest's `stubEnv` is
  typed: most keys take `string | undefined`, but `DEV`, `PROD`, and
  `SSR` are special-cased to accept `boolean`. To test the dev /
  prod branch in `config.default.ts` we stub `DEV` (and `PROD` for
  symmetry), `vi.resetModules()`, then `await import('./config.default')`
  so the top-level constants re-evaluate. Without the reset, the
  module is cached and the stub has no effect on the already-resolved
  exports.
- **Module-evaluation-time constants vs lazy resolution.**
  `backendUrl` and `wsUrl` are evaluated once when the module first
  loads. That's fine in production (the env is set at build time and
  never changes), but tests need the import-reset trick above. The
  alternative — a function `getBackendUrl()` called per request —
  would be testable without `resetModules` but would shift every
  call site to remember the function form. We kept the constant
  shape because it's what every consumer already imports.

## Decisions taken

- **Decision:** `backendUrl = ''` in dev-unset is the lever, not
  `proxy: { '/api': ..., baseUrl: '/api' }` on the client.
  **Alternatives considered:** (a) hardcode the proxy paths on the
  client (`createClient({ baseUrl: '/api' })`) and skip the env-aware
  resolver; (b) leave `backendUrl` pointing at `http://localhost:8080`
  in dev and add a CORS allowlist on the backend instead.
  **Why this one:** option (a) would diverge dev from prod (production
  uses an absolute `baseUrl` from the env var), and the divergence
  would propagate into the STOMP URL derivation too. Option (b) is
  the real fix for production (and it is flagged as cross-repo work
  for the backend) but doesn't help in the dev workflow today.
  Empty-string-in-dev is the smallest possible change that delivers
  same-origin behavior without changing how the client is constructed.
- **Decision:** `changeOrigin: true` on both proxy entries.
  **Alternatives considered:** omit it (which preserves the
  `Host: localhost:5173` header on the proxied request).
  **Why this one:** Spring's `forward-headers-strategy` can be
  configured to honor `X-Forwarded-Host` (which the proxy also sets),
  but the cleanest contract is "the backend sees a request that
  looks like it came from `localhost:8080`". Defensive: even if the
  backend grows a host-name check later, the proxy keeps working
  without coordination.
- **Decision:** keep the `http://localhost:8080` fallback in
  production builds when `VITE_BACKEND_URL` is unset.
  **Alternatives considered:** make the fallback an empty string in
  prod too (same as dev), or throw at module load.
  **Why this one:** "noisy fallback" beats "silent fallback" and
  "crash at startup". The deploy workflow sets the env var; reaching
  this branch in production means a deploy regressed. A localhost
  URL is loud (every user's browser fails to reach localhost from
  their machine, errors surface in DevTools immediately) without
  making the bundle itself unbuildable.
- **Decision:** treat `VITE_BACKEND_URL === ''` (empty string) as
  "unset" and fall through to the dev default.
  **Alternatives considered:** honor it literally — empty string
  wins the explicit-override branch.
  **Why this one:** an empty-string env var almost always indicates
  a misconfigured CI step (`VITE_BACKEND_URL=` with no value).
  Treating it as unset matches the `typeof fromEnv === 'string' &&
fromEnv.length > 0` guard the original resolver already used. The
  test locks the behavior in.
- **Decision:** the test file uses `vi.resetModules()` +
  `await import(...)` per case instead of restructuring the resolver
  to take env as input.
  **Alternatives considered:** export a pure
  `resolveBackendUrl(env)` function and test that directly, leaving
  `backendUrl` as a thin wrapper.
  **Why this one:** the resolver is small (eight lines), and the
  module-eval-time constants are the surface every consumer
  imports. Extracting a testable function would create two ways to
  spell the same thing. The `resetModules` pattern is idiomatic
  vitest and the test file is the only place that needs it.

## How this compares to what I know

- **Same-origin via dev proxy vs sbt-revolver + http4s with a
  shared port.** A common Scala dev setup serves the SPA's static
  bundle from the same http4s server that hosts the API (one
  `Router`, two `HttpRoutes` mounted at `/` and `/api`). Same-origin
  by construction — there is no second port to proxy from. Vite's
  proxy is the JS-ecosystem equivalent for the case where the
  frontend dev server is a separate process (which it has to be in
  Vite-land to get HMR). The end-user behavior is identical: one
  origin to the browser, one CORS-free environment.
- **`changeOrigin` vs `Host` header rewriting in akka-http
  `ProxyForwarder`.** akka-http's reverse-proxy stub typically
  copies the inbound headers verbatim and lets the user opt in to
  rewriting `Host`. Vite's `http-proxy` is the reverse: the default
  forwards the original `Host` and you opt in to rewriting with
  `changeOrigin`. Same trade-off (which side knows the right host?),
  different default.
- **`import.meta.env.DEV` vs `sys.env` resolved at compile-time.**
  Vite inlines `DEV` and `VITE_*` at build time the same way `sbt`
  plugins like `sbt-buildinfo` inject `BuildInfo.scalaVersion` into
  a generated Scala object. Both are compile-time substitutions;
  both produce a constant in the binary; both eliminate the
  alternative branch via dead-code elimination (`tsc` + esbuild in
  Vite, the Scala compiler + Scala.js DCE on the Scala side). The
  conceptual model is identical.
- **WebSocket upgrade through a proxy vs http4s `WebSocketBuilder`
  behind Caddy.** Caddy in front of a Scala http4s server with a
  WebSocket endpoint requires the `reverse_proxy` directive to set
  `Upgrade websocket` — same intent as `ws: true` on Vite's proxy
  entry. Both are explicit opt-ins because the proxy's default
  behavior is HTTP-only.
- **Compile-time env vs runtime config in Cats Effect apps.** A
  typical Cats Effect / Ciris setup loads config at startup from
  env or file and produces a `Resource[IO, Config]` — runtime
  resolution with explicit failure on missing required keys. Vite's
  compile-time inlining is on the opposite end: there is no
  resolution step at runtime, the bundle ships with the resolved
  values baked in. The trade-off is "deploy a new bundle to change
  config" vs "edit a yaml and restart". For a static SPA that the
  user fetches from a CDN, the compile-time approach is the right
  default — there is no server-side process to consult a config
  file.

## Gotchas / things I learned the hard way

- **`vi.stubEnv` signatures need `DEV` as a boolean.** First draft
  called `vi.stubEnv('DEV', 'false')` (string), and TypeScript
  refused. Vitest's `stubEnv` overload narrows `DEV | PROD | SSR`
  to `boolean` and everything else to `string | undefined`. Once
  the types matched, the rest was straightforward.
- **`vi.resetModules()` is required for the import-reset trick.**
  Without it, `import('./config.default')` returns the same module
  reference the test file already pulled in at the top — the env
  stub does nothing because the constants have already evaluated.
  The reset clears the module registry so the second `import()`
  re-evaluates the top-level code. Subtle but essential.
- **Empty-string `VITE_BACKEND_URL` from CI.** Documented the
  fall-through-to-default behavior because real-world CI configs
  often write `VITE_BACKEND_URL=` (no value) when the build matrix
  forgets to set the env var, and the previous resolver already
  handled that case correctly (`fromEnv.length > 0` guard). The
  test now locks it in so a future refactor doesn't regress.
- **The `regex no-op makes wsUrl correct` chain isn't obvious on
  read.** `''.replace(/^http/, 'ws')` returns `''`. Appending
  `/ws` yields `/ws`, a path-relative URL the browser resolves
  against its current origin. The behavior is correct but it took
  a moment to confirm by hand; the test asserts it explicitly so
  the next reader doesn't have to redo the proof.
- **The test suite implicitly depended on the old `localhost:8080`
  default.** Flipping the dev default to `''` broke 10 unrelated
  tests on the first run — the MSW handlers register on absolute
  URLs against `TEST_API_BASE_URL` and the singleton `apiClient`'s
  `baseUrl` is captured at module eval, so the new empty default
  produced relative requests that never matched. Fixed by adding
  `.env.test` with `VITE_BACKEND_URL=http://localhost:8080`. Vite
  loads `.env.{mode}` files automatically; vitest sets `mode='test'`
  by default. The fix is invisible to runtime code (it only
  affects the test process) and `config.default.test.ts` still
  exercises the empty branch explicitly via `vi.stubEnv`.

## Round 2

The first review round closed with both reviewers approving. The user
then ran the docs/local-e2e.md procedure against the live backend and
hit two bugs the test suite (and the reviewers) did not catch. The
leader approved a single round-2 fix covering both.

### Bug 1 — `docs/local-e2e.md` misdescribed the docker-compose layout

The runbook said "step 1: `docker compose up -d` for Postgres +
Redis, step 2: `./mvnw spring-boot:run` for the Spring Boot app".
That was wrong: the backend repo's `docker-compose.yml` declares
**three** services — `postgres`, `redis`, AND `app` (which builds the
backend container and exposes port 8080). `docker compose up -d`
already brings up the full backend container. The maven step on top
caused a port-8080 collision between the host JVM and the running
container — the symptom the user hit.

**Fix:** rewrote the bring-up section to document the two
legitimate workflows explicitly:

- **Workflow A — Docker compose only.** Recommended for frontend
  smoke testing. `docker compose up -d` brings up everything; verify
  with `curl http://localhost:8080/api/health`; no maven needed.
- **Workflow B — Compose for deps + maven for the app.** For someone
  iterating on backend Java code (hot-reload, debugger attach, logs
  in-terminal). `docker compose up -d postgres redis` (explicitly
  excluding `app`), then `./mvnw spring-boot:run`. If switching from
  A to B, `docker compose stop app` first to free port 8080.

The troubleshooting block grew a dedicated "Port 8080 conflict
between the `app` container and `mvn spring-boot:run`" entry that
explains the cause (both bound to 8080) and the resolution (pick a
workflow and align with it). The "Backend not reachable on 8080"
entry now branches on which workflow the reader used.

### Bug 2 — `useRoomDiscovery` treated GET 404 as fatal

The user's two-browser smoke surfaced this sequence:

1. Player A creates room `CKYMV4` → `POST /api/rooms` returns
   `{ roomId: 'CKYMV4', gameId: null }` (correct: no game until B
   joins).
2. Player A navigates to `/play`. `useRoomDiscovery(CKYMV4, ...)`
   mounts.
3. `GET /api/rooms/CKYMV4` returns **404** (backend bug at
   `RoomService.findById` — flagged separately as cross-repo
   coordination; the room demonstrably exists, this is a
   server-side identity-resolution miss).
4. The hook's round-1 logic mapped 404 → `discoveryState = Error`
   and the `cancelled` flag in cleanup wasn't the trigger here —
   the hook just stopped progressing because the page treated
   `Error` as terminal. Backend logs confirmed **zero STOMP
   connections** from A.
5. Player B joins → `broadcastRoomJoinedEvent` fires to
   `/topic/rooms/CKYMV4` → nobody subscribed → event lost.
6. Player A stays in "Waiting for opponent" forever.

The treatment of GET 404 as fatal was wrong because **STOMP is the
canonical discovery path; GET is a companion for the late-subscriber
race**. A 404 on GET should not abort STOMP — STOMP may still
deliver the join event on a room the GET endpoint cannot find (as the
user's session showed).

**Fix in `src/hooks/useRoomDiscovery.ts`:**

- GET 404 (and any other GET failure) → `console.warn` with a
  diagnostic message including the roomId and the underlying cause.
  Do NOT touch `discoveryState`. The hook stays `Discovering`.
- GET success with `gameId !== null` → still completes immediately
  (unchanged from round 1).
- GET success with `gameId === null` → still no-op (unchanged).
- STOMP `RoomJoinedEvent` → still fires `onGameDiscovered` with
  race protection (unchanged).
- STOMP `onError` / connect rejection → state becomes `Error`. This
  is now the **only** path to `Error`. (Round 1 treated STOMP errors
  as soft and relied on the GET branch to be the fatal one; with GET
  failures softened, STOMP is the canonical signal.)

**Trade-off captured:** in the rare case where BOTH GET fails (404
or transient) AND STOMP fails to connect, the user sits in
`Discovering` indefinitely. That's acceptable — both paths failing
means the backend is unreachable, and a page refresh combined with
the Snackbar surface elsewhere (NetworkError mapping in
`src/api/errors.ts`) will inform the user. The alternative — a
custom timeout-then-Error inside the hook — adds non-trivial timing
machinery for an edge case the broader app already covers.

**Tests** in `src/hooks/useRoomDiscovery.test.tsx`:

- Renamed the "404 → Error" test to "stays in Discovering on 404;
  STOMP keeps listening" and asserted three things: the STOMP
  subscription registers, `console.warn` fires (spy), and
  `discoveryState` is `Discovering` (NOT `Error`). The warn-spy
  pattern (`vi.spyOn(console, 'warn').mockImplementation(...)`) is
  the standard vitest idiom for asserting on a console call without
  cluttering the test output.
- Added a new positive test that reproduces the user's exact
  scenario: GET 404, then STOMP delivers `RoomJoinedEvent`,
  `onGameDiscovered` fires with the event's `gameId`. This is the
  test that would have caught the bug pre-merge.
- All other existing tests pass unmodified — the GET-success path,
  the STOMP-only-completer path, the race-protection path, the
  unmount-cleanup path, and the null-precondition paths are
  orthogonal to the 404 handling.

### Concepts that appear in this round

- **"Canonical path + companion" pattern.** When you have two
  asynchronous discovery paths that converge on the same event, one
  is usually canonical (the source of truth) and the other is a
  companion that handles a narrow race. A failure on the canonical
  path is fatal; a failure on the companion is a soft warning. Round
  1 inverted these — the GET was treated as canonical-enough to
  abort the whole flow on 404. The correct framing: STOMP is the
  canonical source of room-state transitions; the GET only covers
  "we mounted after the second player already joined". With that
  framing, GET-404 is obviously soft.
- **`console.warn` as a diagnostic, not a state mutation.**
  `console.warn` is observable in DevTools, captured by error
  tracking (Sentry, etc.) if it's ever added later, and free to
  emit. State, on the other hand, drives UI: changing it should
  reflect an intent the user perceives. Logging the GET failure
  without flipping state is the cleanest way to leave a forensic
  trail without affecting the user's experience.
- **`vi.spyOn(console, 'warn').mockImplementation(() => undefined)`.**
  The `.mockImplementation(() => undefined)` suppresses the actual
  console output during the test run (otherwise the test would print
  the warning to stderr on every run). The spy's `.mock.calls` is
  the assertion surface. `mockRestore()` at the end of the test
  releases the spy so unrelated tests are unaffected — this matters
  more than it looks because vitest's module isolation does not
  reset console spies between tests.

### Decisions taken in round 2

- **Decision:** soft GET-failure handling collapses 404 into the
  same bucket as transient / 5xx / network errors.
  **Alternatives considered:** keep the 404 branch but treat it as
  "warning + retry-the-GET-once-after-2s" (give the server a chance
  to converge), or surface a separate `gone` discovery state that
  the page treats as "stay calm and wait for STOMP" rather than
  full `Discovering`.
  **Why this one:** the bug is "STOMP gets aborted by a GET 404
  that shouldn't matter to STOMP at all". Adding retry logic or a
  fourth discovery state is solving a different problem (we don't
  know GET will ever succeed — the backend's bug is unrelated to
  timing). The simplest fix that addresses the user's actual
  symptom is "make GET failures stop interfering with STOMP".
  Anything more elaborate carries a maintenance cost without a
  matching benefit.
- **Decision:** STOMP error path now promotes to `Error`.
  **Alternatives considered:** keep STOMP errors soft too (set
  message only, never `Error`), and rely entirely on a page-level
  timeout to surface "discovery is wedged".
  **Why this one:** with GET softened, leaving STOMP soft as well
  means there is NO path from the hook to `Error`. The page-level
  surface for that state is already wired up and useful; cutting
  the only feeder breaks symmetry. STOMP connection failure is
  also the clearest possible signal that the backend is
  unreachable — exactly the case where the user benefits from
  seeing the page-level error UI rather than an empty
  "Discovering" spinner.
- **Decision:** rewrite `docs/local-e2e.md` to document both
  bring-up workflows rather than just picking one.
  **Alternatives considered:** simplify to workflow A only and
  delete the maven path entirely.
  **Why this one:** the maven workflow is the right one for
  someone editing backend Java code (hot reload, debugger attach,
  log noise in-terminal rather than `docker logs`). Removing it
  would actively harm backend-iteration workflows. Documenting
  both with a clear "for what" header lets readers self-select.
