# Feature 22.5 — Clarify join UX now that a token is required

**Feature ID:** `room-join-ux` (from `feature_list.json`)

**Status:** in progress

---

## What we built

Live-testing feature 22 (`room-access-token`) exposed a UX gap: joining a
game to PLAY now requires the full invite link (the secret `joinToken`
rides in the URL fragment), so two leftover controls produced things that
no longer work — the manual "Room ID" text field (typing a bare code
always 403s `INVALID_JOIN_TOKEN`) and the "Copy room code" button (a bare
code can't invite anyone). This feature removes both. On the inviter side
(Play), the "Copy room code" button is gone and the "Copy invite link"
button hides once an opponent has joined (the room is full — no one left
to invite). On the joiner side (NewGame), the create-vs-join mode is now
**derived from the URL**, not a text input: a bare `/new` is create mode
(no Room ID surface at all), while arriving via an invite link
(`/new?roomId=XXXXXX#joinToken=…`) shows a read-only "Joining room: XXXXXX"
display and a "Join game" button.

## TS / React concepts that appear

- **Lazy `useState` initialiser as a one-shot capture** — both the captured
  roomId (`useState(() => normalizeRoomId(searchParams.get('roomId') ?? ''))`)
  and the join token (`useState(() => new URLSearchParams(window.location.hash…))`)
  use the function-form initialiser so the read happens exactly once on
  first mount, before the scrub effect runs. This is the React analogue of
  a Scala `lazy val`: the thunk is evaluated once and the result memoised
  for the component's lifetime. Reading `window.location.hash` directly
  (rather than the router's location) mirrors the OAuth-callback discipline
  — the fragment never reaches React Router because the browser strips it.

- **Derived state instead of stored state** — `joinMode` is no longer a
  boolean in `useState`; it is a pure expression
  (`capturedRoomId.length > 0 && isValidRoomIdFormat(capturedRoomId)`)
  recomputed each render from the single source of truth (the captured
  roomId). Removing the editable field removed an entire class of
  "two pieces of state drift apart" bugs — there is nothing to keep in sync.

- **Nullish gating in JSX with `==`** — the invite button is gated on
  `roomId !== undefined && opponentDisplayName == null`. `opponentDisplayName`
  is `string | undefined`; the loose `== null` matches both `null` and
  `undefined` in one check, which is the idiomatic React way to express
  "no opponent yet" without three-way branching. While waiting,
  `opponentDisplayName` is `undefined` (no game state yet); once the second
  player joins and the game state lands, it becomes their name and the
  button disappears.

- **`useEffect` for an address-bar side effect** — the fragment scrub
  (`history.replaceState(null, '', pathname + search)`) lives in an effect
  with an empty dep array so it runs once after the lazy capture. It
  preserves `window.location.search` (the `?roomId=` watch handle) and only
  strips the fragment — unlike the auth callback, which is pathname-only.

## Decisions taken

- **Decision:** A malformed `?roomId=` (e.g. `?roomId=IO00`) falls back to
  **create mode**, silently dropping the bad value.
  - **Alternatives considered:** (a) surface the existing 6-character format
    error inline, as the old editable field did; (b) attempt the join anyway
    and let the backend 404.
  - **Why this one:** the only way to get a malformed roomId now is manual
    URL tampering — the real invite link always carries a generator-valid
    code. There is no editable field for the user to correct, so an inline
    format error would be a dead end with no recovery action. Falling back
    to create mode is the simplest safe behaviour: the user lands on a
    usable form. The genuine error path that matters — a _valid_ roomId with
    a missing/stale token (`INVALID_JOIN_TOKEN`) — is untouched and still
    surfaces the friendly Snackbar.

- **Decision:** **Hide** the invite-link button once an opponent joins,
  rather than disable it.
  - **Alternatives considered:** disable (greyed-out, still visible) the
    button; leave it always visible.
  - **Why this one:** confirmed with the user. A full room has no open seat,
    so the control has no purpose — a disabled button invites the user to
    wonder why it's there. Hiding is cleaner. The signal was already on
    screen (`opponentDisplayName` flips from undefined to the opponent's
    name), so no new state was needed. Hiding the button does not strand
    keyboard focus: it is the last control in the row and nothing auto-focuses
    it.

- **Decision:** Remove the "Copy room code" control entirely (button +
  `handleCopyCode` callback + the now-unused `ContentCopyIcon` import).
  - **Alternatives considered:** reword its tooltip to "copy for spectating".
  - **Why this one:** spectator/watch is not built yet (out of scope per the
    plan), so a bare code has no user-facing purpose today. A control that
    produces an unusable string is worse than no control.

## How this compares to what I know

- **Derived `joinMode` ≈ a `def` over a `val`.** In Scala you'd model the
  mode as `def joinMode: Boolean = capturedRoomId.exists(isValid)` — a pure
  function of the captured field, never a separately-mutated `var`. Removing
  the editable `TextField` is exactly the refactor from "two `var`s that can
  disagree" to "one `val` plus a `def`". React's render model makes this
  natural: every render recomputes `joinMode`, so there is no stale-flag
  hazard.

- **Lazy `useState` initialiser ≈ `lazy val` / `Sync[F].delay` run once.**
  The fragment capture is a side-effecting read of `window.location` that
  must happen before the scrub mutates it. In Cats Effect you'd sequence
  `Sync[F].delay(readHash)` _before_ `Sync[F].delay(scrub)` inside the
  component's `Resource`/`IO`. React's lazy initialiser gives you the
  "evaluate once, in order, before the cleanup-adjacent effect" guarantee
  declaratively — the initialiser runs during the first render, the effect
  runs after commit.

- **`INVALID_JOIN_TOKEN` Snackbar ≈ a typed error channel surfaced to the
  edge.** The backend's error code arrives as an `ApiError` (a sealed-ish
  discriminated error), is mapped through `messageFor`, and rendered in the
  Snackbar — the same shape as folding an `E` error ADT from a tapir
  `Endpoint[I, E, O, R]` into a user-facing message at the HTTP boundary.

## Gotchas / things I learned the hard way

- The Play test fixtures bit me: `inRoomWhite` has a non-null `gameId`, so
  Play fetches the full game state (which includes `black: Bob`). With the
  new "hide once opponent present" rule, that fixture now hides the invite
  button — so the invite-link copy tests had to move to the _pre-game_
  fixture (`gameId: null`, room parked in `WAITING_FOR_PLAYER` via an MSW
  override) where `opponentDisplayName` stays undefined. I added a dedicated
  `stayWaiting()` helper and a separate test that asserts the button _is_
  hidden once Bob appears, so both halves of the gate are covered.
