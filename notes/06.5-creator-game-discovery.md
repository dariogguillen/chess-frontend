# Feature 06.5 — Creator game discovery

**Feature ID:** `creator-game-discovery`

**Status:** in progress (pending reviewer + user sign-off)

---

## What we built

When Player A creates a room, the server responds with a `roomId` and
`playerId` but no `gameId` — the chess game only exists once Player B
joins. Previously Player A's Play page rendered "Waiting for opponent"
forever; nothing told the page when the join happened. Backend commit
`c6de3d3` (`fix: room lifecycle`) shipped both a REST companion
(`GET /api/rooms/{id}`) and a STOMP topic (`/topic/rooms/{roomId}`
carrying a `RoomJoinedEvent`) for this purpose. This feature wires both
on the frontend: a new `useRoomDiscovery` hook runs GET + STOMP in
parallel while `room.gameId === null`, dispatches the first
non-null `gameId` to the existing `setGameId` operation on
`UserContext`, and unmounts itself once the gameId resolves. The
existing chain (`getGameState` + `useGameStomp`) then takes over
without a code change.

## TS / React concepts that appear

- **REST + STOMP companion pattern for fire-and-forget events.** STOMP
  topics in Spring's `SimpleBrokerMessageHandler` have no replay: a
  subscriber that connects after the broker has already broadcast the
  event sees nothing. The mitigation is universal — pair the topic
  with a REST endpoint that returns the current state, and let the
  client decide which one delivers first. `useRoomDiscovery` runs both
  in parallel and a single `discoveredRef` flag picks the winner.
  Compare to event-sourcing systems where the projection IS the
  catch-up mechanism; here the projection is the controller method
  reading from Redis.
- **Discriminated union via explicit `type` field.** The backend's
  `RoomEvent` is a sealed Java interface with a constant `type()`
  method per variant — `"ROOM_JOINED"` today, `"ROOM_CLOSED"` and
  `"PLAYER_LEFT"` are anticipated. The wire payload is self-describing
  ("`type": "ROOM_JOINED", ...`) rather than relying on Jackson's
  `@JsonTypeInfo`, which would bind the wire format to a specific
  library's annotation policy. On the TS side `RoomEvent` is a
  discriminated union with `event.type === RoomEventType.RoomJoined`
  narrowing the rest of the fields; the const-object value is tied to
  the literal type via `typeof RoomEventType.RoomJoined`, so the
  discriminator cannot drift.
- **Race-free first-write-wins guard.** Two async paths
  (`GET /api/rooms/{id}` and a STOMP subscribe handler) can each
  produce a `gameId`. The hook keeps a single closure-scoped
  `discovered` boolean; the first path to flip it wins, the second is
  ignored. `Promise.race` would not work: it rejects on the first
  rejection too, and one path failing is fine here as long as the
  other succeeds. We hand-roll the guard because the semantics
  ("first SUCCESS wins, failures are tolerated") are more specific
  than what the standard primitives offer.
- **Two short-lived STOMP clients vs one shared.** `useRoomDiscovery`
  and `useGameStomp` have disjoint lifetimes — the discovery hook
  lives only while `gameId === null`, the game hook only afterwards.
  Each owns its own STOMP client. Sharing one would require
  coordinating two hooks' connect / subscribe order; instead each
  hook calls `createStompClient` + `connect()` + subscribes +
  `disconnect()`s independently. STOMP connections over WebSocket are
  cheap (a single handshake, then multiplexed frames), and the
  simplicity of one-client-per-hook is the bigger win.
- **Const-object pattern continues to amortise.** This feature adds
  three more const-object discriminants in the same style as
  `GameStatus`, `Role`, `Side`, `ConnectionState`, `IdentityKind`,
  `RoomPhase`, and `ApiErrorCode`: `RoomStatus` (with a `satisfies`
  clause against the generated schema), `RoomEventType`, and
  `DiscoveryState`. Three values for `RoomStatus` is low risk for
  forgotten entries, so we skip the inverse exhaustiveness assertion
  (`Exclude<RawRoomStatus, RoomStatus> extends never`); the existing
  `narrowRoomStatus` switch catches an unexpected wire value at
  runtime via a thrown `ApiError`. For the other two const-objects
  there is no `satisfies` anchor — the value (a STOMP event
  discriminator, a UI state tag) doesn't appear in the OpenAPI
  surface — so they stand alone, same style.
- **Defensive `setGameId` on the context.** The discriminated `RoomState`
  union has `gameId` only on the `InRoom` arm. `setGameId` uses a
  functional setState that no-ops when `prev.phase !== InRoom`, so a
  call from a stale closure (after the user `leaveRoom`s, for
  example) cannot reintroduce a half-typed state. The branch is
  unreachable in normal use; the test covers it because the type
  system permits the call site to fire from any state.
- **`useRoomDiscovery` lifecycle and cleanup.** The effect builds a
  STOMP client, connects, subscribes, and registers a cleanup that
  drops the subscription + disconnects the client + sets a
  `cancelled` flag that blocks any further dispatch. On unmount and
  on precondition loss (a re-render where `roomId`/`playerId` becomes
  null), React invokes the cleanup before re-running the effect — the
  hook self-tears-down when `gameId` resolves and Play.tsx passes
  `null` on the next render.

## Decisions taken

- **Decision:** REST + STOMP companions in parallel, with a
  first-of-N completion guard.
  **Alternatives considered:** (a) STOMP only (no replay → late
  subscribers stuck forever); (b) polling the REST endpoint until
  gameId is non-null (works but wastes a request per second per
  waiting room); (c) a sequenced "STOMP first, then GET as fallback"
  (still loses if the SUBSCRIBE frame races the broker's broadcast).
  **Why this one:** parallel + first-wins handles every race
  configuration symmetrically. The cost is two requests per
  discovery instead of one, but the hook only runs for the brief
  window between create and join — a few seconds in practice.
- **Decision:** two STOMP clients, one per hook (`useRoomDiscovery`
  and `useGameStomp` do NOT share).
  **Alternatives considered:** one client per Play mount, reused
  across hooks via a Context or a shared ref. **Why this one:** the
  two hooks have disjoint lifetimes; sharing introduces a
  coordination problem (whose responsibility is `disconnect()`?
  what if the discovery hook unmounts before the game hook
  subscribes?) for no real saving. Stomp connections are cheap.
- **Decision:** STOMP subscribe to `/topic/rooms/{roomId}` carries no
  `playerId` header.
  **Alternatives considered:** mirror the `useGameStomp` pattern and
  send the header on every subscribe for consistency.
  **Why this one:** the backend's `ViewerCountTracker` only applies
  to the games topic (where players self-exclude from the spectator
  count). The rooms topic has no such dimension — the broker just
  broadcasts the join event once. Sending the header would be
  meaningless noise on the SUBSCRIBE frame.
- **Decision:** `RoomStatus` const-object skips the inverse
  exhaustiveness assertion that `GameStatus` and `ApiErrorCode` have.
  **Alternatives considered:** add the
  `Exclude<RawRoomStatus, RoomStatus> extends never` block for
  parity. **Why this one:** three values is low risk for a forgotten
  entry, and `narrowRoomStatus` already surfaces an unexpected wire
  value as a thrown `ApiError`. The assertion would be insurance for
  a future backend status addition; we accept the risk because the
  branch in `narrowRoomStatus` would catch any new value at runtime
  before it could silently flow through.
- **Decision:** `narrowRole` shim in `src/api/rooms.ts` stays for the
  POST endpoints. The new `PlayerInRoom.role` field (on the GET
  endpoint) has `@Schema(allowableValues = {"WHITE","BLACK"})`, so
  the generated type is already the `'WHITE' | 'BLACK'` literal
  union; no shim needed. **Why this asymmetry:** the create/join
  endpoints predate the `allowableValues` discipline; tightening
  them would require backend changes and a coordinated frontend
  cleanup that is not in scope for this feature. Documented as
  carry-over.
- **Decision:** the GET path treats a 404 (`ROOM_NOT_FOUND`) as
  fatal, but other GET failures as non-fatal soft errors.
  **Alternatives considered:** any GET failure → `Error`.
  **Why this one:** a 404 means the room doesn't exist — STOMP, even
  if reachable, will never broadcast for it. Other failures (network
  blip, 5xx) are transient; STOMP may still deliver the join event
  on the next reconnect. The hook stashes the soft-error message
  but stays in `Discovering`, so the user sees a spinner instead of
  a misleading error.

## How this compares to what I know

- **First-of-N completion vs Cats Effect `Race.race`.**
  `cats.effect.Race.race(fa, fb)` returns the first to complete
  (success OR failure), with the loser cancelled. Our hand-rolled
  guard handles a stricter shape: first SUCCESS wins; failures are
  tolerated until both paths give up. In Cats Effect we would
  compose `fa.attempt.race(fb.attempt)` and then handle the
  `Either[Throwable, A]` results; in TS we lean on the `discovered`
  flag inside two `async` functions because there is no
  `cancellation` primitive on a `Promise` and Promise.race has the
  wrong success-vs-failure semantics. Both ecosystems converge on
  "you write the race-resolution yourself; the primitive only
  guarantees one half of the contract".
- **Discriminated union vs sealed trait + Jackson polymorphism.**
  Scala sealed traits with circe / play-json `derived` codecs are
  the type-safe equivalent of TypeScript's discriminated unions on
  an explicit `type` field. The Spring/Jackson side here
  deliberately avoids `@JsonTypeInfo` (which would bind the JSON
  wire format to a Jackson-specific discriminator-resolution rule)
  by making `type` a plain string field on each record — the
  pattern other languages and platforms can match against without
  needing the Jackson library. circe's `Encoder.deriveEnumDecoder`
  or a tagged ADT encoder gives the same shape from the other side.
- **`useEffect` cleanup vs `Resource.make`.** The effect's cleanup
  closure drops the STOMP subscription, disconnects the client, and
  sets `cancelled` so any still-pending await is no-ops on resume.
  Same intent as `Resource.make(acquire)(release)` in Cats Effect —
  the component's mount/unmount IS the resource scope. The
  TypeScript version is dirtier (the `cancelled` flag is manual;
  Cats Effect's `Resource` integrates with the cancellation
  protocol) but the modelling intent is identical.
- **Refs vs `Deferred[F, A]`.** The `discoveredRef`/closure
  `discovered` flag and the `onGameDiscoveredRef` are React's way of
  saying "this cell lives outside React's reconciliation". In Cats
  Effect, the same idea is `Deferred[F, A]` (a one-shot signal) or
  `Ref[F, A]` for general mutable cells. The discipline is the same
  (avoid stale closures, give the async tasks a shared piece of
  state); the mechanics differ (React reconciliation vs Cats
  Effect's runtime).
- **The "GET + STOMP" pattern in fs2.** In an fs2 stream this would
  look like `Stream.eval(getRoomState(roomId)) ++
Stream.resource(subscribeToTopic(...))` merged with `merge`, then
  `evalMapAccumulate` over a `discovered: Boolean` to gate. The
  TypeScript hook does the same thing imperatively in two `async`
  functions because the React runtime is push-based (callbacks fire
  imperatively as events arrive), where fs2 is pull-based. Same
  semantic shape, different control flow.

## Gotchas / things I learned the hard way

- **The new endpoint forced an OpenAPI snapshot refresh.** Backend
  has the `GET /api/rooms/{id}` route with `RoomDetailsResponse` +
  `PlayerInRoom` shapes. The schema regeneration also picked up an
  unrelated `PlayerGameSummary` shape (the player-history endpoint
  added in the same backend commit), which lands as ambient codegen
  output even though we don't consume it yet. This is the
  snapshot-on-disk pattern working as designed — the contract
  exists in `schema.ts` whether or not we use it today.
- **`server.url` drift in the snapshot.** Springdoc emits the
  resolved server URL in `servers[0].url`. Booting the backend
  locally to fetch the spec writes `http://localhost:8080`; the
  previous snapshot was fetched against `https://chess-backend.duckdns.org`.
  The URL is metadata used only by Swagger UI / codegen tooling for
  default base URLs; `openapi-fetch` consumes it via our own
  `baseUrl` config. To keep the committed snapshot clean of
  developer-machine drift, I restored the duckdns URL after the
  fetch — a small `jq` patch that the leader could codify into the
  `openapi:fetch` script as a follow-up.
- **React 19's `set-state-in-effect` lint catches synchronous
  setState in the effect body.** The first draft of `useRoomDiscovery`
  called `setDiscoveryState(Discovering)` synchronously before
  kicking off the two `async` runners; the new lint flagged it as a
  cascading-render risk. Moved the call inside `runStomp()` (which
  lands in a microtask before any await), matching the same
  workaround `useGameStomp` already uses. Functionally equivalent;
  semantically the rule's intent is "external systems should drive
  setState, not the effect body itself".
- **The Play.tsx test mock now juggles two STOMP clients per
  mount.** The first `createStompClient` call (when the page mounts
  with `gameId === null`) is for discovery; the second (when
  `setGameId` flips the state) is for the game. The mock keeps a
  chronological array and routes per-test by the subscribed topic
  prefix (`/topic/rooms/` vs `/topic/games/`). Less elegant than a
  factory per hook, but the test layer benefits from "see the
  client by the topic it touched" semantics — no implicit ordering
  assumed.
- **No new dependencies.** Everything in this feature uses code
  already in the tree: `openapi-fetch`, `@stomp/stompjs` (via the
  `src/utils/ws` wrapper), `msw` for the REST mocks, `vitest` +
  `@testing-library/react` for the hook test. The `min-release-age=7`
  policy in `.npmrc` is irrelevant here.

## To dig deeper

  — what `convertAndSend("/topic/rooms/...", event)` does on the
  server side and why it is fire-and-forget without broker-managed
  replay. The backend's `RoomService.broadcastRoomJoinedEvent` is a
  textbook example.
- [React's `set-state-in-effect` lint rule](https://react.dev/learn/you-might-not-need-an-effect)
  — the canonical "you might not need an effect" page that motivates
  the rule. The microtask-boundary workaround we use isn't on that
  page but the philosophy is.
- [MDN: Promise.race semantics](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/race)
  — confirms the "first settle wins (resolution OR rejection)"
  semantics we deliberately avoid. The hand-rolled `discovered`
  flag is the substitute.
- The backend's `RoomService.java` (chess-backend-java repo, commit
  `c6de3d3`) — the join → game-creation → broadcast sequence is
  worth reading once to know what the frontend is waiting for.
