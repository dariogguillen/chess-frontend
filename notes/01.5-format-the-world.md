# Feature 01.5 — Format the world

**Feature ID:** `format-the-world` (from `feature_list.json`)

**Status:** in progress

---

## What we built

A repo-wide Prettier pass that normalized 21 drifted files (legacy
`src/*.tsx`, harness docs, workflow YAML, JSON configs) and a new
`format:check` step in `./init.sh` that gates every future change
against Prettier's idea of style. The `progress/` directory was
added to `.prettierignore` because those files are rotated by the
leader workflow, not the formatter, and a competing rewriter would
race them.

## TS / React concepts that appear

- **Formatters and linters as disjoint concerns.** ESLint owns the
  structural rules (unused vars, exhaustive deps, no class
  components). Prettier owns whitespace, quote style, line length,
  trailing commas. We make the two agree by appending
  `eslint-config-prettier` last in the ESLint chain — it disables
  the small set of ESLint stylistic rules that would otherwise fight
  Prettier. Concretely we saw this in `eslint.config.js`: it now ends
  with a semicolon (Prettier) and ESLint did not complain (because
  the `semi` rule is one of the ones `eslint-config-prettier` turns
  off). See <https://github.com/prettier/eslint-config-prettier>.
- **`.prettierignore` semantics.** It is parsed like `.gitignore`
  but consulted only by Prettier. We use it for two reasons here:
  (a) build outputs and generated files (`dist/`, `coverage/`,
  `package-lock.json`, `*.svg`) — the formatter has no business
  there; and (b) workflow-owned files (`progress/`) where the
  formatter would race the human/agent that owns them. Notably,
  Prettier _also_ skips files it has no parser for during a
  recursive walk (e.g. `init.sh`) — so `prettier --check .` did not
  fail on the bash script even without an ignore entry, but a direct
  `prettier --check init.sh` errors with "no parser inferred".
  Defensive entries for `.sh` are not needed today.
- **Gate on `--check`, never `--write`.** A verification gate
  observes; it does not mutate. Wiring `npm run format:check` into
  `./init.sh` means a non-formatted file fails the build with a list
  of offending paths and a hint (`Run Prettier with --write to
fix.`). Wiring `format --write` into the gate would silently
  modify files during verification, hiding drift and producing
  dirty working trees from CI. Same reasoning applies to `eslint
--fix` versus `eslint`, and `tsc --noEmit` versus `tsc -b`.

## Decisions taken

- **Decision:** Add `progress/` to `.prettierignore`.
  - **Alternatives considered:** (a) let Prettier reformat
    `progress/current.md` and `progress/history.md` along with
    everything else; (b) move progress files out of the Prettier
    discovery root entirely.
  - **Why this one:** the progress files have a workflow owner —
    the leader writes them via Edit/Write, often interleaved with
    `jq` rotations of `feature_list.json`. A formatter that
    rewrites them during a gate run would race those edits and
    introduce noise diffs in unrelated features. An ignore line is
    the smallest blast radius for that decoupling. We keep
    `notes/` formatted because notes are content, not workflow
    state.

- **Decision:** Position `format:check` between `lint` (step 6) and
  `typecheck` (step 7), labelled step 6.5.
  - **Alternatives considered:** (a) before `lint`; (b) after
    `test`; (c) inside `lint` via a Prettier ESLint plugin.
  - **Why this one:** both `lint` and `format:check` are static
    text checks with cheap failure modes (mechanical fix). Putting
    them adjacent makes the failure cluster visible. Running
    Prettier as an ESLint plugin
    (`eslint-plugin-prettier`) is the official anti-pattern
    nowadays — it slows ESLint down and conflates the two
    concerns. The 6.5 label keeps the existing 1..9 numbering
    stable so older references to "step 7 is typecheck" still
    line up.

- **Decision:** Do not add `init.sh` to `.prettierignore`.
  - **Alternatives considered:** add it defensively to make the
    intent explicit.
  - **Why this one:** Prettier without `prettier-plugin-sh`
    silently skips files it cannot parse during recursive walks.
    Verified empirically: `npm run format:check` does not include
    `init.sh` in its file list. Adding a defensive ignore would
    be noise. If we ever pull in the bash plugin, we revisit
    this.

## How this compares to what I know

- **In Scala this would be `scalafmt --check` + `scalafmtCheck` in
  CI.** Exact same shape: a formatter with a config file
  (`.scalafmt.conf` vs `.prettierrc.json`), an ignore mechanism
  (`project.excludeFilters` vs `.prettierignore`), and a check mode
  that exits non-zero on drift without writing. The disjoint
  concerns split also matches: `scalafix` owns structural rewrites,
  `scalafmt` owns whitespace, and they don't fight because they
  operate on different rules. `eslint-config-prettier` is the JS
  equivalent of being careful which `scalafix` rules you enable
  alongside `scalafmt`.
- **`Resource`-style scoping does not apply here.** Prettier is a
  one-shot transformation, not a lifecycle. The closest Cats Effect
  analogue is just a pure function over a string.
- **Compared to `sbt scalafmtOnCompile`:** we deliberately do NOT
  run `format --write` on every commit or every `init.sh`. That
  hook-on-write pattern is the JS equivalent of a Git pre-commit
  hook running `prettier --write`; it can hide drift from CI and
  produces "phantom edits" the author did not consent to. Our gate
  observes only.

## Gotchas / things I learned the hard way

- The original `package.json` and `vite.config.ts` had CRLF line
  endings. Prettier silently normalized to LF, which is correct,
  but produced a "whole file changed" diff that briefly looked
  alarming. The compiled bundle was byte-for-byte identical
  (`524173` bytes, same hashed filename `index-yv8l1I7D.js`),
  which is the test that mattered.
- The `.claude/settings.json` hook bash string is a single JSON
  string value, so Prettier's reflow stays outside the string.
  Confirmed by piping a synthetic `tool_input` payload through the
  command — still exits 2 with the BLOCKED message. The risk
  imagined in the plan (Prettier mangling the bash) did not
  materialize.
- The `.github/workflows/deploy-frontend.yml` got every double-quote
  flipped to single. YAML accepts both equivalently, and the
  workflow parses fine. Worth flagging that GitHub Actions
  examples in the wild are usually double-quoted, so any future
  copy-paste of an Actions snippet will look "wrong" until
  Prettier touches it.
