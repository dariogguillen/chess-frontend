# Feature 11.8 — Redirect /play to /new when there is no active room

**Feature ID:** `play-no-room-redirect` (from `feature_list.json`)

**Status:** in progress

---

## What we built

Opening `/play` directly in a fresh tab (no rehydrated session) used to
paint a dead-end "phantom board" — "Waiting for opponent", "Room ID: —",
a "Guest" label — with no `roomId` / `gameId` / `playerId`, so nobody
could ever join. The Play page now decides **at mount** whether it has a
usable room: on the `none` arm of the `RoomState` discriminated union it
short-circuits to `/new` with `replace`, so the phantom board never
paints and Back does not return to it. The same redirect now also covers
the URL-vs-stored reconciliation mismatch (previously a `leaveRoom()`
that left the dead-end board on screen). Cleanup: the stray, handler-less
`<Typography>Options</Typography>` header was removed; the spectator-count
`Chip` it used to head is preserved with its Tooltip and `aria-label`.

## TS / React concepts that appear

- **Render-time redirect via `<Navigate replace />`** — React Router's
  `<Navigate>` is a component that, when rendered, performs a navigation
  in its own effect. Returning it from a component is a _render-time_
  decision: the component returns `<Navigate to="/new" replace />`
  instead of the page tree, so the page's own DOM is never committed.
  `replace` swaps the current history entry rather than pushing, so the
  Back button does not land back on the dead-end. Docs:
  <https://reactrouter.com/en/main/components/navigate>.
- **Lazy `useState` initialiser as a mount-once capture** — `useState(()
=> room.phase === RoomPhase.None)` runs the initialiser exactly once
  per component mount and ignores the argument on every subsequent
  render. We use it to _freeze the mount-time phase_ into a boolean. Even
  if `room.phase` later flips to `none` (abandonment, rehydrate failure),
  the captured boolean does not change — the guard is immune to
  post-mount transitions. This is the same discipline the file already
  uses for the chess.js instance (`useState(() => new Chess())`) and the
  `reconciledRef` mount guard.
- **Discriminated-union narrowing on `RoomState`** — `RoomState` is
  `{ phase: 'none' } | { phase: 'in-room'; roomId; playerId; role; gameId }`
  (the const-object `RoomPhase` supplies the discriminant literals). The
  `none` arm has _no_ game identity by construction, which is exactly why
  it is unrenderable as a board and the right place to guard. TypeScript
  narrows `room` on `room.phase === RoomPhase.InRoom`, so `room.roomId`
  is only reachable on the in-room arm — the compiler enforces that the
  guard's premise ("no usable identity on `none`") holds.
- **StrictMode double-invoke + mount-once** — in development React 18/19
  StrictMode mounts, unmounts, and remounts a component, and invokes
  lazy initialisers / effect bodies twice to surface impure code. The
  lazy `useState` is naturally double-invoke-safe (pure read of
  `room.phase` / `roomIdFromUrl`); the reconciliation effect remains
  guarded by `reconciledRef` so its `leaveRoom()` side effect runs once.
- **No setState-in-effect** — the lint rule `react-hooks/set-state-in-
effect` forbids synchronously setting state inside an effect body
  (cascading renders). The first cut set a `redirectAfterReconcile` flag
  from inside the reconciliation effect and tripped the rule; the redirect
  decision is instead folded into the single mount-time lazy `useState`
  (`redirectToNewGame`), which detects both the empty-room case and the
  URL-vs-stored mismatch purely from the first render's inputs. The effect
  keeps only the `leaveRoom()` session-clear side effect.

## Decisions taken

- **Decision:** Guard with a lazy `useState` capturing the mount-time
  phase + a render-time `<Navigate replace />`, rather than a
  `useNavigate()` call inside a `useEffect`.
  - **Alternatives considered:** (a) `useEffect(() => { if (none)
navigate('/new', { replace: true }); }, [])` ref-guarded like
    `reconciledRef`; (b) a route `loader` guard in the data router.
  - **Why this one:** the effect approach runs _after_ the first paint,
    so the phantom board flashes for a frame before the redirect — the
    very dead-end we are removing. The render-time `<Navigate>` returns
    before any board markup is produced: no flash. A `loader` guard would
    be the cleanest architecturally, but the redirect premise
    (`room.phase`) lives in React Context, which a route loader cannot
    read without plumbing the session into the router — out of scope for
    a one-page fix. The lazy-`useState` capture is also what makes the
    guard immune to the **race** described below; a naive
    `useEffect(..., [room.phase])` reacting to every `none` transition
    would compete with the abandonment flow.
- **Decision (race avoidance):** the guard reacts to the mount value
  _only_, never to later transitions into `none`.
  - **Why:** two existing flows transition `room` to `none`
    _post-mount_ and already navigate themselves —
    `handleAbandonedHome` → `navigate('/home')` (Play.tsx), and
    `handleAbandonedNewGame` / the 404 / `GAME_ALREADY_ENDED` paths →
    `navigate('/new')`. If the guard fired on every `none` transition it
    would issue a competing `navigate('/new')` and could win the race
    against `handleAbandonedHome`'s `/home`, sending the user to the
    wrong place. Capturing the mount value sidesteps the coordination
    problem entirely: at the moment those flows run, the captured boolean
    is already `false` (we mounted in-room), so the guard stays silent.
    Test (c) is the explicit non-regression for this.
- **Decision (reconciliation behavior change):** the URL-vs-stored
  mismatch branch now redirects to `/new` (with `replace`) in addition
  to calling `leaveRoom()`.
  - **Alternatives considered:** keep `leaveRoom()`-only and let the
    fresh-entry path paint; auto-join the URL's `roomId`.
  - **Why this one:** under the minimal scope a fresh entry without a
    matching session is itself a dead-end (see the scope decision below),
    so leaving the phantom board on a mismatch is the same bug. Routing
    to `/new` is consistent with the entry guard. Auto-join was
    explicitly deferred.
- **Scope decision (deferred):** a `?roomId=XXX` in the URL **without** a
  valid in-room session does **not** auto-join or spectate — `phase ===
none` redirects to `/new` regardless of the query param. Deep-link join
  would need a join-vs-spectate decision and `POST /api/rooms/{id}/join`
  wiring (cross-repo), tracked as the separate `play-deeplink-join`
  feature. Test (a's sibling) pins this: `/play?roomId=abc-123` with no
  session still redirects.

## How this compares to what I know

- **Short-circuit before the handler (http4s / `OptionT` / `EitherT`).**
  The render-time `<Navigate>` is the React analogue of an http4s
  middleware that inspects the request and returns a `Response` (a 302)
  _before_ the route handler ever runs — `OptionT[F, Response]` /
  `Kleisli` short-circuit. The phantom-board-flash bug is what you get if
  you instead let the handler run and emit a redirect from _inside_ it
  (the effect-based approach): the body executes first. Deciding in
  `render` is deciding in the middleware layer; deciding in `useEffect`
  is deciding in the handler after side effects have already begun.
- **Lazy `useState` ≈ `lazy val`.** `useState(() => expr)` computes
  `expr` once on first access (mount) and memoises it for the scope's
  lifetime — exactly Scala's `lazy val` semantics. It is _not_ `def`
  (recomputed each call / render) and not an eager `val` (the argument
  form `useState(expr)` still evaluates `expr` every render, just
  discards it after mount).
- **Discriminated union ≈ sealed trait ADT + exhaustive match.**
  `RoomState`'s `phase` is the discriminator the same way a sealed
  trait's subtype is; `room.phase === RoomPhase.InRoom` narrows like a
  `case InRoom(roomId, …) =>` arm, and the `none` arm simply has no
  game-identity fields — modelling "no room" as a distinct case rather
  than a bag of nullable fields, which is the ADT habit.

## Gotchas / things I learned the hard way

- Several pre-existing tests asserted the **old** dead-end behavior
  (rendering the phantom board on the `none` arm). Those were updated to
  assert the redirect, not weakened — the behavior they described no
  longer exists by design. The "no STOMP connection on no room" test
  still holds verbatim (a redirect never builds a client).
- I first assumed the redirect would surface through the suite's
  `useNavigate` mock — i.e. assert `navigateMock('/new', { replace: true,
  … })`. It does **not**, and that wasted a debugging cycle: `<Navigate>`
  does call `useNavigate` internally, but it closes over **react-router's
  own binding** of the hook, captured inside the library module. The
  suite's mock only replaces the `useNavigate` reference that _our_ code
  imports and calls imperatively — it never reaches the copy `<Navigate>`
  uses. So the mock sees nothing on a render-time redirect. The fix was to
  assert the **outcome** instead of the call: render `<Play>` inside a real
  route tree (`MemoryRouter` + `<Routes>`) with a `/new` route sentinel
  (`renderWithRoutes` / `NewGameSentinel`), and assert the sentinel renders
  (`new-game-route` testid). The header comment in `Play.test.tsx:188-193`
  documents exactly this. Lesson: don't try to spy on a router component's
  navigation through a hook mock; let it actually navigate and assert where
  it lands.
