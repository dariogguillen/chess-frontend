# Feature 26.99 — Check indicator

**Feature ID:** `check-indicator` (from `feature_list.json`)

**Status:** in progress

---

## What we built

A play-testing tweak: an on-board signal when a king is in check. When the
backend reports `GameStatus.Check` or `Checkmate`, the king of the side to
move (`gameState.turn` — the side that must respond) is shaded red on the
board, and the `TurnIndicator` grows a small textual "Check" chip beside the
turn chip so the state is not conveyed by colour alone. Checkmate is terminal
and already pops the winner modal, but the red king still shows underneath so
the losing move is legible. Play-only; the spectator view inherits it for free
(same `gameState`).

## TS / React concepts that appear

- **Pure derivation memoized on a value, not a reference** — `checkSquareStyles`
  in `Play.tsx` is a `useMemo` keyed on `[fen, gameState?.status,
gameState?.turn]`. Unlike the 22.7 last-move highlight (which memoizes on the
  `moves` _array reference_ because Play never mutates it in place), the check
  square is derived from the rendered `fen` _string_ — a primitive, so value
  equality is reference equality and the memo recomputes exactly when the FEN,
  status, or side-to-move changes. The derivation deliberately reads `fen`
  (render state) and not the mutable chess.js instance, so it stays a pure
  function of props during render.
- **Object-spread layering with explicit precedence** — the board consumes a
  single `squareStyles` record built by `{ ...lastMoveStyles,
...checkSquareStyles, ...moveHints }`. Spread order is the precedence: amber
  last-move is the base, the red check king spreads next (more urgent — it must
  not be masked by an amber tint on the rare square that is both), and the
  active move-hints spread last so legal-destination dots still win while the
  user is mid-selection. This is last-writer-wins on object keys, the same
  semantics as merging `Map`s right-biased.
- **A pure parser extracted from the component** — `findKingSquare(fen, side)`
  walks only the FEN piece-placement field (rank 8 → 1, files a → h, digits are
  empty-square runs) and returns the king's algebraic square or `null`. It has
  no React surface and no shared state, so it is unit-tested in isolation
  (`kingSquare.test.ts`) — the same shape `docs/conventions.md` points at for
  "when a unit test earns its place": real branching (the digit runs, the
  malformed/absent fallbacks).
- **Conditional rendering of an additive cue** — the `TurnIndicator` computes
  `inCheck = gameState.status === GameStatus.Check` and renders `{inCheck &&
<Chip label="Check" .../>}` adjacent to the (refactored) turn chip inside the
  existing `role="status"` / `aria-live="polite"` live region, so the cue's
  appearance is announced to assistive tech.

## Decisions taken

- **Decision:** Parse the FEN by hand in a small pure helper rather than
  instantiate a `new Chess(fen)` and call `chess.board()` to locate the king.
  - **Alternatives considered:** (a) read the page's live `chess` instance
    during render; (b) build a fresh chess.js instance from the FEN inside the
    memo.
  - **Why this one:** (a) is a render-time read of mutable state and would
    couple the highlight to chess.js's internal position rather than the
    rendered `fen` — exactly the impurity the plan warned against. (b) is pure
    but heavier (constructs a full move generator just to read one square) for
    no benefit; the king's square is a trivial string walk. The handwritten
    parser is deterministic, ~20 lines, and returns `null` rather than throwing
    on a malformed placement so a contract drift can never crash the render.

- **Decision:** Highlight the king of `gameState.turn` (the side _to move_),
  for both `Check` and `Checkmate`.
  - **Alternatives considered:** highlight whichever king the FEN says is
    attacked (would need full attack detection); highlight only on `Check` and
    leave `Checkmate` to the modal.
  - **Why this one:** in chess the side to move is by definition the side whose
    king is in check (you cannot leave your own king in check), so `turn` is the
    authoritative, zero-computation answer — no attack scan needed. Including
    `Checkmate` was an explicit ask: the modal covers the _result_, but the red
    king on the board shows _where_ the mate landed.

- **Decision:** Red is a fixed translucent literal `rgba(220, 38, 38, 0.5)`,
  not a theme token.
  - **Alternatives considered:** `theme.palette.error.main` via `alpha()`;
    a board-theme-derived colour.
  - **Why this one:** identical reasoning to the 22.7 amber decision — the
    overlay must read on both light and dark board themes (which are opaque
    square fills, intentionally theme-independent), so it cannot key off a board
    theme, and the move-hint affordance already owns the MUI primary. A
    translucent red tints whatever themed square sits underneath without hiding
    the king glyph. The `TurnIndicator`'s "Check" chip _does_ use the MUI
    `error` palette token — it is a normal MUI component, not a board overlay, so
    the theme-token rule applies there and is honoured.

- **Decision:** Precedence — check king sits between last-move (below) and
  move-hints (above).
  - **Why this one:** the three layers almost never collide (a king square is
    rarely the from/to of the last move or a current legal destination), but
    when they do: the check cue should beat a stale amber last-move tint (more
    urgent), while a live move-hint should still beat the check tint (the user
    is actively choosing a square and needs the dots). Spread order encodes this
    with zero conditional logic.

## How this compares to what I know

- **In Cats/`Eq` terms** — the last-move memo (22.7) bets that an unchanged
  array _reference_ means an unchanged value, which only holds because the
  producer never mutates in place (the `case class` + `copy` discipline). The
  check memo doesn't need that bet: it keys on the FEN _string_, a primitive
  with structural equality baked in, so it's the easy case — `Eq[String]` is
  just `==`. Picking the dependency that is cheapest to compare correctly is the
  same instinct as choosing the right `Eq` instance for a `memoize`.
- **In a parser-combinator sense** — `findKingSquare` is a tiny hand-rolled
  parser over the placement grammar (`rank{/rank}×7`, where a rank is a run of
  pieces and digit-encoded gaps). In Scala you'd reach for `cats-parse` and get
  a typed `Parser[Board]`; here the grammar is small and fixed enough that a
  `for`-loop with an accumulator (`fileIndex`) is clearer than pulling in a
  combinator library — and it degrades to `null` instead of a `Left`, because a
  React render has no error channel to thread.
- **Layered `squareStyles` as a right-biased `Semigroup`** — `{ ...a, ...b,
...c }` is exactly `a |+| b |+| c` under a last-writer-wins `Monoid[Map[K,
V]]`. Scala's default `Map` `Semigroup` combines _values_; JS object spread
  always takes the rightmost, which is the right-biased monoid you'd build
  explicitly with `Semigroup.instance((x, y) => x ++ y)`.

## Gotchas / things I learned the hard way

- One pre-existing 22.7 test ("terminal-status transition clears squareStyles")
  dispatched a `CHECKMATE` event with `turn: White` over the starting FEN and
  asserted the merged styles were exactly `['e5', 'e7']`. That assertion is now
  legitimately stale: the white king on `e1` picks up the new check highlight,
  so the correct merged record is `['e1', 'e5', 'e7']`. The test's _intent_
  ("the move-hint layer cleared, last-move stays") is unchanged — I tightened
  the expected keys to include `e1` rather than weaken the assertion. This is
  the same flavour of merge-aware test update the 22.7 note flagged.
- The SAN/checkmate tests that fire `status: 'CHECKMATE'` assert on _text_, not
  `squareStyles`, so the new highlight on those FENs (black king on e8) is
  invisible to them — no churn there.
