# Feature 20.3 — Login & register pages + Header authed wiring + logout

**Feature ID:** `auth-ui` (from `feature_list.json`)

**Status:** done

---

## What we built

The email/password UI layer on top of the 20.2 auth plumbing. Two new
route-level pages — `/login` (email + password) and `/register` (email +
password + display name) — submit through the `login()` / `register()`
wrappers, lift the returned `AuthSession` into the authenticated identity
via `setAuthenticated`, and navigate to `/home`. A new self-gating
`AccountMenu` component lives in the `Header`: it renders nothing for a
guest and an account icon + menu (display name + Log out) for an
authenticated user, with a confirmation dialog guarding logout when a
game is in progress. The dead `authed` boolean prop that the app-shell
threaded into `Header` since the ui-refresh feature is gone — auth state
is now read where it is used. Anonymous play stays fully usable; no route
is gated.

## TS / React concepts that appear

- **Early `return <Navigate />` as a render-time redirect** — both auth
  pages do `if (identity.kind === IdentityKind.Authenticated) return
<Navigate to="/home" replace />;` before any other hook-free branch.
  In react-router's data-router, rendering a `<Navigate>` element queues
  an imperative navigation as a side effect of the render. The guard sits
  after the `useState` calls so the Rules of Hooks are not violated (all
  hooks run unconditionally; the conditional `return` is below them).
- **Controlled `<TextField>` with a `touched` flag** — validation
  (`looksLikeEmail`, `password.length >= 8`) computes on every render, but
  the error styling and helper text only switch once a field is `touched`
  (on blur, or on submit which marks all touched). This is the
  "don't shout on first paint" pattern; the derived booleans
  (`showEmailError`) are pure functions of state, not stored state.
- **`<Box component="form" onSubmit={...} noValidate>`** — wrapping the
  fields in a real `<form>` makes Enter submit for free (the browser's
  implicit submission), and `type="submit"` on the button participates.
  `noValidate` disables the browser's native bubble so our MUI helper
  text is the single error surface. `event.preventDefault()` stops the
  full-page navigation a form would otherwise do.
- **Self-gating context-reading child** (`AccountMenu`) — mirrors the
  `BoardThemeSelector` precedent. Instead of the parent (`Header`)
  computing `authed` and passing a prop, the child calls `useUserContext`
  and decides for itself, returning `null` for the guest case. The parent
  stays presentational and the auth decision lives in one place.
- **MUI `Menu` vs `Dialog` and the focus/inert interaction** — an open
  MUI overlay marks the rest of the app `aria-hidden`/`inert`, so during
  a Dialog's close transition the underlying account button is absent
  from the accessibility tree. The cancel test therefore asserts the
  dialog dismissed (`waitFor(() => queryByRole('dialog')).toBeNull()`)
  rather than re-querying the now-inert button — a behaviour-true
  assertion that also dodges a transition race.
- **Spread-with-conditional array construction** — the Drawer drops the
  "Log in" entry for an authenticated user via
  `...(isAuthenticated ? [] : [loginEntry])`. Cleaner than a mutable
  `push` and keeps the array literal declarative.

## Decisions taken

- **Decision:** two separate pages (`/login`, `/register`), not a single
  combined toggle.
  - **Alternatives considered:** one page with a "Log in / Sign up"
    tab toggle.
  - **Why this one:** deep-linkable URLs (an invite or a "create account"
    CTA can point at exactly one), it matches the existing `/login` route
    and Drawer link, and each form stays small and single-purpose. The
    20.4 Google button will live on the login page without crowding a
    shared form.

- **Decision:** the logout confirmation dialog lives in `AccountMenu`
  (the UI), not in the `logout()` primitive.
  - **Alternatives considered:** baking the "are you sure" into
    `UserContext.logout`.
  - **Why this one:** 20.2 deliberately shipped `logout()` as a pure
    primitive (clears token + identity + room). The warning is a
    UI concern keyed on `room.phase === RoomPhase.InRoom`, and it belongs
    where the button is. Context stays free of dialog state.

- **Decision:** client-side validation is a thin gate (email shape,
  password ≥ 8); the server stays the source of truth.
  - **Why this one:** the backend documents an 8–72 char password and
    owns "is this email registered / are these credentials correct". The
    client check only stops obviously malformed input from a pointless
    round-trip; everything real surfaces as an `ApiError` mapped through
    `messageFor` into the same Snackbar/Alert the rest of the app uses.

- **Decision:** delete the `authed` prop entirely rather than derive it
  in `App` and keep passing it.
  - **Why this one:** the prop existed only as a placeholder from the
    ui-refresh feature. With `AccountMenu` reading context directly, the
    prop has no consumer; keeping it would be dead plumbing inviting
    drift. `Header` is auth-agnostic again.

## How this compares to what I know

- **In http4s/tapir this would be...** the form-submit path is the client
  analogue of a `POST` endpoint returning either a success body
  (`AuthResponse`) or a typed error ADT (`ErrorResponse`). Where tapir
  narrows on the sealed error type, the page narrows on
  `cause instanceof ApiError` then on `cause.code` (a string-literal
  union) via the `errorMessages` lookup — the same "total mapping from
  error to message" you would write as a `match` over a sealed trait.
- **In Cats Effect this would be...** `handleSubmit` is an `IO` program:
  `setSubmitting(true)` is the acquire, the `try/finally` is
  `bracket`/`guarantee` (always release `submitting`), and the
  `catch (cause)` is `handleErrorWith`. The difference is that React's
  effect is fired imperatively by the event, not described and then run.
- **The `Navigate` guard vs a redirect middleware** — in http4s you would
  short-circuit in a `Kleisli`/auth middleware before the route runs.
  Here the redirect is expressed declaratively as a returned element and
  react-router performs it; there is no separate middleware layer because
  the route component _is_ the place the decision is made.

## Gotchas / things I learned the hard way

- A MUI `Dialog`/`Menu` open state makes the rest of the tree inert, so
  RTL queries for elements "behind" the overlay fail with
  "unable to find an accessible element" even though the node is in the
  DOM. Asserting on the overlay's own state (dialog present/absent) is
  both more correct and more stable than re-querying the obscured button.
- `getByLabelText(/log in/i)` would have collided on the Register page
  (the link text) had there also been a "Log in" button; scoping queries
  by role (`link` vs `button`) keeps them unambiguous. The page titles
  are queried by `level: 1` so the heading does not collide with the
  same-named submit button.
