# Feature 26.98 — Direct invitations (send)

**Feature ID:** `direct-invitations-send` (from `feature_list.json`)

**Status:** in progress

---

## What we built

The second (sender) half of direct game invitations. From the Play page, the
creator of a still-open FRIEND room can open a friend-picker dialog and invite
a specific friend straight into the room (the live-push counterpart to the
share link); the invited friend appears as a "pending" row with a Cancel
button. From the profile's Friends list, an "Invite to play" action creates a
FRIEND room, sends the invitation, and lands the inviter on `/play` in one
step. When an invitee rejects, the inviter sees a push toast ("Dave declined
your invitation.") and the pending row clears. There is no backend list-sent
endpoint, so the outgoing invitations are tracked locally in the app-level
provider (session-only).

## TS / React concepts that appear

- **Extending a context's value type with a `satisfies`-free union of
  capabilities.** `InvitationsContextValue` (in `InvitationsContext.tsx`) grew
  from three members (receive side) to nine (send side + a notice channel).
  Because it is a `Readonly<{…}>` object surfaced through `useMemo`, every
  consumer that destructures it (`useInvitations()`) gets compile-time
  knowledge of the new `invite` / `cancelOutgoing` / `outgoing` / `notice`
  members — and every hand-built test value (e.g. in `InvitationsMenu.test`,
  `FriendsSection.test`) had to be extended or it fails to typecheck. The
  compiler enforces that the mock and the real shape cannot drift.

- **A ref synced in an effect, not during render.** The STOMP handler lives
  inside the connect `useEffect` and must read the _current_ `outgoing` list
  to resolve an invitee's display name when an `INVITATION_DECLINED` push
  arrives — but it must not re-subscribe every time the list changes. The
  classic fix is a ref mirroring the state. ESLint 10's `react-hooks/refs`
  rule forbids writing `ref.current = value` during render, so the sync lives
  in its own `useEffect(() => { outgoingRef.current = outgoing }, [outgoing])`.
  The one-render lag is harmless: an outgoing row is always committed well
  before its matching declined push can arrive.

- **`set-state-in-effect` and the microtask hop.** `InviteFriendDialog`'s load
  effect must reset `loading`/`loadError` when the dialog opens, but ESLint's
  `react-hooks/set-state-in-effect` rule (cascading-render guard) forbids a
  _synchronous_ `setState` in an effect body. The same idiom `FriendsSection`
  and `Profile` use applies: `await Promise.resolve()` first, so every
  `setState` is provably deferred past the synchronous body.

- **A discriminated-union `switch` gaining a real arm.** The
  `INVITATION_DECLINED` event was parsed but ignored in 26.97. Filling in its
  `case` in the provider's `applyEvent` switch is a one-line change that the
  `never` exhaustiveness default already guaranteed was reachable — the
  union's compile-time completeness is what let 26.97 ship the type without
  the handler.

- **Lifting a Snackbar to the app root via a context channel.** Declines and
  background failures can fire while the user is anywhere, so the notice is a
  provider field (`notice` + `clearNotice`) read by a single
  `InvitationsNotice` component mounted once in `App`, rather than a Snackbar
  per page. MUI's `Alert` defaults to `role="alert"` (an assertive live
  region) so the message is announced.

## Decisions taken

- **Decision:** Track sent invitations locally in the provider (session-only).
  - **Alternatives considered:** add a backend `GET /api/me/invitations/sent`
    endpoint (cross-repo); persist to `sessionStorage`.
  - **Why this one:** the backend exposes no list-sent surface, and adding one
    is out of scope for a frontend feature. You invite while waiting in the
    room, so the window where the list matters is short; a refresh losing it
    is acceptable. The inviter still learns of an _accept_ through the normal
    `RoomJoinedEvent` in Play, and of a _decline_ through the push toast — so
    the only thing lost on refresh is the "pending + cancel" affordance, not
    any correctness.

- **Decision:** Identify the "waiting creator" by the presence of the secret
  `joinToken`.
  - **Alternatives considered:** track a `isCreator` boolean in the room state;
    compare `playerId` against the room's first player.
  - **Why this one:** only the creator's in-room arm carries the `joinToken`
    (a joiner and a spectator never do), so `joinToken !== null &&
opponentDisplayName == null && !isSpectator` is a precise, already-present
    signal. The `opponentDisplayName == null` clause also excludes a bot room
    (which fills the opponent slot immediately), so the invite control never
    shows where it would be meaningless.

- **Decision:** Bind `invite` to the room in Play and let the throw propagate
  out of the provider op.
  - **Alternatives considered:** swallow the error inside the provider and set
    a notice from there.
  - **Why this one:** the picker dialog needs to know whether the send
    succeeded (to close + show "sent") or failed (to keep open + show the
    error), so the op re-throws and the dialog routes the message to the
    caller's Snackbar with a `'success' | 'error'` severity. The `outgoing`
    list is only mutated on success — a `ROOM_FULL` adds nothing.

- **Decision:** Reuse the existing per-page Snackbars in Play for invite
  results, but add a _separate_ app-level Snackbar for declines.
  - **Why this one:** an invite result is tied to a user action _in Play_, so
    it belongs to Play's existing success/error Snackbars. A decline is a
    passive event that can arrive anywhere, so it rides the provider's notice
    channel and a root-level Snackbar — matching the inline-status-over-modals
    preference (a state the user did not directly cause → a push, not a modal).

- **Decision:** Fold in the 26.97 polish — accept/decline failures now set a
  notice instead of being swallowed — in the same provider ops.
  - **Why this one:** the notice channel created for declines is exactly the
    surface those swallowed failures needed; wiring them through it is a
    two-line change and resolves the deferred follow-up.

## How this compares to what I know

- **In Cats Effect this would be…** the `outgoingRef` synced-in-effect is a
  `Ref[F, List[Outgoing]]` that the STOMP consumer reads with `ref.get` inside
  its handler, while the UI updates it with `ref.set`. The difference is that
  React's ref is _not_ concurrency-safe — it relies on React's single-threaded
  render/commit model — whereas a `cats.effect.Ref` is atomic. The
  "sync-in-effect, not in render" rule is React's way of keeping the ref a
  commit-phase value, much like you'd only `ref.set` inside an `IO` action,
  never in a pure expression.

- **In http4s this would be…** `sendInvitation` / `cancelInvitation` are the
  same `Http4sClientDsl` `POST`/`DELETE` calls plus a circe-derived decoder —
  here the decoder is `openapi-fetch`'s generated body type plus the
  `mapError`/`ApiError` boundary that promotes the `{ error }` channel to a
  thrown error, the analogue of `client.expectOr(req)(onError)`.

- **In tapir this would be…** the nine-member `InvitationsContextValue` is like
  growing a service trait with more `Endpoint`-backed methods: every caller
  that pattern-matches on the trait must handle the new members, and the
  test doubles (the hand-built context values) are the in-memory
  interpreters that must implement the full trait or fail to compile.

- **Compared to `Resource`-scoped state**: the provider's `outgoing` and
  `notice` live for the whole authenticated session and are torn down (cleared)
  in the connect effect's cleanup when identity flips to guest — the same
  `Resource.make(acquire)(release)` lifetime the receive-side list already had,
  now carrying the send-side state too.

## Gotchas / things I learned the hard way

- ESLint 10 + `eslint-plugin-react-hooks` 7 flags `ref.current = x` _during
  render_ as an error (`react-hooks/refs`), not a warning — the first attempt
  (sync the ref inline) failed the lint gate and had to move into an effect.
- An open MUI `Dialog` marks the rest of the page `aria-hidden`, so a
  `getByRole('button', …)` for the page's Cancel button (behind the still-open
  picker) finds nothing even though `findByText` sees the hidden row. The Play
  cancel test had to wait for the dialog to leave the tree
  (`queryByRole('dialog')` gone) before querying the page button.
- Adding a `useInvitations()` call to Play meant _every_ test file that renders
  Play (or, transitively, `FriendsSection` via `Profile`) had to wrap in an
  `InvitationsProvider` — five test files, including the resync suite and the
  Profile suite. A guest identity means the provider never connects, so a mock
  factory + empty seed is enough.
