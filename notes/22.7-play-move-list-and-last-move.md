# Feature 22.7 — Move list (SAN) + last-move highlight on the board

**Feature ID:** `play-move-list-and-last-move` (from `feature_list.json`)

**Status:** in progress

---

## What we built

Two in-game readability improvements on the Play page. (1) The from/to
squares of the most recently played move are now shaded on the board at
all times — whoever moved — so on your turn you can see the opponent's
last move and after you move the highlight shifts to yours (standard
lichess/chess.com behaviour). (2) A move list renders the game's moves
in standard algebraic notation (SAN), numbered by full move
(`1. d4 d5  2. c4 …`), in a scrollable panel beside the board. No
backend change: both features are derived entirely from the
`gameState.moves` history the server already sends.

## TS / React concepts that appear

- **`useMemo` keyed on a reference, not a value** — both the last-move
  highlight (`lastMoveStyles` in `Play.tsx`) and the SAN derivation
  (`MoveList`) memoize on `gameState?.moves` / the `moves` prop. This
  works because Play _never mutates_ the moves array in place — every
  `MoveEvent` and ACK builds a fresh array via spread
  (`[...prev.moves, summary]`). So reference equality is a faithful
  "did a move land?" signal, and the expensive replay (a whole game
  through chess.js) only re-runs when one actually does. Contrast with
  `useMoveHints`, which can't memo on the chess.js _instance_ (mutable,
  stable identity) and instead fingerprints the position via the FEN
  string.
- **Object spread as layer composition** — the single `squareStyles`
  prop the board consumes is `{ ...lastMoveStyles, ...moveHints }`. The
  spread order encodes precedence: the highlight is the base layer, the
  active move-hints spread _second_ so a hint on a highlighted square
  wins (last-key-wins in an object literal). This is the same
  last-writer-wins semantics as merging two `Map`s.
- **Pure function extracted from a component** — `toSanList` is a pure
  `ReadonlyArray<MoveSummary> => string[]`. It constructs its own
  `new Chess()` locally, so it has no shared mutable state and is unit-
  testable in isolation (no render, no DOM). The convention note in
  `docs/conventions.md` ("when a unit test earns its place") points
  exactly at this shape: pure logic with real branching (the fallback).
- **`tsconfig` `lib` floor and `Array.prototype.at`** — the obvious way
  to read the last move is `moves.at(-1)`, but the app `tsconfig` targets
  ES2020 and `at` is an ES2022 lib method, so the typechecker rejects it.
  The fix is index access (`moves[moves.length - 1]`) rather than bumping
  the project-wide lib floor for one call — a reminder that the typed
  surface is the configured `lib`, not what the runtime actually
  supports. The empty array maps to `undefined`, which the highlight memo
  treats as "no move yet → empty record".
- **Semantic list markup over MUI** — the move list renders as
  `<Box component="ol">` / `<Box component="li">` so the structure (an
  ordered list) is conveyed to assistive tech, not just visually. Colour
  is not load-bearing: every ply is text.

## Decisions taken

- **Decision:** Derive SAN by replaying through a _fresh_ `new Chess()`
  from the start position, not the page's live `chess` instance.
  - **Alternatives considered:** (a) map each `MoveSummary` to SAN in
    isolation; (b) reuse the live `chess` instance.
  - **Why this one:** SAN is position-dependent — `g1f3` is `Nf3` from
    the start but `Ngf3` if a second knight also reaches f3, and a move
    can be a capture (`exd5`), a check (`+`), or mate (`#`) only relative
    to the board. So (a) is impossible without the running position. The
    live instance (b) is at the _current_ position; replaying from there
    would be nonsense. A fresh instance seeded at the standard start and
    fed the moves in order is the only correct source, and chess.js'
    `move(...).san` computes the disambiguation/check/mate suffixes for
    free.

- **Decision:** Defensive fallback to `from+to` coordinates on an
  unreplayable move, for that move and every move after it.
  - **Alternatives considered:** throw (crash the render); skip the bad
    move and continue; render `???`.
  - **Why this one:** the server validates every move before it lands in
    `gameState.moves`, so this branch should never fire — but a render
    must never crash on a contract drift or desync. Once the replayed
    position diverges from the server's, _no later move_ can be reliably
    notated (the chess.js board is now wrong), so the whole tail degrades
    to coordinates rather than emitting plausible-but-wrong SAN.

- **Decision:** Highlight colour is a fixed low-alpha amber
  (`rgba(255, 208, 0, 0.45)`), not a board-theme colour and not the MUI
  primary.
  - **Alternatives considered:** derive from the active board theme;
    derive from `theme.palette.primary` via `alpha()` (as the move-hints
    do).
  - **Why this one:** the highlight must read on _both_ light and dark
    board themes without coupling to any one of them. The board themes
    are opaque square fills (a "midnight" board is intentionally
    theme-independent — see `boardThemes.ts`), so keying off them would
    be a category error. The MUI primary is already the move-hint
    affordance; reusing it would blur the two signals. A translucent
    amber overlay tints whatever themed square sits underneath (the
    library renders `squareStyles` on a child layer over the base
    square) and stays distinct from the indigo hints.

- **Decision:** Highlight precedence — hints win over the highlight.
  - **Why this one:** when the user is mid-selection, the legal-
    destination dots and capture rings are the actionable signal and
    must not be masked by the amber tint. With no selection `moveHints`
    is `{}` so the highlight shows alone (the common case). Spreading
    hints second achieves this with zero conditional logic.

- **Decision:** Layout — board `Grid size={{ xs: 12, md: 8 }}`, move list
  `{{ xs: 12, md: 4 }}`, list capped at the board's `maxHeight` (600) and
  internally scrollable, stacking below the board on `xs`.
  - **Why this one:** it fills the empty right-side space in the user's
    screenshot on wide screens while staying usable on mobile, and the
    `overflowY: auto` cap keeps a long game from pushing the page height
    unbounded. Auto-scroll to the tail (a `useEffect` on the move count
    setting `scrollTop = scrollHeight`) keeps the latest move in view.

## How this compares to what I know

- **In Cats Effect / a fold this would be...** `toSanList` is a
  `foldLeft` over the move list threading a mutable `Chess` accumulator —
  except chess.js is imperative, so instead of `State[Chess, String]`
  we mutate a locally-scoped instance. The function stays _referentially
  transparent at its boundary_ (same input → same output, no shared
  state) even though its innards are effectful, the same way you'd wrap
  a mutable Java builder inside a pure method and never let the mutation
  escape. The fallback-tail is the `attempt`/`recover` arm: on the first
  `Left`, stop folding and emit the remaining inputs verbatim.

- **In circe this would be...** the `MoveSummary` → SAN step has no
  decoder analogue because SAN isn't _in_ the wire payload — it's
  _computed_ from the coordinate history. The closest parallel is a
  derived view: the server sends the normal form (coordinates), and the
  client reconstitutes a richer presentation (SAN) the way you might
  derive a display string from a case class rather than store it.

- **Memoization vs `Eq`** — `useMemo([moves])` is React's structural-
  sharing bet: it trusts that an unchanged _reference_ means unchanged
  _value_. That only holds because the producer never mutates in place —
  exactly the discipline `case class` + `copy` gives you for free in
  Scala. The `useMoveHints` FEN-fingerprint trick is the manual
  `Eq[Position]` you'd reach for when the value itself can't be compared
  by reference.

## Gotchas / things I learned the hard way

- Merging the highlight into the shared `squareStyles` prop meant three
  pre-existing tests that asserted `squareStyles === {}` after a move now
  legitimately carry the last-move highlight. Their _intent_ was "the
  move-hint overlay cleared", so I tightened them to assert the exact
  remaining keys (the highlighted from/to) rather than emptiness — the
  empty-record assertion was conflating two distinct layers. One of the
  three was also quietly racy (it happened to catch the post-drop /
  pre-ACK window); the tighter assertion removes the flake.
- The default `sampleGameState()` test fixture has `moves: []`, which is
  why the bulk of the existing hint tests stayed green untouched — no
  moves means no highlight, so an empty `squareStyles` is still correct
  for those.
