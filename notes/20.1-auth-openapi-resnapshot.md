# Feature 20.1 — Auth OpenAPI re-snapshot

**Feature ID:** `auth-openapi-resnapshot` (from `feature_list.json`)

**Status:** done

---

## What we built

A pure-codegen enabler. The deployed backend grew an auth bundle
(register / login / `/api/me` / `/api/me/games`) but the committed
OpenAPI snapshot predated it, so none of the auth endpoints or schemas
existed in the generated TypeScript. We re-snapshotted `openapi.json`
from the live prod backend, regenerated `src/api/generated/schema.ts`,
and absorbed the two contract changes that ripple into our hand-written
code: the `Player` → `PlayerView` schema rename, and three new
server-side error codes. No auth runtime code ships in this sub-feature
— it only makes the auth surface type-available for 20.2–20.4.

## TS / React concepts that appear

- **OpenAPI → TypeScript codegen (`openapi-typescript`)** — the
  `openapi:generate` npm script feeds `openapi.json` into
  `openapi-typescript`, which emits a single `schema.ts` exporting a
  `components['schemas'][...]` namespace and a `paths` map. Our
  hand-written wrappers (`games.ts`, `wsEvents.ts`, `errors.ts`) alias
  into that namespace, so a contract change surfaces as a _compile_
  error rather than a runtime surprise. The generation is
  deterministic: re-running it on an unchanged spec yields a
  byte-identical file (verified here).

- **Indexed access types + `NonNullable`** — `errors.ts` derives its
  server error union with
  `NonNullable<components['schemas']['ErrorResponse']['error']>`. The
  generated `error` field is optional (`?`), so the indexed access is
  `string-enum | undefined`; `NonNullable` strips the `undefined`. When
  the backend adds an enum value to the `@Schema(allowableValues=...)`,
  it flows straight into this union on the next generate — no manual
  edit to the type.

- **Compile-time exhaustiveness via `Exclude<A, B> extends never`** —
  `errors.ts` has a type-level assertion
  (`_ApiErrorCodeExhaustiveCheck`) that fails to compile if the
  `ApiErrorCode` _type_ gains a member the runtime const object does
  not enumerate. This is the mechanism that caught the three new auth
  codes: the type side picked them up automatically from the
  regenerated schema, and `tsc` then refused to build until the const
  object and the `errorMessages` `Record<ApiErrorCode, string>` were
  brought back in sync. The error message is literally encoded in the
  failing conditional's "false" branch.

## Decisions taken

- **Decision:** Fetch the snapshot from the _prod_ backend, not the
  `localhost:8080` the `openapi:fetch` script targets.
  - **Alternatives considered:** spin up the backend locally; permanently
    rewrite the script's URL.
  - **Why this one:** the validated auth bundle is deployed to prod and
    `localhost:8080` is not running. A one-off
    `curl -fsSL https://chess-backend.duckdns.org/v3/api-docs | jq . > openapi.json`
    is the minimal path. Making the script's URL configurable is a
    separate polish item, deliberately out of scope here so this
    sub-feature stays pure codegen + mechanical renames.

- **Decision:** Treat the three new error codes
  (`AUTHENTICATION_REQUIRED`, `EMAIL_ALREADY_TAKEN`,
  `INVALID_CREDENTIALS`) as in-scope mechanical mirroring, not a
  scope expansion to report-and-stop.
  - **Alternatives considered:** stop and ask the leader, since the
    plan only enumerated the `Player` → `PlayerView` alias retarget in
    `games.ts` / `wsEvents.ts` and did not mention `errors.ts`.
  - **Why this one:** the plan's gate is "init.sh green end-to-end —
    typecheck must compile against the regenerated schema." The three
    codes are a _direct, unavoidable_ consequence of the re-snapshot
    (they live in `ErrorResponse.error`'s `allowableValues`), and the
    `errors.ts` exhaustiveness check is explicitly _designed_ to force
    this mirror — its own doc comment describes "a new code lands on the
    type side ... but nobody mirrors it into this runtime object" as the
    exact case it guards. Adding three const entries, three known-codes
    set members, and three user-facing message strings is the same
    class of mechanical mirror as the `PlayerView` rename, not auth
    runtime logic. No login/register flow, token storage, or middleware
    ships here.

- **Decision:** Add `errors.test.ts` covering the new codes through
  `mapError` and `messageFor`.
  - **Why this one:** `errors.ts` had no co-located test. The
    compile-time `Exclude` check guards the _type_ side, but the
    runtime `KNOWN_CODES` set (which gates whether `mapError` promotes a
    body to a typed `ApiError`) is not covered by that check — a code
    could be in the const object and the messages map yet missing from
    the set, and still compile. The behavioral test closes that gap.

## How this compares to what I know

- **In tapir / circe this would be...** regenerating your client stubs
  from the server's `Endpoint` definitions. `openapi-typescript` is the
  client-side equivalent of deriving a typed client from an OpenAPI
  document — except the "codec" is structural typing plus `JSON.parse`,
  not a derived `Decoder[A]`. There is no runtime validation: the
  generated types are erased at compile time, so a wire payload that
  lies about its shape will type-check against `schema.ts` and only blow
  up where you actually touch a missing field. That is why `errors.ts`
  keeps a runtime `isServerErrorBody` guard in addition to the types.

- **In a Scala sealed trait this would be...** the `Exclude<A, B>
extends never` assertion is the TypeScript hand-rolled version of
  what `sealed trait` + exhaustive pattern match gives you for free. In
  Scala, adding a case to a sealed ADT makes every non-exhaustive
  `match` a compiler warning/error automatically. TypeScript has no
  closed-union exhaustiveness for a _runtime value_, so we synthesise it
  with a conditional type whose false branch is a descriptive error
  object — the build fails at the declaration site that fell behind.

- **Codegen idempotency** is the property you rely on from
  `sbt`/`scalapb` or guardrail: running the generator twice on the same
  input is a no-op. We verify it explicitly here (regenerate, `diff`,
  expect empty) because a non-idempotent generator would mean the
  committed `schema.ts` is not reproducible from the committed
  `openapi.json`.

## Gotchas / things I learned the hard way

- The working tree already had `openapi.json`, `schema.ts`, and the two
  aliases mutated when I picked up the session — but `errors.ts` had not
  been touched, so the first `./init.sh` failed _only_ at typecheck.
  The lesson: the plan enumerated the _obvious_ two alias sites
  (`Player` → `PlayerView`) but missed the _transitive_ fallout of the
  re-snapshot through the auto-derived `ServerErrorCode` union. Always
  let `tsc` enumerate the full blast radius of a codegen change rather
  than trusting the plan's hand-listed call sites.

- The local `openapi.json` matched prod byte-for-byte only after
  normalising both through `jq -S` (sorted keys). Spring/`springdoc`
  does not guarantee stable key ordering across requests, so a raw
  `diff` of the curl output against the committed file can show spurious
  changes; sort before comparing.
