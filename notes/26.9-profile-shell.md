# Feature 26.9 — Profile shell

**Feature ID:** `profile-shell` (from `feature_list.json`)

**Status:** done

---

## What we built

A minimal `/profile` page: the authenticated user's account home and the
stable anchor for the social epic (friends, my games, stats land here as
their own features later). It shows the display name + email (fetched via
`me()` on mount) and three placeholder "coming soon" sections. A new
**Profile** item in the account menu navigates to it. The route is guarded:
a guest is redirected to `/home`.

## TS / React concepts that appear

- **Inverse auth guard** — `Login` redirects an already-authenticated user
  away (`identity.kind === IdentityKind.Authenticated → <Navigate>`).
  `Profile` is the mirror: it redirects a _guest_ away
  (`identity.kind !== IdentityKind.Authenticated → <Navigate to="/home" replace />`).
  The `replace` keeps the guarded URL out of the history stack so Back
  doesn't bounce the user back into the guard.

- **`useEffect` with a `cancelled` flag** — the `me()` fetch is an async
  effect; the cleanup sets `cancelled = true` so a state update from a
  resolved/rejected promise after unmount (or after `identity` changes) is
  dropped. This is the React idiom for "ignore a stale in-flight result"
  when you don't have an `AbortController` on the call (the `me()` wrapper
  takes no signal). Cleanup is mandatory here per `docs/conventions.md`.

- **Discriminated-union narrowing for state seeding** — `displayName` state
  is seeded from `identity` only on the `Authenticated` arm; the `kind`
  discriminant gates access to `identity.displayName`. The same narrow
  guards the effect body and the early `Navigate`.

- **Graceful degradation over crash** — `me()` rejecting (stale token,
  transport blip) is caught; the page keeps the identity's `displayName`
  and omits the email rather than throwing. The user is still logged in as
  far as the client knows, so the page stays usable.

- **`role="status"` + `aria-live="polite"`** — the loading state announces
  itself to assistive tech; the spinner itself is `aria-hidden` (the
  "Loading your profile…" text carries the meaning, not colour or motion).

## Decisions taken

- **Decision:** fetch the email via `me()` on mount rather than widening
  `AuthenticatedIdentity` to carry it.
  - **Alternatives considered:** add `email` to `AuthenticatedIdentity` and
    populate it from the login/register/OAuth flows.
  - **Why this one:** the identity ADT is deliberately minimal
    (`userId` + `displayName`); email is profile data, not identity. The
    OAuth-callback path already does a `me()` round-trip, but it discards
    the email into the identity shape. Keeping the fetch local to the page
    avoids touching the context contract and the three auth entry points
    for a single field this one page needs. The fetch is cheap and the page
    is account-only.

- **Decision:** v1 is shell only — placeholder sections, no friends CRUD.
  - **Alternatives considered:** build friends list/requests now.
  - **Why this one:** the user explicitly scoped v1 to "info + navigation".
    The placeholder sections are real, accessible headings so the later
    features (friends, my games, stats) slot into a stable home without a
    re-layout.

- **Decision:** lazy-load the route (`React.lazy`), matching NewGame/Play.
  - **Why this one:** Profile is account-only and not on the default path,
    so it should not weigh on the initial bundle. It also makes an API call,
    putting it in the "heavy enough to split" bucket alongside Play.

- **Decision:** `PersonIcon` for the menu item, not the `AccountCircleIcon`
  already used by the menu's trigger button.
  - **Why this one:** reusing the trigger's icon for an item inside the same
    menu reads as a duplicate. `PersonIcon` is per-path imported
    (`@mui/icons-material/Person`), never the barrel, per the tree-shaking
    rule.

## How this compares to what I know

- **The inverse guard as a refined type** — in Scala you'd model the route
  handler as taking an `AuthenticatedUser` and let the type system make the
  guest case unrepresentable at the boundary (a `RequestContext[User]` you
  can only obtain after auth). React has no such boundary on a route
  component, so the guard is a runtime early-return that the discriminant
  narrows _after_ — `if (identity.kind !== Authenticated) return <Navigate>`
  is the value-level stand-in for the type that would have excluded the
  guest case upstream.

- **`useEffect` cleanup ≈ `Resource` release** — the `cancelled` flag is a
  hand-rolled version of what `Resource.make(acquire)(release)` gives you in
  Cats Effect: the effect's scope is the mount-to-unmount window, and the
  cleanup runs on scope exit. Here "release" is just "don't write state from
  a now-stale promise" rather than freeing a real resource.

- **Catch-and-degrade vs `MonadError`** — `me().catch(() => setEmail(null))`
  is the imperative shape of `meIO.handleError(_ => none)` — recover into a
  benign value instead of propagating. The page renders the recovered state.

## Gotchas / things I learned the hard way

- The effect runs before the early `Navigate` guard is _evaluated on the
  same render_ (hooks must be unconditional and run top-to-bottom before any
  return), so the effect body needs its own `identity.kind` guard even
  though a guest is redirected — otherwise a guest mount would fire a
  pointless `me()`. Belt-and-suspenders, but correct.
