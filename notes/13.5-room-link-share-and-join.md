# Feature 13.5 — Room link share and join

**Feature ID:** `room-link-share-and-join` (from `feature_list.json`)

**Status:** in progress

---

## What we built

On the `/play` page, when a room is active we show two copy controls
next to "Room ID: XXXXXX": one copies the 6-char room code, the other
copies a full invite link to `/new?roomId=XXXXXX`; both confirm with a
Snackbar. The New Game form lost its "Join an existing game" checkbox —
the optional Room ID input now _is_ the mode (empty creates, filled
joins), with client-side format validation and a deep-link pre-fill so
a friend who opens the invite link only has to type a nickname.

## TS / React concepts that appear

- **Deriving state instead of storing it.** The old form held a
  `const [join, setJoin] = useState(false)` boolean _next to_ the
  `roomIdInput` string. Two cells, one truth, free to drift (e.g. join
  ticked but the field empty). The new form keeps only the string and
  derives `const joinMode = roomIdInput.trim().length > 0`. `joinMode`
  is a plain `const` recomputed each render — no setter, no effect, no
  way to desync. See `src/pages/NewGame/NewGame.tsx`.
- **`useState` lazy initialiser for one-shot seeding.** The `?roomId`
  pre-fill uses `useState(() => normalizeRoomId(searchParams.get('roomId') ?? ''))`.
  The function form runs exactly once on first mount (React ignores it on
  re-renders), so a later edit to the field is never clobbered by the
  query param. Same pattern the Play page already uses for its
  mount-time entry guard.
- **`navigator.clipboard.writeText` — an async, gated, secure-context
  API.** It returns a `Promise`, requires a secure context
  (HTTPS / `localhost`), and can reject if permission is denied. We wrap
  it in `copyToClipboard` (`src/pages/Play/Play.tsx`): guard for the API
  being absent (`navigator.clipboard === undefined`), `try`/`catch` the
  write, and route both the success and the two failure modes into a
  single `copyMessage` state cell that drives one Snackbar. A copy
  attempt can never throw into render.
- **`useSearchParams` for read-only query access.** React Router's
  `useSearchParams()` returns a `URLSearchParams`; `.get('roomId')`
  yields `string | null`. We only read it (the tuple's setter is
  unused), feeding the value through `normalizeRoomId`.
- **Building URLs that respect the router basename.** The invite link is
  `window.location.origin + import.meta.env.BASE_URL(stripped) + '/new?roomId=…'`,
  not a bare `/new?roomId=`. `BASE_URL` is Vite's build-time base path
  (always trailing-slashed). On Cloudflare Pages it is `/` (the strip is
  a no-op), but a future sub-path deploy would otherwise emit a link that
  404s. This mirrors the existing basename handling in
  `src/routes/Public.tsx`.
- **`Readonly`/immutability discipline** is unchanged here — no new DTOs;
  the helper exports plain `const` primitives.

## Decisions taken

- **Decision:** put the room-id format helper in a new
  `src/utils/roomId.ts` rather than next to `Role`/`RoomStatus` in
  `src/api/rooms.ts`.
  - **Alternatives considered:** co-locating it in `rooms.ts` beside the
    other room types.
  - **Why this one:** the format is _not_ a wire contract — there is no
    OpenAPI DTO for a room code (it is a generated string / path param),
    so it does not belong with the narrowing/codec layer. It is a pure,
    framework-free predicate reused by NewGame and tests; `src/utils/` is
    where pure helpers live per `docs/conventions.md`. Keeping it out of
    `rooms.ts` also keeps that file focused on the typed client.

- **Decision:** validate the room-id _format_ on the client but let the
  server own _existence_.
  - **Alternatives considered:** (a) no client validation, let every code
    round-trip and rely on `404 ROOM_NOT_FOUND`; (b) try to verify
    existence client-side with a probe GET before enabling submit.
  - **Why this one:** format is a cheap, total, offline check — gating it
    client-side avoids a guaranteed-to-fail network call for obvious
    typos and gives instant feedback (TextField `error` + helperText,
    submit disabled). Existence is inherently a server question
    (rooms come and go), so a well-formed-but-unknown code still goes to
    the server and surfaces `404 ROOM_NOT_FOUND` through the existing
    error Snackbar. This is the boundary-validation vs domain-validation
    split: shape locally, identity remotely.

- **Decision:** IconButtons with `aria-label` + Tooltip for the copy
  controls, shown only when `roomId !== undefined`.
  - **Alternatives considered:** always-visible text buttons; rendering
    them disabled in the `—` empty state.
  - **Why this one:** in the empty state there is nothing to copy, so the
    controls would be dead UI; conditional render is cleaner than a
    disabled affordance. Icons keep the room-id row compact; the
    `aria-label`s ("Copy room code" / "Copy invite link") give them
    accessible names (CHECKPOINTS a11y + ui-reviewer recipe 5), and the
    success/failure Snackbar conveys state by text, not colour alone.

## How this compares to what I know

- **Deriving `joinMode` vs a stored flag** is the same instinct as
  modelling with the data you already have rather than a parallel
  `Boolean` that can contradict it. In Scala you would not keep
  `roomId: Option[String]` _and_ `isJoining: Boolean` in the same case
  class when `roomId.exists(_.trim.nonEmpty)` already answers the
  question — the redundant field is an illegal-state generator. React's
  pull toward "store everything in `useState`" makes this drift easier to
  introduce, so the discipline matters more here.
- **`copyToClipboard`'s guard + try/catch** is a hand-rolled version of
  what `IO`/`Resource` gives you for free. In Cats Effect you would model
  the clipboard write as an `IO[Unit]` and `.attempt` it into an
  `Either[Throwable, Unit]`, then fold both arms into the UI state. Here
  the `Promise` is the effect, `await` inside `try/catch` is the
  `.attempt`, and `setCopyMessage` on each arm is the fold. The
  availability guard is the equivalent of checking a capability before
  acquiring it.
- **Client format check + server existence check** maps to tapir/http4s
  input validation vs business validation: a `Validated` /
  `EndpointInput` refinement rejects a malformed code before it reaches
  the handler (our `isValidRoomIdFormat`), while "does this room exist?"
  is a `F[Either[NotFound, Room]]` in the service layer (the backend's
  `404 ROOM_NOT_FOUND`). Two layers, two responsibilities.

## Soft coupling to the backend

`src/utils/roomId.ts` mirrors the backend's `RoomCodeGenerator`:
alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no I/L/O/0/1, to avoid visual
ambiguity), length 6, case-insensitive lookup (the server upper-cases
the path id). There is **no shared schema** for room codes — they are
generated strings and path params, not OpenAPI DTOs — so this constant is
a deliberate, documented duplication. If the backend ever changes the
alphabet or length, `ROOM_ID_ALPHABET` / `ROOM_ID_LENGTH` are the single
place the frontend must follow. The format check is intentionally lenient
about _existence_: a code that passes the shape check but no longer maps
to a room is the server's call (`404 ROOM_NOT_FOUND`).

## Gotchas / things I learned the hard way

- The MUI `slotProps.htmlInput` `maxLength: 6` already clamps typing, but
  `normalizeRoomId` still clamps defensively for the `?roomId` pre-fill
  path, which bypasses the input's `maxLength` entirely (a crafted link
  could carry a longer string).
- `import.meta.env.BASE_URL` always carries a trailing slash, so the
  invite-link builder strips it before joining with the leading-slash
  path — otherwise you get `//new`.
