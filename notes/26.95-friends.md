# Feature 26.95 — Friends

**Feature ID:** `friends` (from `feature_list.json`)

**Status:** done

---

## What we built

The full friends cycle inside the profile's Friends section: the user's
own shareable friend code (with a copy button), an add-a-friend-by-code
form, the incoming-request list (accept / reject), the outgoing-request
list (cancel), and the accepted-friends list (remove, behind a
confirmation dialog). It is backed by a new typed API module
(`src/api/friends.ts`) wrapping the eight live friend endpoints, with the
same `ApiError` / `mapError` discipline as `rooms.ts` and `auth.ts`.

## TS / React concepts that appear

- **Generic narrowing of a Spring `Page` envelope** — `narrowPage<Raw, T>`
  takes the optional-field generated page shape plus a per-item narrower
  and returns a tight `Page<T>` (`items` + `page` / `totalPages` / `last`
  meta). The generic keeps one projection for both `FriendsPage` and
  `FriendRequestsPage`. Defensive defaults (`totalPages ?? 1`, `last ??
true`) mean an incomplete envelope never offers "Load more" into the
  void.
- **`useCallback` with an empty dep array for stable loaders** — the three
  list loaders (`loadFriends` / `loadIncoming` / `loadOutgoing`) are
  memoised so the mount `useEffect`'s dependency array is honest
  (`exhaustive-deps` is satisfied) and the action handlers can call them
  freely without re-creating the effect. This is one of the few legitimate
  `useCallback` uses per `docs/conventions.md` (a dependency of another
  hook that would otherwise change identity each render).
- **Re-fetch over optimistic update** — every mutating action awaits the
  server then re-fetches the affected list(s). Accept re-fetches _both_
  incoming (the row vanishes) and friends (the row appears) in parallel via
  `Promise.all`. No client-side reconstruction of server state; the server
  stays the single source of truth.
- **Parallel mount fetches (no waterfall)** — the friend code and the three
  lists are independent, so the mount effect fires all four together rather
  than awaiting them in sequence, per the React-performance rules.
- **A `ListState<T>` discriminant-free state record** — `{ items, page,
last, loading, loaded }` per list. `loaded` distinguishes "never fetched"
  (show spinner) from "fetched, empty" (show the empty copy) so the empty
  state does not flash during the first load.
- **`useEffect` cleanup with a `cancelled` flag** — the friend-code fetch
  guards its `setState` calls behind a `cancelled` ref-in-closure so an
  unmount mid-flight does not set state on a dead component (mirrors the
  pattern already in `Profile.tsx`).

## Decisions taken

- **Decision:** one `deleteFriendRequest(requestId)` wrapper serves both
  "reject incoming" and "cancel outgoing".
  **Alternatives considered:** two named wrappers.
  **Why this one:** the backend endpoint
  (`DELETE /api/me/friends/requests/{id}`) is identical for both — there is
  no REJECTED state, both just delete the row. Two wrappers would be a
  cosmetic lie about a single server operation. The UI layer decides which
  list to refresh.

- **Decision:** pagination is an explicit per-list "Load more" button that
  _appends_ the next page, shown only while `last === false`.
  **Alternatives considered:** numbered page controls; silent truncation to
  page 0.
  **Why this one:** the plan forbids silent truncation. "Load more" is the
  lowest-friction control for a friends list (you scan top-to-bottom, you
  rarely page backwards) and append-not-replace means the user never loses
  rows they already saw. Numbered controls are overkill at friend-list
  scale.

- **Decision:** a shared Snackbar funnels every action error through
  `messageForError(unknown)` → `messageFor(code)`.
  **Alternatives considered:** per-list inline error rows.
  **Why this one:** matches the existing `NewGame` Snackbar pattern, keeps
  the error copy in `errors.ts` (the localisation single-point), and avoids
  five separate error surfaces. Passive list-load failures and
  user-initiated action failures both land in the same announced toast.

- **Decision:** the friends list (and only the friends list) gates Remove
  behind a confirmation `Dialog`; request reject/cancel are immediate.
  **Alternatives considered:** confirm everything; confirm nothing.
  **Why this one:** removing an accepted friend is the only destructive,
  not-easily-undone action (you would need their code to re-add). Rejecting
  or cancelling a _pending_ request is cheap to redo. This mirrors the
  Logout confirm in `AccountMenu` (confirm only what the user would regret).

## How this compares to what I know

- **In http4s + circe this would be...** the eight `client.GET/POST/DELETE`
  calls are what you would get from a Tapir/`Http4sClientDsl` client plus
  circe codecs. The `narrowFriend` / `narrowFriendRequest` functions are
  the hand-rolled equivalent of a circe `Decoder` that refuses a partial
  JSON — except the generated `schema.ts` types every field optional
  (Spring's `@Schema` does not emit `required`), so we re-impose the
  not-null contract at the boundary instead of trusting the codec. The
  thrown `ApiError(UnknownError)` on a missing field is the `DecodingFailure`
  you would get from a circe `Decoder[A]` that hit a `null`.
- **`Page<T>` ≈ a `fs2.Stream` page you `compile`** — except here the
  "stream" is user-driven: each "Load more" click pulls the next page and
  concatenates. There is no laziness or backpressure; it is a plain
  `List[A]` you grow by hand.
- **`useCallback` ≈ memoising a closure so a downstream `Eq`/identity check
  is stable** — in Cats you would not think about identity of a function
  value; in React, referential identity of a callback is load-bearing for
  `useEffect` deps, so you hoist it. The closest Scala analogue is caching a
  partially-applied function so a `==`-by-reference cache key stays stable.
- **Re-fetch over optimistic ≈ "read-your-writes via a fresh query"** —
  rather than maintain a local replica and reconcile (an `Ref[F, State]`
  you mutate in lock-step with the server), we treat the server's GET as
  authoritative after every write. Simpler, at the cost of a round-trip.

## Gotchas / things I learned the hard way

- The generated page types make `content`, `number`, `totalPages`, and
  `last` all optional. The `narrowPage` defaults matter: without
  `last ?? true` an empty 200 with no `last` field would have shown a
  "Load more" button that fetches page 1 forever.
- `getFriendCode` returns `FriendCodeResponse`, but openapi-fetch's `data`
  is typed as the union body; I cast through
  `as GeneratedFriendCode | undefined` before the null-check, the same shape
  the list wrappers use for their page bodies (the generated 2xx body is
  not directly assignable without the narrowing step).
- The accept-test needed distinct `displayName`s across the request and the
  resulting friend so the assertion ("Friends since …" appears) proves the
  row migrated lists rather than just re-rendered. Querying by the
  `secondary` text is the cleanest signal that it is the friends-list entry.
