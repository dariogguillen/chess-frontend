# Feature 11.6 — Restore-tab resync

**Feature ID:** `restore-tab-resync` (from `feature_list.json`)

**Status:** in progress

---

## What we built

A two-line surgical fix on the Play page that recovers the board after a
session-restore (`Ctrl+Shift+T`) navigation aborts the initial-load GET
mid-flight. Concretely: dropped the `AbortController` from the
initial-load effect (so the cleanup no longer kills the in-flight
request), and dropped the initial-mount suppression in feature 11.1's
resync effect (so the first `Disconnected → Connected` transition
always issues a recovery GET). The trade-off is one deliberate
idempotent double-fetch per mount on the happy path; the payoff is a
robust safety net against an unobservable race between `back_forward`
navigation, React.lazy + `<Suspense>`, and React 19's concurrent
rendering.

## TS / React concepts that appear

- **`AbortController` + `useEffect` cleanup — and when NOT to use it.**
  ([MDN —
  `AbortController`](https://developer.mozilla.org/en-US/docs/Web/API/AbortController),
  [React docs — `useEffect` cleanup](https://react.dev/reference/react/useEffect#parameters))
  The textbook pattern wires `AbortController` into a `fetch(..., {
signal: ac.signal })` and aborts in the cleanup. That works when the
  fetch's resolution is irrelevant to a no-longer-mounted component —
  the goal is to free server / network / browser resources. It stops
  working the moment React's cleanup is fired _speculatively_ on a
  component that will keep rendering: the cleanup runs as a hint, not
  as a commitment, and aborting the fetch on hint-level information
  destroys work that the component still wants. Feature 11.6's first
  surgical change is to demote the cancellation contract from "cancel
  the effect itself" to "suppress the downstream consumer when the
  closure has been superseded", which is exactly what a closure-scoped
  `let cancelled = false` flag expresses without amplifying the
  damage.

- **Concurrent-rendering speculative cleanup under `back_forward`.**
  ([React 19 release notes —
  Concurrent rendering](https://react.dev/blog/2024/12/05/react-19),
  [web.dev — Back-forward cache](https://web.dev/articles/bfcache))
  The bug-producing combination here is `back_forward` navigation
  (history traversal / session-restore) hitting a `<Suspense>`
  boundary that wraps a `React.lazy(...)` page chunk. The browser
  walks the history, React starts hydrating the page chunk, the
  Suspense boundary may render-then-cleanup-then-render-again as
  the lazy module resolves; an effect mounted inside the page chunk
  sees a cleanup that LOOKS like an unmount and is actually a
  transient probe. Any side effect that's destructive on cleanup
  (`AbortController.abort()`, an `EventSource.close()`, a
  `clearTimeout`) will eat work the next render needed. The
  defensive pattern is exactly the same one Cats Effect leans on:
  prefer flag-style suppression of downstream consumers over
  cancellation of the upstream producer, unless you genuinely need
  the producer to stop.

- **`useRef<ConnectionState | null>` as a transition detector — same
  shape, simpler gate.** Feature 11.1 used the `null` sentinel as a
  "skip the first edge" filter so the resync effect didn't
  double-fetch alongside the initial-load. Feature 11.6 keeps the ref
  but drops the special-case for `null`: the gate is now "transition
  INTO Connected fires; staying Connected does not", which collapses
  to a single comparison (`previousConnectionState.current ===
Connected ? skip : fire`). The `null` initial value just means "we
  have not yet seen any state on this mount" and falls through to
  "fire on the first Connected" naturally. Less code, fewer corner
  cases, same lifetime semantics.

- **The "deliberate idempotent double-fetch" pattern.** When two
  effects fan out from independent triggers (mount + WS connect) and
  each can robustly serve the same goal (load authoritative game
  state), the choice between "deduplicate them" and "let both run
  idempotently" is a robustness trade-off. Deduplication couples the
  two effects via a shared flag (`hasFetchedOnce`); idempotence
  decouples them at the cost of redundant work on the happy path. We
  pick idempotence when (a) the work is genuinely idempotent (a GET
  with no side effect on the server is the canonical example), (b)
  the cost of duplication is small (one ~500-byte response), and (c)
  the cost of the rare failure mode the second path covers is large
  (board stuck at initial position with no recovery). The Scala
  analogue is `cats.Monoid` + `combineN` returning a result that
  converges regardless of how many times you apply it.

## Decisions taken

- **Decision: Drop `AbortController` from the initial-load effect
  entirely instead of guarding the abort on "are we actually
  unmounting".**
  - **Alternatives considered:** keep the controller and add a
    "mounted-for-real" guard (e.g. a `useRef<boolean>` flipped after
    a microtask delay, so the speculative cleanup window doesn't
    abort).
  - **Why this one:** the guard adds complexity and timing assumptions
    (how long is the speculative window? what if Suspense triggers
    more than once?) that have to be tested for every React minor
    release. The flag-only pattern has the same robustness with
    strictly less moving machinery; the only cost is that an actual
    unmount-during-fetch lets the network response complete in the
    background, which is harmless (the closure's `cancelled = true`
    suppresses the state write).

- **Decision: Drop the initial-mount suppression in the resync
  effect, accepting the deliberate double-fetch.**
  - **Alternatives considered:** keep the suppression and only fix
    the AbortController issue.
  - **Why this one:** Change 1 alone fixes the back_forward case if
    the speculative cleanup is the only failure mode. The production
    forensic on 2026-05-28 showed it was the dominant one, but
    "dominant" is not "only" — the resync drop also covers transient
    network errors on the initial GET, mid-fetch tab-throttle
    interruption, and any future failure mode of the initial-load
    effect we haven't yet diagnosed. Defense in depth is cheap here
    (one extra GET on mount) and the payoff is bounded recovery
    latency (~100ms after WS Connected) regardless of how the
    initial-load failed.

- **Decision: Document the deliberate double-fetch loudly in the
  inline comment.**
  - **Alternatives considered:** terse comment ("resync fires on
    every Connected transition").
  - **Why this one:** a future implementer with a perf-optimization
    mindset will see two GETs racing on mount and want to
    deduplicate them. The original feature 11.1 author already made
    that mistake and the user paid for it. The comment now spells
    out the bug-prevention rationale and references this note for
    the long form, so the next "let me clean this up" instinct
    bounces off the prior-art warning.

- **Decision: REST-overwrites semantics for the resync vs MoveEvent
  race.**
  - **Alternatives considered:** event-overwrites semantics — if a
    MoveEvent arrives between the resync's GET dispatch and its
    resolution, the event wins and the GET response is dropped.
  - **Why this one:** match the existing feature 11.1 semantics
    instead of introducing a new arbitration rule. The REST GET is
    the authoritative snapshot when it resolves — the backend's
    Postgres state has already absorbed any event that fired before
    the GET returned. Picking REST-wins is the simplest mental model
    ("the snapshot we have is the authoritative state at the time
    of GET resolution"), and the alternative would require tracking
    "did an event arrive after dispatch" with extra state.

- **Decision: Reverse the "no double-fetch on initial mount" test
  instead of deleting it.**
  - **Alternatives considered:** delete the test with an inline
    comment referencing this note.
  - **Why this one:** the test still verifies a contract — just the
    opposite contract from before. Reversing it to "fires the
    deliberate idempotent double-fetch on initial mount" preserves
    the regression guard (a future implementer who reintroduces the
    suppression breaks this test) and the test name reads as
    documentation of the intent. Deletion would leave a gap; comment
    only would lose the assertion.

- **Decision: Skip the Playwright e2e for this fix.**
  - **Alternatives considered:** drive `Ctrl+Shift+T` via a
    Playwright session-restore simulation.
  - **Why this one:** Playwright cannot deterministically simulate
    bfcache / `back_forward` navigation. The
    `getEntriesByType('navigation')[0].type` value is set by the
    browser based on actual history traversal, not by a synthetic
    navigation API call. The unit tests cover the
    abort-and-recover invariant via MSW `HttpResponse.error()` for
    the initial GET; that's the closest deterministic proxy.

## How this compares to what I know

- **In Cats Effect this would be...** the canonical "cancel the
  producer vs suppress the consumer" decision. `AbortController` is
  morally the `IO` cancellation token: `IO.race(fetchIO, cancelTok)`
  cancels the producer outright. The closure-scoped flag is morally
  `Deferred[IO, Unit]` used as a permission ticket: the consumer
  reads `flag.get` and only proceeds when the ticket is still valid,
  while the producer keeps running to completion. The right tool
  depends on whether you want the side effect (the network request)
  to stop, or just want to ignore its result. Under React's
  speculative cleanup, you want the latter — and getting it wrong
  destroys work that the component still wants.

- **In `fs2.Stream` this would be...** the same transition-detector
  pattern as feature 11.1, just with the `prev.isEmpty` filter
  removed. The full Scala-y rendering is:

  ```scala
  connectionStateStream
    .scan(Option.empty[ConnectionState]) { (prev, curr) => Some(curr) }
    .zipWithPrevious
    .collect { case (Some(prev), curr) if prev != Connected && curr == Connected =>
      curr
    }
    .evalMap(_ => getGameState >>= syncFromServer)
  ```

  The `useRef<ConnectionState | null>` is the React-idiomatic spelling
  of the `zipWithPrevious` + filter combo; the `null` initial value
  doubles as the "we have no previous yet" Option-like sentinel.
  Feature 11.6 removes the extra "`prev.isDefined`" filter, so the
  first edge fires too.

- **In tapir this would be...** unchanged. `getGameState` is the same
  `Endpoint[GameId, ApiError, GameState, Any]` we always called. The
  interesting bit is not the endpoint; it's the call-site discipline
  around when to invoke it and how to handle cancellation /
  cleanup races. tapir doesn't prescribe a "fire on transition INTO
  Connected" pattern; that's downstream of an `fs2.Stream` of
  connection events derived from the WS client lifecycle.

- **In http4s / Cats Effect, the `back_forward` analogue is...** a
  fiber that is observed as "completed" but actually still has
  scheduled continuations. The lesson is the same in both ecosystems:
  if you mutate observable state on a cleanup hook (or a `finalizer`,
  or a `bracketCase`'s release), make sure the state you're mutating
  is one the next pass actually wants gone — otherwise the cleanup
  is destructive in a way the runtime model doesn't surface.

## Gotchas / things I learned the hard way

- **`performance.getEntriesByType('resource')` is the forensic tool
  of last resort.** The user reported the bug with no DevTools open.
  The browser's `performance` API retains every resource fetch in a
  ring buffer, so a `performance.getEntriesByType('resource').filter(e
=> e.name.includes('/api/games/'))` from the JS console after the
  bug recovers shows every GET that ran. The signature of an aborted
  fetch is `transferSize: 0`, `decodedBodySize: 0`, and a tiny
  `duration` (single-digit ms in our case): the request was
  dispatched and immediately abandoned before any bytes came back.
  Pair this with `getEntriesByType('navigation')[0].type` to learn
  whether the page entry was `'navigate'`, `'reload'`, `'back_forward'`,
  or `'prerender'` — `back_forward` is the session-restore tell.
  This pattern works for ANY production bug where DevTools wasn't
  open at the time; the buffer survives until the page unloads. Add
  it to the JS-console toolkit.

- **`performance.getEntriesByType('navigation')` only returns ONE
  entry per page load.** It is the entry that describes how the
  page itself was navigated to, not a list of subsequent
  navigations. For an SPA history-traversal across the React Router
  client-side routes, the `navigation` entry stays pinned to the
  initial page load — which is fine for the back_forward
  detection here, because the bug only manifests on a session
  restore (the actual page reload).

- **MSW's `HttpResponse.error()` is the right shape for "the network
  failed" in tests, but it surfaces as `ApiErrorCode.NetworkError`,
  not as a `DOMException('AbortError')`.** That's fine for the
  recovery test (the resync just needs ANY failure on the first GET
  to fire on first Connected), but it's worth knowing if you're
  trying to assert specifically on the abort code path. There's no
  great MSW seam for "throw an AbortError specifically"; you would
  need to bypass MSW and stub `fetch` directly.

- **The `cancelled` flag pattern requires that the closure NOT close
  over external mutable state.** Each effect-run captures its own
  `let cancelled = false`; the cleanup flips THAT closure's variable.
  If you refactored this to a `useRef<boolean>` shared across runs,
  you'd reintroduce a subtle bug: a cleanup-then-re-mount cycle would
  leave the shared ref permanently `cancelled = true` unless you
  remember to reset it on each effect run. The closure-scoped `let`
  is the simpler tool and is what the React team recommends.
