# Feature 20.4 — Google OAuth: sign-in button + `/auth/callback` fragment handling

**Feature ID:** `auth-google-oauth` (from `feature_list.json`)

**Status:** done

---

## What we built

The final slice of `user-accounts`: a "Sign in with Google" affordance on
the login page and the `/auth/callback` landing route that completes the
OAuth round-trip. The button is a full-page navigation to the backend's
Spring Security entry point (`/oauth2/authorization/google`); the backend
bounces through Google and redirects the browser back to
`/auth/callback#token=<jwt>` (or `#error=...`). The callback page reads the
URL fragment, scrubs it from the address bar, persists the token, fetches
`GET /api/me` to learn who the user is, sets the authenticated identity,
and redirects to `/home`. Error fragments redirect to `/login` with a
friendly message. Anonymous play is untouched — no route is gated.

## TS / React concepts that appear

- **The URL fragment (`window.location.hash`) as an out-of-band channel** —
  OAuth implementations stash the token after the `#` because the fragment
  is never sent to a server in an HTTP request; it lives purely
  browser-side. We read `window.location.hash` directly (it sits _outside_
  react-router's abstraction — `useLocation()` would also surface it, but
  reading the DOM property is the honest model for "what the browser
  landed on") and parse it with `new URLSearchParams(hash.replace(/^#/, ''))`.

- **`history.replaceState` to scrub a secret from the address bar** — the
  JWT must not linger in the visible URL or the back-stack.
  `window.history.replaceState(null, '', window.location.pathname)` rewrites
  the current entry in place, dropping the `#token=...` without adding a
  history entry. We do this _first thing_, before any async work.

- **The StrictMode double-invoke + a ran-once ref** — in dev, React 18
  mounts, unmounts, and remounts every component once to surface effects
  that are not idempotent. Our callback effect is destructive (it scrubs the
  hash), so a naive second run would see an empty fragment and bounce a
  legitimately-authenticating user to `/login`. A `useRef(false)` flag
  (`handled.current`) guards the body so it runs exactly once. This is the
  established idiom in this repo (see the `cancelled` flag in
  `UserContext`'s rehydration effect).

- **`useState` lazy initialiser reading `location.state`** — the Login page
  seeds its error Snackbar from `useState(() => authErrorFromState(location.state))`.
  The initialiser runs once on first render; `location.state` is a
  first-render fact for that mount (react-router carries the
  `navigate('/login', { state })` payload into the new location), so there
  is no need for an effect.

- **Defensive narrowing of `unknown`** — react-router types `location.state`
  as `unknown` (it is arbitrary serializable data the previous route chose
  to pass). `authErrorFromState` narrows: object, non-null, `authError` is a
  string. This is the same discipline as `isServerErrorBody` in
  `errors.ts`.

- **`Button component="a"` — the polymorphic-component prop** — MUI's
  `component` prop swaps the rendered element while keeping the MUI styling.
  Here it renders a real `<a href>` (full-page navigation to a possibly
  cross-origin backend URL), _not_ a react-router `<Link>` (which would do a
  client-side route transition and never leave the SPA). The accessible role
  becomes `link`, which the test asserts on.

- **`React.lazy` for the route** — `/auth/callback` is registered lazily in
  `Public.tsx`, matching `Login`/`Register`/`NewGame`/`Play`. It is a leaf
  page reached only by an external redirect, so it should not be in the
  initial bundle.

## Decisions taken

- **Decision:** `authenticateWithToken(token)` is a _new_ UserContext op,
  distinct from the existing `setAuthenticated(session)`.
  - **Alternatives considered:** reuse `setAuthenticated` and have the
    callback page do the `me()` fetch itself.
  - **Why this one:** the email/password flow already holds the full
    `AuthSession` (token + user) from the login response, so
    `setAuthenticated` takes both with no round-trip. OAuth hands the
    frontend _only_ the token in the fragment — there is no user object — so
    the `me()` round-trip is mandatory on this path. Encapsulating
    "persist → `me()` → set identity, clear token on failure" in the context
    keeps the token-lifecycle policy in one place (the context owns
    `writeToken`/`clearToken`) rather than leaking it into a page. The op
    reuses `setAuthenticated` internally for the final flip, so the
    identity-shaping logic is not duplicated.

- **Decision:** on `me()` failure, `clearToken()` then _rethrow_.
  - **Alternatives considered:** swallow the error and navigate internally;
    leave the token in place.
  - **Why this one:** a token that `me()` rejects is dead — leaving it would
    make the next page load retry a stale credential (the mount-rehydration
    effect). Rethrowing lets the _caller_ (the callback page) decide the UX
    (redirect to `/login` with a generic message). Separation of mechanism
    (context clears the bad token) from policy (page chooses the redirect).

- **Decision:** error fragments map to friendly copy in the page, not in
  `errors.ts`.
  - **Alternatives considered:** add `email_taken` / `oauth_missing_profile`
    to the `ApiErrorCode` machinery.
  - **Why this one:** these are OAuth-flow-specific fragment values, not
    server `ErrorResponse.error` codes — they never travel through the
    `ApiError` path. A small local `Record<string, string>` keeps them where
    they are produced. The generic fallback still routes through
    `messageFor(ApiErrorCode.UnknownError)` so an unexpected code degrades
    gracefully.

- **Decision:** add an `/oauth2` Vite dev proxy entry.
  - **Why this one:** in dev, `backendUrl` is `''`, so `googleAuthUrl`
    resolves to the path-relative `/oauth2/authorization/google`. Without a
    proxy entry, the browser would navigate to
    `http://localhost:5173/oauth2/...` (the Vite dev server), which has no
    such route. Mirroring the `/api` entry forwards it to the backend.
    Google's own callback to the backend
    (`/login/oauth2/code/google`) hits the backend origin directly and needs
    no frontend proxy.

- **Decision:** raised the global Vitest `testTimeout` to 15s.
  - **Why this one:** adding a new test file tipped the full parallel suite
    past the 5s default on a loaded machine — the `userEvent.type` +
    `waitFor(navigation)` success-path tests in `Login`/`Register` flake
    under CPU contention (they pass comfortably in isolation). The bump adds
    headroom without weakening any assertion.

## How this compares to what I know

- **In http4s / oauth2 terms** — the backend owns the `AuthorizationCodeGrant`
  dance (Spring Security here, `org.http4s.client.oauth1`/oauth2 middleware
  there). The frontend's only job is the redirect endpoint that receives the
  final credential. The fragment-vs-query split is the same security
  consideration you weigh server-side: a query string lands in access logs
  and the `Referer` header; the fragment never leaves the browser. Putting
  the JWT in the fragment is the "implicit-flow leftover" pattern — and
  `replaceState` is the manual equivalent of the redirect-after-POST you do
  to keep a secret out of the resubmittable URL.

- **The ran-once ref vs `Ref[F, Boolean]`** — `useRef(false)` plus
  "check-then-set inside the effect" is exactly a `Ref[IO, Boolean]` guard
  around an effect you must run at most once. The difference: there is no
  concurrency here (React effects run on the single JS event loop), so the
  check-and-set needs no `modify`/CAS — a plain mutable field is safe.

- **`clearToken` + rethrow vs `MonadError`** — the context op is the
  TypeScript shape of `me().handleErrorWith { e => clearToken *> raiseError(e) }`
  — run a compensating action on failure, then re-raise so the caller's
  error channel still fires. `Promise.catch` returning a rejected promise
  (via `throw`) is the `raiseError`.

- **`useState` lazy init vs `lazy val`** — same as elsewhere in this repo:
  the initialiser is computed on first render and never again, like a
  `lazy val` memoised for the scope's lifetime. The audience-relevant nuance
  is that React re-running the _component function_ does not re-run the
  initialiser — only the first mount does.

## Gotchas / things I learned the hard way

- jsdom's `window.location.hash` is writable and `window.history.replaceState`
  is real, so the scrub logic is testable without mocking the location
  object — but the hash lives _outside_ react-router's `MemoryRouter`, so the
  test sets `window.location.hash` directly rather than through
  `initialEntries`.
- MUI's `CircularProgress` defaults to `role="progressbar"`. To make the
  callback's _loading status_ the single announced thing, the spinner is
  `aria-hidden` and the visible "Signing you in…" text carries
  `role="status"` + `aria-live="polite"`.
- The full-suite timeout flake was the surprise: a change that adds zero
  risk to existing logic (a new isolated test file) still destabilised
  unrelated tests purely through added parallel CPU load. The fix is config,
  not code.

## Out of scope (documented for follow-up)

End-to-end OAuth in dev additionally requires infra config outside this
frontend: a Google-console redirect-URI entry for the backend's
`/login/oauth2/code/google` and the backend's `frontendBase` set to the
dev frontend origin so it redirects back to `/auth/callback`. That is
backend/infra work, not frontend scope.
