# Feature 11.7 — Turn Indicator

**Feature ID:** `turn-indicator` (from `feature_list.json`)

**Status:** in progress

---

## What we built

A small chip next to the local player's display name on the Play page
that answers a single question — "is it my turn?" — in user-relative
terms. Two visible states: "Your Turn" (filled primary, PlayArrow
icon) when `gameState.turn === role`, and "Opponent's Turn" (outlined
default, HourglassEmpty icon) when it differs. Hidden in three
states: pre-load (`gameState === null`), no in-room context
(`role === null`), and any terminal status (CHECKMATE / STALEMATE /
DRAW / ABANDONED), so the chip never contradicts the modal dialog or
the inline abandon banner that own the "game over" framing.

## TS / React concepts that appear

- **Pure presentational component — props in, JSX out.**
  ([React docs — Your first
  component](https://react.dev/learn/your-first-component))
  The `TurnIndicator` has no `useState`, no `useEffect`, no derived
  hooks. The `isMyTurn` predicate is a single comparison evaluated
  inline at render time. The component exists primarily to give a
  _name_ to the derivation rule from `(gameState, role)` to a
  particular chip variant — the same role a small named function
  plays in any language. React's component model just happens to
  carry the call site (an `<element />`) as the natural notation for
  composing those rules into a UI tree.

- **Discriminated rendering with `return null`.**
  ([React docs — Conditional
  rendering](https://react.dev/learn/conditional-rendering))
  Three of the four code paths in `TurnIndicator` are early `return
null`. That is more honest than wrapping the chip in an outer
  ternary or a `gameState && role && !isTerminalStatus(...) && <Chip
  ... />`: each guard reads as "this is a state in which the
  component genuinely has nothing to say", and the component's
  identity (visible / invisible) is the first thing the reader sees,
  not the last branch of a long expression.

- **`Readonly<T>` on the props type.**
  ([TS handbook — Readonly
  modifier](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-0.html#readonly-properties-and-index-signatures))
  `TurnIndicatorProps` wraps the prop record in `Readonly<...>` so
  the body cannot mutate the inputs even by accident. At runtime this
  enforces nothing (React already treats props as immutable), but it
  catches a class of bugs at compile time and documents the contract
  with the same vocabulary the rest of the codebase uses.

- **Direct path imports for `@mui/icons-material/*`.**
  The icons are imported as `@mui/icons-material/PlayArrow` and
  `@mui/icons-material/HourglassEmpty`, not via a barrel
  (`@mui/icons-material`). MUI's icon barrel re-exports thousands of
  modules; a single named import from it pulls a measurably larger
  chunk graph into the build. The direct path import is the standard
  MUI guidance for production code and matches the pattern already
  used by `OpponentStatus` (`HourglassBottomIcon`, `CloudOffIcon`).

- **`aria-label` for state semantics, not the visible string.**
  ([WAI-ARIA — `aria-label`](https://w3c.github.io/aria/#aria-label))
  The visible label of the active arm is "Your Turn" — short, scans
  fast, useful for a sighted user. The `aria-label`, by contrast, is
  the full semantic sentence ("It is your turn to move"). Two
  channels: the visual one (color + shape + short text) and the
  semantic one (the label). Both have to communicate the same state,
  and the label is the source of truth for screen readers — the
  rendered color is invisible to them and the rendered text might be
  ambiguous out of context.

## Decisions taken

- **Decision: user-relative labels ("Your Turn" / "Opponent's Turn"),
  not color-relative ("White to move" / "Black to move").**
  - **Alternatives considered:** a single chip showing the side that
    moves next ("White's turn"), independent of who is viewing.
  - **Why this one:** the user's mental question is _always_ "is it
    my turn?". The color-relative framing forces a mental
    translation step on every glance — "I'm white, so 'White's turn'
    means me; OK, my turn". The user-relative framing answers the
    question directly. Same affordance, less cognitive load. The
    color-relative framing also breaks down for spectators (which
    we do not have today, but the precedent matters).

- **Decision: hide the chip during `isTerminalStatus(...)` instead of
  rendering a "Game over" arm.**
  - **Alternatives considered:** a third visible arm with neutral copy
    ("Game over", outlined, no color).
  - **Why this one:** the page already has two strong terminal
    affordances — `CustomDialog` for CHECKMATE / STALEMATE / DRAW,
    `GameOverByAbandonBanner` for ABANDONED. A "Game over" chip in
    the same render tree would be a third, weaker signal that
    competes with both. The component is more useful when it knows
    its own boundary and steps aside.

- **Decision: `color="default"` (outlined) for the passive arm rather
  than `color="info"`.**
  - **Alternatives considered:** `color="info"` with the outlined
    variant; would have read as more "alive" and could blend with
    the existing info-coloured `OpponentStatus` chip.
  - **Why this one:** the passive arm is _the most common_ state from
    the local player's perspective (they wait roughly half the
    game). A subdued chip is the right amount of presence. The
    active arm earns the visual weight (filled, primary) because it
    is the call-to-action; the passive arm earns the absence of
    weight because it is the steady state.

- **Decision: barrel re-export in `index.tsx`, not `index.ts`.**
  - **Alternatives considered:** `index.ts` (no JSX in the barrel, so
    the `.ts` extension is technically more accurate).
  - **Why this one:** the existing peers (`OpponentStatus/index.tsx`,
    `GameOverByAbandonBanner/index.tsx`) ship `.tsx`. Matching the
    convention beats arguing about the extension; consistency is
    more valuable than precision here.

- **Round 2 — minWidth lock + `aria-live` live region.**
  Two non-blocking polish items raised by ui-reviewer after Round 1:
  - A horizontal shimmy in the chip's column when the label flipped
    between "Your Turn" (~9 chars) and "Opponent's Turn" (~15 chars).
    Fixed by adding a `minWidth: 148px` lock to both arms, sized to the
    natural width of the wider arm (icon + label + chip padding at MUI
    `small`). 148px was chosen over a `theme.spacing(N)` token because
    the right value is a function of icon + font metrics, not the
    spacing grid; tying it to a spacing token would obscure the intent.
    The value lives in a single named constant
    (`CHIP_MIN_WIDTH_PX`) at the top of the file so future label
    edits land in one place.
  - The chip was not in a live region, so screen readers did not
    announce transitions between the two arms. Fixed by wrapping the
    chip in a `Box role="status" aria-live="polite"`. The wrapper
    approach was chosen over `slotProps` on the Chip because the
    component already returns `null` in three hidden states; with the
    wrapper, the live region only exists when there is something to
    announce, which is the cleanest semantic for the mount /
    label-change / unmount cycle. `polite` is the right politeness
    level: a turn flip is a normal status update, not an error.
  - **`OpponentStatus` got the same `aria-live="polite"` wrapper in
    this round for consistency.** Same gap, same fix, same politeness
    level. The `connected` arm still returns `null` (no live region to
    mount); the `disconnected` countdown and the brief `abandoned`
    static chip both gain announcement coverage. The genuinely terminal
    abandonment case is owned downstream by the inline
    `GameOverByAbandonBanner`, so `polite` is correct there too.

- **Round 3 — `OpponentStatus.ReconnectingChip` a11y restructure
  ("two surfaces" pattern).**
  ui-reviewer's REQUEST-CHANGES on Round 2 flagged a screen-reader
  flood: the Round 2 wrapper `Box role="status" aria-live="polite"` sat
  around the `ReconnectingChip`, but the chip's inner `setInterval`
  rewrites the visible label every second during the ~30–90s grace
  window. Every per-second mutation inside an `aria-live` region is a
  fresh announcement, so the user would hear "Reconnecting · 89s…
  Reconnecting · 88s… Reconnecting · 87s…" queued up across the whole
  window. `polite` queues; it does **not** deduplicate. The Round 2
  shape was wrong for this specific chip — it would have been
  acceptable on a chip with static text (and is fine on `AbandonedChip`
  and on `TurnIndicator`, both of which mutate only on infrequent
  state transitions).
  - **The fix is to split the announcement from the visible text** —
    the "two surfaces" pattern. The visible `<Chip>` keeps the
    per-second countdown ("Reconnecting · 42s") for sighted users, but
    carries a STATIC `aria-label` (`"Opponent reconnecting"`, no
    countdown) so direct AT navigation to the chip hears the steady
    state, not a moving number. A SIBLING visually-hidden
    `Box role="status" aria-live="polite"` holds the static
    announcement text and mounts only while the disconnected arm is
    active. Mounting fires the announcement ONCE; the live region's
    content never changes, so per-second visible-label updates do
    NOT trigger re-announcements. When the arm unmounts (opponent
    reconnects → `connected` arm renders `null`, or opponent abandons
    → `AbandonedChip` mounts with its own live region), the next
    transition's announcement carries the load.
  - **Visually-hidden CSS is the right tool when a live region's
    content needs to be different from the visible element.** The
    standard "sr-only" recipe — zero-size, off-screen via
    `clip: rect(0 0 0 0)`, `position: absolute`, `overflow: hidden`,
    `whiteSpace: nowrap` — keeps the element in the accessibility
    tree (so screen readers and `getByRole('status')` see it) while
    removing it from the visual layout. Crucially `display: none`
    and `visibility: hidden` would NOT work — both hide the element
    from assistive tech as well as from sighted users, which defeats
    the purpose. The CSS lives in a `visuallyHiddenSx` constant at
    the top of `OpponentStatus.tsx`; the constant is also a documented
    seam for future reuse if another component needs the same trick.
  - **Compare with the standard sr-only pattern.** The classic
    `.sr-only` class is the same recipe, just applied via a global
    stylesheet. In a MUI-emotion world, `sx` is the idiomatic place
    to put it; in a Tailwind world it would be the built-in
    `sr-only` utility; in plain CSS, an exported `.visually-hidden`
    class. The semantics are identical; the styling vehicle differs.
    The choice here is to keep it inline as `sx`-on-`Box` because the
    use site is one (1) place and there is no other consumer yet.
    When a second component wants the same treatment, this constant
    extracts cleanly into a shared utility.
  - **The `aria-label` on the chip also went static** as a
    belt-and-suspenders measure. Even though the visible chip is no
    longer the source of the announcement (the hidden region is), a
    user who navigates focus _onto_ the chip directly would still
    have the per-second number read out as the accessible name if
    the aria-label included it. Making the aria-label static
    (`"Opponent reconnecting"`) keeps the steady state consistent
    across both surfaces.
  - **`AbandonedChip` and `TurnIndicator` are unchanged from Round 2.**
    Both have static or low-frequency content (Disconnected is a
    single static string; turn-flip transitions happen at most every
    few seconds at fast time control, not per second). The
    `aria-live="polite"` wrapper is correct for them.

## How this compares to what I know

- **In Cats this would be...** a `def render: (GameState, Role) => Option[Html]`
  function — same total signature, including the
  `None` arm for the three hidden states. The React component is
  thinly disguised: `gameState: GameState | null` and `role: Role |
null` carry the optionality at the call site, the early `return
null` carries the `None` arm at the return site. The `Eq[A]`
  typeclass derivation analogy is even closer if you squint —
  `TurnIndicator` is a derivation rule that produces a UI element
  from the data, in the same way `derive[Eq[Foo]]` produces an
  equality check from the structure of `Foo`. The "presentation" of
  the data is mechanical given the inputs; we just give it a name so
  the call site does not have to spell it inline.

- **In http4s this would be...** a `Decoder[GameState] => Response`
  layer rendering an HTML fragment, which is exactly the same pure
  derivation pattern. The only difference is that the React function
  composes with the rest of the page via the virtual DOM whereas the
  http4s function composes via the `HttpRoutes[F]` algebra.

- **`useState` and `useEffect` are not here on purpose.** Coming from
  Cats Effect, the temptation is to reach for `Ref[F, ...]` and
  `Resource.make` even when the data needed is already in scope. The
  React equivalent of "the data is already in scope" is "the parent
  threads it through as props"; reaching for `useState` here would be
  the same mistake as reaching for a `Ref` to hold a constant.

- **The "discriminated rendering" pattern is your `match` on a sealed
  trait.** Three `null` arms followed by an `isMyTurn` branch is
  structurally identical to:
  ```scala
  (gameState, role) match {
    case (null, _) => None
    case (_, null) => None
    case (g, _) if isTerminal(g.status) => None
    case (g, r) if g.turn == r => Some(activeChip)
    case _ => Some(passiveChip)
  }
  ```
  The fact that JSX makes you spell `null` rather than a `None` value
  is a syntactic difference, not a semantic one.

## Gotchas / things I learned the hard way

- The `aria-label` is the source of truth for assistive tech, even
  when the visible label is short and unambiguous. The first version
  of the chip in my head was just `label="Your Turn"` with no
  `aria-label`; the screen reader would have announced "Your Turn"
  out of context with no indication of _which_ turn or _what_ turn.
  The plan specified the explicit label, and it was the right call.

- `@mui/icons-material/PlayArrow` (direct path) vs
  `@mui/icons-material` (barrel). Bundle-wise this matters more than
  it feels like it should; reaching for the barrel even once in a
  page chunk would balloon the chunk by tens of kilobytes. The
  pattern was already in place in `OpponentStatus`; the gotcha is
  that the barrel autocompletes more aggressively in editors, so the
  discipline is mostly about not letting the editor write the wrong
  import for you.
