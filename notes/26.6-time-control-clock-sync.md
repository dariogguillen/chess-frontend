# Feature 26.6 — Fix: opponent move doesn't refresh the clocks (live divergence)

**Feature ID:** `time-control-clock-sync` (from `feature_list.json`)

**Status:** done

---

## What we built

A bug fix found live-testing feature 25 (time-control) in prod: in a timed
game the two players' clocks **diverged** over the course of the game. The
root cause was a missing data propagation — an OPPONENT move arriving over
STOMP never refreshed the clock fields, so each tab only re-synced its
clocks on ITS OWN moves. This fix carries the clock values the backend
already sends on every `MoveEvent` (`whiteTimeRemainingMs`,
`blackTimeRemainingMs`, `playedAt`) through the frontend type and into
`gameState`, so an opponent's move re-anchors both clocks exactly the way
your own move already did.

## The bug, precisely

Two move paths feed `gameState` on the Play page, and they were asymmetric:

- **Your own move** → `submitMove` (REST POST) returns the full
  `GameState` with fresh clocks → `syncFromServer` applies all of it,
  including `whiteTimeRemainingMs` / `blackTimeRemainingMs` / `lastMoveAt`
  (`Play.tsx`, the `submitMove` call). Correct.
- **The opponent's move** → arrives as a STOMP `MoveEvent` →
  `applyOpponentMove` did `setGameState((prev) => ({ ...prev, fen, status,
turn, moves }))` — and **left the three clock fields at the value from
  the initial GET**. So clocks only advanced on your own turns.

Net effect: each tab decremented its own side correctly (its own POST
refreshed both clocks), but never saw the _opponent's_ time elapse, so the
two tabs disagreed about the opponent's remaining time, and the gap grew.

## Root cause: backend sends, frontend ignored

This was a one-sided contract drift, not a logic bug. The backend
`MoveEvent.java` record **does** send `whiteTimeRemainingMs: Long`,
`blackTimeRemainingMs: Long` (both `null` for an untimed game) and
`playedAt: Instant`. The hand-maintained frontend mirror type `MoveEvent`
(`src/api/wsEvents.ts`) declared `playedAt` but **omitted both
`*RemainingMs` fields**, and `applyOpponentMove` consequently never read
them. STOMP frames are parsed with a raw `JSON.parse(frame.body) as T`
(`src/utils/ws/stompClient.ts`) — there is no per-field narrowing layer —
so the data was physically present on the wire and silently dropped at the
type boundary: TypeScript can only forward what the type declares the
consumer can read.

The feature-25 tests missed this because their `MoveEvent` fixtures were
built from the (incomplete) type, so they had no clock fields to assert on.

## The fix

1. **`src/api/wsEvents.ts`** — added `whiteTimeRemainingMs: number | null`
   and `blackTimeRemainingMs: number | null` to the `MoveEvent` type
   (`number | null` because the backend `Long` is `null` for an untimed
   game; `playedAt` was already present). No parse/narrow function exists
   for STOMP events — the generic `subscribe<T>` cast is the only boundary —
   so declaring the fields is sufficient for the data to flow.
2. **`src/pages/Play/Play.tsx`** — in `applyOpponentMove`'s
   `setGameState` updater, added `whiteTimeRemainingMs:
event.whiteTimeRemainingMs`, `blackTimeRemainingMs:
event.blackTimeRemainingMs`, and `lastMoveAt: event.playedAt`. Now an
   opponent move refreshes both clocks and re-anchors the countdown,
   identical to the REST own-move path.
3. The own-move path (`submitMove` → `syncFromServer`) is unchanged. Untimed
   games still send `null` clock fields, which flow through unchanged and
   render no clocks (`hasClock` stays false).

## TS / React concepts that appear

- **The type boundary is the only thing a `JSON.parse … as T` cast can
  surface.** `subscribe<T>` does `JSON.parse(frame.body) as T` with no
  schema validation. That cast is a _promise_ to the compiler, not a check:
  the runtime object had the clock fields all along, but because the `T`
  (`MoveEvent`) didn't declare them, every downstream consumer was
  statically blind to them. Widening the type is the entire fix — there is
  no extra runtime plumbing. This is the failure mode of structural typing
  with unchecked boundaries: a field you don't name is a field you can't
  read, even when it's right there in memory.
- **Functional `setState` updater preserving the rest of the record.**
  `applyOpponentMove` uses `setGameState((prev) => ({ ...prev, … }))`. The
  bug was an incomplete spread target — `...prev` carried the _stale_ clock
  values forward, which read like "preserved" but was actually "never
  updated". The fix is to name the freshly-arrived fields after the spread
  so they override.
- **`number | null` at the wire boundary as the untimed sentinel.** Mirrors
  `GameState`'s own clock fields (`src/api/games.ts`): `null` means untimed.
  Keeping `MoveEvent`'s fields the same shape lets `applyOpponentMove`
  assign them straight across with no coalescing.

## Decisions taken

- **Decision:** Fix by propagating the event's clock fields, not by firing
  an extra REST GET after each opponent move.
  - **Alternatives considered:** On every opponent `MoveEvent`, re-fetch the
    authoritative `GameState` over REST (guaranteed-fresh clocks).
  - **Why this one:** The backend already puts the authoritative clocks on
    the move event — a GET would be a redundant round-trip per move,
    doubling traffic and adding latency/flicker, to recover data that's
    already in hand. The event is the delta _and_ carries the clocks; use
    it. (The existing resync-on-reconnect GET still covers the
    dropped-event / reconnect case.)

- **Decision:** Map `playedAt` → `lastMoveAt` so the countdown re-anchors.
  - **Alternatives considered:** Only update the two frozen `*RemainingMs`
    values and leave `lastMoveAt` from the prior move.
  - **Why this one:** `useClockCountdown` derives the live value as
    `frozen - (now - lastMoveAt)` for the side to move. If `lastMoveAt`
    stayed at the _previous_ move's instant while `*RemainingMs` jumped to
    the new frozen values, the very next render would subtract the whole
    inter-move gap from the new value and the clock would lurch. Updating
    all three together keeps the freeze-point and the freeze-value
    consistent — exactly what `syncFromServer` does with the REST payload.

## How this compares to what I know

- **In circe / tapir this would be...** the exact analogue of a `Decoder`
  for `MoveEvent` whose case class simply lacked two fields: `decode` would
  succeed (circe ignores unknown JSON keys by default), the wire bytes
  carry the data, and your code can't see it because the case class never
  modelled it. The remedy is identical — add the fields to the case class /
  the TS type. The difference is that here the "decoder" is a bare
  `as MoveEvent` cast with **no** structural verification at all, so there
  isn't even a decode step that _could_ have flagged a mismatch; the type
  is a pure compile-time assertion. A runtime validator (zod / a circe
  `Decoder` with `.as`) would at least make the boundary honest.
- **In Cats Effect this would be...** the asymmetry between the two update
  paths is like having two `Ref.update`s for the same `Ref[F, GameState]`
  where one updates four fields and the other updates seven — both compile,
  both "work", and the bug is only visible as state divergence over time.
  The fix is making the two updates write the same field set.

## Gotchas / things I learned the hard way

- The fields were already on the wire — I confirmed this before touching
  anything (backend `MoveEvent.java` sends them, and `subscribe<T>` does a
  raw cast with no narrowing), so the entire fix is a type widening plus a
  three-line spread. It's tempting to reach for a re-fetch; the data was
  already in the payload.
- Adding mandatory fields to `MoveEvent` made every test fixture that
  constructs one fail to compile — a _good_ signal. Five fixtures across
  four test files (`wsEvents.test.ts` ×3, `useGameStomp.test.tsx`,
  `Play.test.tsx`) needed the fields. The compiler found them all; I didn't
  have to grep. (The two local throwaway `MoveEvent`-named structural types
  in `stompClient.test.ts` / `useStompSubscription.test.tsx` are NOT the
  real type and were unaffected.)

## Follow-up (out of scope — flagged, not implemented)

The countdown derives `elapsed = now - playedAt` using the **client's
system clock**. Between two tabs on the _same_ machine (which is how this
bug was found and is now fixed) the system clock is shared, so they agree.
But across two _different_ machines a residual skew remains: each client's
`Date.now()` differs from the server's `playedAt` clock by that machine's
own offset, so each renders a slightly different live value even with
identical frozen inputs. Hardening this would mean anchoring the countdown
to the **local receipt time** of the event (or syncing a server-clock
offset) instead of to the server-stamped `playedAt`. That's a separate,
smaller-magnitude issue; the dominant visible bug here was the missing
propagation, which same-machine two-tab testing already proves is gone.
Left as a future `clock-skew-anchoring` follow-up.
