# Feature 26.8 — Re-snapshot OpenAPI for friends + invitations

**Feature ID:** `social-contract-resnapshot` (from `feature_list.json`)

**Status:** done

---

## What we built

A pure-codegen enabler, the third of its kind (mirrors 20.1
`auth-openapi-resnapshot` and 21 `backend-contract-resnapshot`). The
backend deployed friendship + friend-invitations to prod, growing the
wire contract well past the committed `openapi.json` (last snapshotted at
feature 21). We re-snapshotted `openapi.json` from the **deployed prod**
backend, regenerated `src/api/generated/schema.ts`, and mirrored the eight
new server error codes into our hand-written exhaustiveness-guarded error
module. No feature code, UI, or routes ship here — this only makes the new
friend/invitation paths and schemas type-available for the upcoming
`profile-shell` / `friends` / `direct-invitations` features.

## The contract delta (verified prod vs committed snapshot, 2026-06-26)

The re-fetched snapshot matched the leader's pre-verified delta exactly:

- **New paths (12):** `/api/me/friend-code`, `/api/me/friends`,
  `/api/me/friends/{userId}`, `/api/me/friends/requests`,
  `/api/me/friends/requests/{id}`, `/api/me/friends/requests/{id}/accept`,
  `/api/me/friends/requests/incoming`,
  `/api/me/friends/requests/outgoing`, `/api/me/invitations`,
  `/api/me/invitations/{roomId}`, `/api/me/invitations/{roomId}/accept`,
  `/api/me/invitations/{roomId}/to/{inviteeUserId}`.
- **New schemas (8):** `FriendCodeResponse`, `FriendRequestResponse`,
  `FriendRequestsPage`, `FriendResponse`, `FriendsPage`,
  `InvitationResponse`, `SendFriendRequestRequest`, `SendInvitationRequest`.
- **Removed/renamed schemas:** NONE. Unlike 20.1 (which renamed
  `Player` → `PlayerView` and forced an alias retarget), this snapshot
  renames nothing, so there is no `components['schemas'][...]` alias to
  retarget. All 19 pre-existing schema names survive verbatim.
- **Removed paths:** NONE.
- **New error codes (8)** — the part of the delta that breaks the
  typecheck through our exhaustiveness guards (see Decisions):
  `ALREADY_FRIENDS`, `DUPLICATE_FRIEND_REQUEST`, `FRIEND_CODE_NOT_FOUND`,
  `FRIEND_NOT_FOUND`, `FRIEND_REQUEST_NOT_FOUND`, `INVITATION_NOT_FOUND`,
  `NOT_ROOM_MEMBER`, `SELF_FRIENDSHIP`. All flowed into
  `ServerErrorCode = NonNullable<components['schemas']['ErrorResponse']['error']>`
  on the next generate.

## TS / React concepts that appear

- **OpenAPI → TypeScript codegen (`openapi-typescript`)** — the
  `openapi:generate` npm script feeds `openapi.json` into
  `openapi-typescript`, emitting one `schema.ts` that exports a
  `components['schemas'][...]` namespace and a `paths` map. Our
  hand-written wrappers (`errors.ts`, `games.ts`, `rooms.ts`, …) alias
  into that namespace, so a contract change surfaces as a **compile**
  error rather than a runtime surprise. Generation is deterministic:
  re-running it on an unchanged spec yields a byte-identical file
  (verified idempotent here via `diff`).

- **Indexed access + `NonNullable` deriving a literal union** —
  `ServerErrorCode` is
  `NonNullable<components['schemas']['ErrorResponse']['error']>`. When the
  backend adds an enum value to the `error` field's allowable values, it
  flows straight into this union on the next generate — no manual type
  edit. That is exactly how the eight new friend/invitation codes entered
  the type side.

- **Compile-time exhaustiveness via `Exclude<A, B> extends never`** —
  `errors.ts` carries a type-level assertion
  (`_ApiErrorCodeExhaustiveCheck`) whose false branch is a descriptive
  error object. When the derived `ApiErrorCode` union gains a member the
  runtime `ApiErrorCode` const object does not enumerate, the conditional
  resolves to the error shape and `tsc` fails at the declaration site.
  This is the mechanism that forced the mirror: the type side picked up
  the eight new codes automatically; the build then refused to compile
  until the const object (plus the `KNOWN_CODES` set and the
  `Record<ApiErrorCode, string>` message map) were brought back in sync.
  The `satisfies Record<ApiErrorCode, string>` on `errorMessages` is the
  complementary guard — it rejects a const-object entry that has no
  message.

## Decisions taken

- **Decision:** Snapshot from **prod**, not local, for this re-snapshot.
  - **Alternatives considered:** run the backend on `localhost:8080` and
    use the `openapi:fetch` script (which targets localhost); spin up a
    local instance.
  - **Why this one:** the friendship + friend-invitations commits are
    **deployed to prod** (verified live by the leader minutes before this
    session), so prod `/v3/api-docs` carries the full delta;
    `localhost:8080` is not running. Reproduce with:
    `curl -fsSL https://chess-backend.duckdns.org/v3/api-docs | jq . > openapi.json`.
    The `openapi:fetch` script's localhost URL was **not** rewritten — a
    configurable-URL script remains a separate polish item, deliberately
    out of scope (same call as 21).

- **Decision:** treat the eight new error codes as **in-scope mechanical
  mirroring**, exactly as 20.1 (three new codes) and 21 (one new code,
  `INVALID_JOIN_TOKEN`) did.
  - **Why mirror here, not stop:** unlike 21, where the plan asserted "no
    breaking typecheck change" and the new enum values were a surprise,
    this plan **named** the eight breaking codes up front and explicitly
    scoped the mirror in (const object + `KNOWN_CODES` + `errorMessages` +
    a `mapError` test), citing the 20.1/21 precedent. The fix is purely
    additive (new const entries, new `KNOWN_CODES` members, new message
    strings) and touches no feature flow. Consuming these codes in real
    UI is the upcoming friends/invitations features, not this enabler.

- **Decision:** user-facing copy follows the leader's suggested strings
  verbatim (e.g. `SELF_FRIENDSHIP` → "You can't add yourself as a
  friend."; `INVITATION_NOT_FOUND` → "That invitation was not found or has
  expired."). They match the tone of the existing `errorMessages` entries
  (short, friendly, second person), so no rewording was warranted. Unlike
  21, there was **no** behavioral decision to make here: these codes are
  pure error-message data with no terminal-state or narrowing policy
  (contrast 21's `TIMEOUT`, which had to join `isTerminalStatus`).

## How this compares to what I know

- **In tapir / circe this would be...** regenerating client stubs from
  the server's `Endpoint` definitions. `openapi-typescript` is the
  client-side equivalent of deriving a typed client from an OpenAPI
  document — except the "codec" is structural typing plus `JSON.parse`,
  not a derived `Decoder[A]`. The generated types are erased at compile
  time, so a wire payload that lies about its shape type-checks and only
  blows up where you touch a missing field. That is why `errors.ts` keeps
  runtime guards (`isServerErrorBody`, `KNOWN_CODES.has(...)`) alongside
  the types.

- **In a Scala sealed trait this would be...** the `Exclude<A, B> extends
never` assertion is TypeScript's hand-rolled sealed-trait + exhaustive
  `match`. In Scala, adding a case to a sealed ADT makes every
  non-exhaustive `match` a compile error for free. TypeScript has no
  closed-union exhaustiveness for a runtime value, so we synthesise it
  with a conditional type whose false branch is a descriptive error
  object — the build fails at the declaration that fell behind. Here,
  adding eight enum members to the wire contract turned that assertion red
  until the const object enumerated all eight.

- **Codegen idempotency** is the `scalapb`/guardrail property: running the
  generator twice on the same input is a no-op. Verified explicitly here
  (regenerate, `diff`, expect empty) so the committed `schema.ts` is
  reproducible from the committed `openapi.json`.

## Gotchas / things I learned the hard way

- None this round. The delta matched the leader's pre-verification
  exactly (12 paths / 8 schemas / 0 renames / 8 codes), and because no
  schema was renamed there was no alias-retarget blast radius — the only
  `tsc` fallout was the single exhaustiveness guard in `errors.ts`, which
  the mirror closed in one pass. Worth re-stating the standing lesson from
  20.1/21 anyway: for a codegen change, let `tsc` enumerate the full blast
  radius rather than trusting a hand-listed set of call sites.
