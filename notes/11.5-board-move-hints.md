# Feature 11.5 — Board move hints

**Feature ID:** `board-move-hints` (from `feature_list.json`)

**Status:** done

---

## What we built

Dragging one of your own pieces now lights up its legal destinations on
the board. Quiet (non-capture) targets show a centred translucent dot;
capture targets — including en passant — show an inset ring. Hints
clear on drop (legal, illegal, off-board, or same-square cancel), on
opponent move, on game end, on POST failure (server rejected the move),
and on `Escape`. The whole policy is derived from
`chess.moves({ square, verbose: true })` and rendered via the new
`squareStyles` option that `react-chessboard` v5 exposes.

## TS / React concepts that appear

- **Custom hook + `useMemo` keyed on a string fingerprint** — chess.js
  is an imperative, mutable library. The instance reference never
  changes across renders, so listing it in a `useMemo` dependency array
  is a no-op. The canonical workaround is to depend on a value that
  _does_ change with the state of the world: the FEN string. FEN
  round-trips losslessly under `load`/`fen()`, so equal FENs imply
  equal positions. `useMoveHints` therefore reads `chess.fen()` into a
  local `fen`, depends on `[fen, selectedSquare, theme.palette.primary.main]`,
  and reads `chess.moves(...)` inside the memo. The `chess` parameter
  is deliberately not in the dep array (and the lint rule is
  suppressed at the call site with a comment).
- **`useEffect` with a global event listener and explicit cleanup** —
  `react-chessboard` v5 (on `@dnd-kit` internals) doesn't expose a
  drag-cancel callback. To honour the convention that `Escape` cancels
  a selection mid-drag, `Play.tsx` registers a `keydown` listener on
  `window` while `selectedSquare !== null` and removes it on unmount or
  when the selection clears. The effect's dep array is `[selectedSquare]`
  so the listener registers and tears down at the boundaries of a
  selection, not on every render.
- **MUI `alpha()` + `useTheme()`** — both styles derive from
  `theme.palette.primary.main` via `alpha(color, opacity)`. Routing
  through the theme keeps the hint visible under both light and dark
  modes today, and makes the upcoming `board-themes` feature (12) a
  matter of palette swaps rather than scattered hex literals.
- **React 19 `react-hooks/set-state-in-effect`** — the original plan
  proposed a `useEffect(() => setSelectedSquare(null), [fen, status])`
  to clear hints on any position change. React 19's ESLint rule
  flags this as a cascading-render anti-pattern. The fix was to push
  the clear into the actual transition points: `syncFromServer`,
  `applyOpponentMove`, `handleGameAbandoned`, and `revertTo`. Each
  transition is the right place to own its side-effects on
  drag-related UI state — the effect was a global hook that
  duplicated work already triggered by the same updates. Documented
  here so the reviewer doesn't expect the effect that the plan
  described.
- **Discriminated capture branch via chess.js' verbose move list** —
  `chess.moves({ square, verbose: true })` returns `Move[]` where
  `captured?: PieceSymbol` is `undefined` on a quiet move and the
  captured piece's letter on a capture (`'p'`, `'n'`, etc.).
  En passant is `captured: 'p'` with `flags` including `'e'`. The hook
  branches on `m.captured !== undefined` to pick `MOVE_STYLE` vs
  `CAPTURE_STYLE`. The TypeScript narrowing is on `captured`'s
  presence rather than `flags` matching, which keeps the conditional
  symmetrical for normal captures and en passant.

## Decisions taken

- **Decision:** factor a `useMoveHints` hook in `src/hooks/` instead of
  inlining the logic in `Play.tsx`. **Alternatives considered:** a
  module-level pure function called from inside `Play`'s render; a
  `useMemo` directly in `Play`. **Why this one:** the hook has a
  natural Hook surface (`useTheme` for the theme; `useMemo` keyed on
  FEN). A pure function would still need theme access threaded in;
  inlining a `useMemo` would mix chess-move-derivation with the
  rest of the Play page's state machinery. Keeping it isolated also
  gives unit tests a clean handle.

- **Decision:** push hint-clearing into the transition functions
  (`syncFromServer`, `applyOpponentMove`, `handleGameAbandoned`,
  `revertTo`) rather than driving it from a `useEffect` keyed on
  `[fen, status]`. **Alternatives considered:** keep the effect (the
  plan's original wording). **Why this one:** React 19's
  `react-hooks/set-state-in-effect` rule blocks the synchronous
  `setState` inside an effect (lint error, not warning). The effect
  was also a global hook duplicating the clearing work already
  triggered by the same updates — every entrypoint that mutates the
  FEN is a function we control. Cascading renders disappear; the
  state machine reads more linearly. The Escape effect remains an
  effect because it owns an external resource (window event listener)
  that genuinely benefits from `useEffect`'s acquire/release model.

- **Decision:** ship without a Playwright spec for this feature.
  **Alternatives considered:** extend `e2e/two-player.spec.ts` to
  drive a `mouse.down` + `mouse.move` mid-drag and assert on the
  `style` attribute of a known legal-destination square; new
  `e2e/move-hints.spec.ts` doing the same in isolation. **Why this
  one:** the existing two-player spec already drives `mouse.down`
  → `mouse.move` → `mouse.up` as one atomic gesture because
  `@dnd-kit`'s `PointerSensor` is timing-sensitive — pausing mid-drag
  to query a square's computed style introduces a flaky window where
  the React commit may not have landed by the time Playwright reads
  the DOM. The 13-test Vitest surface (7 hook tests + 6 Play-page
  tests) covers every relevant code path: drag-start populates,
  drag-start on opponent piece doesn't, drop clears, opponent move
  clears, terminal status clears, Escape clears. Manual smoke
  confirms the visual rendering. The cost/benefit of the e2e — given
  the @dnd-kit fragility documented in feature 7's work — points
  toward skipping it.

- **Decision:** keep the starting alpha values from the plan (0.35 for
  the move dot, 0.55 for the capture ring). **Alternatives
  considered:** higher values (more visible) or lower (less obtrusive).
  **Why this one:** the indigo `#6366F1` primary at 0.35 reads clearly
  against both the cream light squares and the brown dark squares of
  react-chessboard's default board, and the 0.55 ring at 4px inset
  draws a recognizable outline without competing with the piece
  itself. Will revisit once the upcoming `board-themes` feature (12)
  introduces alternative board palettes — those may need per-theme
  tuning.

- **Decision (Round 2):** drop `cursor: 'pointer'` from both
  `MOVE_STYLE` and `CAPTURE_STYLE` records produced by
  `buildMoveHintStyles`. **Alternatives considered:** keep the
  pointer cursor on hint squares for visual emphasis. **Why this
  one:** `squareStyles` paints the destination square (not the
  piece), so the pointer cursor was rendering on empty squares and
  opponent pieces that aren't actually clickable — click-to-select
  is explicitly out of scope. Per web convention, a pointer cursor
  on a non-clickable element is misleading. The dot (quiet move)
  and ring (capture) already communicate the affordance via shape
  and colour, which is the right channel for a drag-driven UI.

- **Decision:** the hook is theme-aware but otherwise pure of
  policy — it does NOT enforce the "own-side only" gate.
  **Alternatives considered:** consult `Role` inside the hook so the
  hint never renders against an opponent piece even if the caller
  forgets to filter. **Why this one:** the role-policy is already
  owned by `canDragPiece` (feature 6.8). Centralising the gate in
  one place (the drag-start handler) keeps the hook a clean
  projection of chess.js' output. The unit test documents the
  decision: passing `'e7'` while it's White's turn returns
  `{}` (because chess.js itself doesn't generate moves for the
  side-not-to-move), and the Play-page test confirms that even when
  chess.js would generate moves, `handlePieceDrag`'s
  `canDragPiece` check prevents the selection.

## How this compares to what I know

- **`useMemo` keyed on FEN ≈ `Eq[Position]` derived from a normalised
  FEN in Scala.** In Scala you'd derive `Eq[Position]` (or
  `Hash[Position]`) from the canonical string representation and cache
  via `Memoize.unsafeMemo(fn)(Eq[FEN])`. React's `useMemo` is the same
  idea expressed at the call site: "I depend on these reactive values;
  please skip recomputation when they're unchanged by `Object.is`."
  The mutability of `chess.js` is what forces the FEN-as-key trick —
  with an immutable `Position` ADT (like
  [scalachess](https://github.com/lichess-org/scalachess)'s
  `chess.Game`), the instance reference itself would change on every
  move and the lookup would be by reference.
- **`useEffect` + window listener ≈ `Resource.eval(IO(addListener))
.onFinalize(IO(removeListener))`.** The mental model carries over
  almost one-to-one: the effect's body is `acquire`, the returned
  cleanup is `release`, and the dep array controls when to
  re-acquire. Where it diverges: React doesn't _re-acquire_ unless a
  dep changes; Cats Effect's `Resource` is a fresh `acquire` on every
  composition. And React schedules cleanup batched against the next
  effect, where `Resource` releases promptly on scope exit.
- **`Move[]` with `captured?: PieceSymbol` ≈ an ADT with a
  `Capture(piece: Piece)` constructor.** TypeScript narrows on
  presence/absence of a field; Scala narrows on the constructor
  itself. The TS form is less explicit (you can't `exhaustiveMatch`
  on "is this a capture?" — you check a field) but the chess.js
  contract is fine in practice: `captured` is `undefined` xor a
  defined `PieceSymbol`, and the `Move.flags` string carries the
  finer-grained breakdown if you ever need it (`'c'` capture, `'e'`
  en passant, `'p'` promotion, etc.).
- **The "push state change into transitions, not into effects"
  pattern ≈ avoiding `Ref#update` in a watcher fiber when the
  producer already has the ref.** In Cats Effect, if you find
  yourself spinning up a `Ref.get` poller to react to a change,
  you've usually let the producer leak — the producer should
  update the watcher's state directly. The React equivalent: if
  your effect is just "when this state changes, update that
  state", the upstream state change should set both. React 19's
  lint rule formalises the intuition.

## Gotchas / things I learned the hard way

- React 19's `react-hooks/set-state-in-effect` is strict. The plan
  proposed an effect for FEN-change clearing and I lifted it
  verbatim; lint refused. The refactor (push clears into the
  transition functions) is genuinely cleaner, but it was a 5-minute
  surprise.
- `Move.captured` on en passant is `'p'`, not `undefined`. I
  briefly considered branching on `flags.includes('e')` for
  en passant; checking `captured !== undefined` is equivalent and
  simpler.
- `useTheme()` inside a custom hook is fine, but the test must wrap
  the hook in a `ThemeProvider`. Without it, MUI silently returns a
  default theme — the tests still ran but the style comparisons
  would have been against the wrong palette. Wrapping it explicitly
  makes the test's coupling to the theme visible.
