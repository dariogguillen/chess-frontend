# Feature 26.7 — Watch a live game as a spectator

**Feature ID:** `spectator-view` (from `feature_list.json`)

**Status:** in progress

---

## What we built

A spectator opens a `/watch?roomId=X` link and watches a live game in a
read-only board view: live moves, clocks (for timed games), the SAN move
list, the viewer count, and the terminal-result modal. There is no manual
code entry — the player shares a "Copy watch link" button from the Play
page. A refresh on `/watch` re-derives everything from the URL; a room
with no active game (still waiting) or a bad roomId shows a friendly
message instead of an empty board.

## TS / React concepts that appear

- **Reusing one component with a discriminating prop** — `Play` gains an
  optional `spectator?: boolean` prop. The `/watch` route renders
  `<Play spectator />`; `/play` renders `<Play />` with the default
  `false`. The same component tree serves two roles; the prop fans out
  into a handful of `isSpectator ? … : …` derivations (roomId source,
  playerId, role, gameId source, hidden controls). This keeps the
  reconnect / resync / viewer-count / terminal machinery shared rather
  than forked.
- **Rules of Hooks under a mode switch** — the player- and spectator-
  discovery hooks are BOTH called on every render. We never wrap a hook
  in a conditional; instead each is _disabled_ by passing a `null`
  roomId. `useRoomDiscovery` gets `discoveryRoomId = null` in spectator
  mode; `useSpectatorDiscovery` gets `spectatorRoomId = null` in player
  mode. The hook call order is therefore identical on every render, which
  is what React requires.
- **Extending a hook's null-handling instead of forking it** —
  `useGameStomp(gameId, playerId, …)` previously treated `playerId ===
null` as a no-op (alongside `gameId === null`). We split those: only
  `gameId === null` short-circuits now. With a null `playerId` the hook
  subscribes WITHOUT the `playerId` STOMP header (the omission is what
  makes the backend's `ViewerCountTracker` count the subscriber as a
  viewer), and the `movedBy === playerId` self-filter becomes a structural
  no-op (a real UUID never equals `null`), so a spectator sees both sides'
  moves.
- **Local state vs. context state (Option B)** — the spectator's gameId
  lives in a local `useState` (`spectatorGameId`), not in the shared
  `UserContext` `RoomState`. Because the roomId is in the URL, a refresh
  re-runs discovery from scratch; no persistence is needed and no new
  context arm is introduced. The effective `gameId` is
  `isSpectator ? spectatorGameId : playerGameId`.

## Decisions taken

- **Decision:** Extend `useGameStomp` to accept a null `playerId` as
  spectator mode rather than write a second STOMP hook.
  - **Alternatives considered:** a dedicated `useSpectatorStomp` that
    subscribes to the same two topics.
  - **Why this one:** the reconnect-with-backoff, the resync-on-reconnect
    `connectionState` transitions, the viewer-count subscription, and the
    `onClose`/`onError` plumbing are all identical for a spectator. A fork
    would duplicate ~120 lines and create a second drift surface. The only
    real difference is "omit the header / no self-filter", and a null
    `playerId` already expresses both for free. The one player-path test
    that asserted "does nothing when playerId is null" was rewritten to
    assert the new spectator behaviour; the remaining player tests are
    untouched and green.
- **Decision:** A small new `useSpectatorDiscovery` (GET-only) rather than
  bending `useRoomDiscovery` to a fourth mode.
  - **Alternatives considered:** add a `spectator` flag to
    `useRoomDiscovery` and skip its STOMP path.
  - **Why this one:** `useRoomDiscovery` races a GET against a STOMP
    `RoomJoinedEvent` because Player A is waiting for a join _transition_.
    A spectator arrives at an already-active game — there is no transition
    to wait for, so the STOMP path is dead weight, and the WAITING/404
    cases need to surface as a _terminal error_ (the opposite of
    `useRoomDiscovery`, which deliberately treats a 404 as soft so STOMP
    can still deliver). The semantics are genuinely different, so a 40-line
    GET-only hook is clearer than a flag that inverts half the behaviour.
- **Decision:** The watch link carries only the roomId, never the join
  token; and the "Copy watch link" button stays visible after the opponent
  has joined (unlike the invite link, which hides).
  - **Why this one:** the roomId is the public watch handle (anyone can
    `GET /api/rooms/{id}` and subscribe to the public game topics); the
    join token authorises _playing_ and must never leak into a watch URL.
    Spectators can be invited at any point while the game is live, so the
    control should not disappear when the seat fills.

## How this compares to what I know

- **In Cats Effect this would be...** the spectator's STOMP subscription
  is a `Resource.make(connect)(disconnect)` whose lifetime is the
  component mount — exactly the player's `Resource`, just acquired with a
  different header set. Passing `playerId = None` (TS `null`) and omitting
  the header is the analogue of `headers.flatMap(_.toList)` where an
  `Option` contributes zero entries when empty — the absence is
  meaningful, not an error.
- **In http4s / tapir this would be...** `useSpectatorDiscovery` is a
  single `GET /api/rooms/{id}` decoded through the same boundary
  narrowing (`getRoomState` → `RoomDetails`) that the player flow uses;
  the WAITING vs ACTIVE branch is a pattern-match on the decoded
  `gameId: Option[GameId]` (`gameId !== null`) rather than on the HTTP
  status — the status only distinguishes "room exists" from "404".
- **Reusing `Play` with a `spectator` prop** is like a single
  `case class` rendered by two `Show`/`Encoder` instances selected by a
  flag: one domain object (the live game), two presentations (interactive
  vs read-only), no duplicated board/clock/move-list logic.

## Gotchas / things I learned the hard way

- The terminal-dialog copy ("Checkmate — Black wins!") renders in BOTH the
  dialog title and the body, so `findByText` throws "multiple elements".
  Use `findAllByText` and assert at least one match.
- `TurnIndicator` already returns `null` when `role === null`, so a
  spectator would have silently shown nothing where the turn chip sits —
  the "Spectating" chip is a deliberate, separate element so the read-only
  state is conveyed in text, not just by absent controls.
- The opponent (top) row falls back to "Waiting for opponent" when
  `opponentDisplayName` is undefined; for a spectator that label is wrong,
  so the fallback is spectator-aware ("Loading game…" until the state
  arrives, suppressed once the friendly error surface takes over).

## To dig deeper

- React docs — [Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks):
  why both discovery hooks must be called unconditionally and gated by
  `null` instead of wrapped in an `if`.
- React docs — [Passing props to a component](https://react.dev/learn/passing-props-to-a-component):
  the `spectator?: boolean` default-prop pattern that lets one component
  back two routes.
- The backend's `ViewerCountTracker` (chess-backend-java): a subscriber
  with a `playerId` SUBSCRIBE header is excluded from the count; omitting
  the header is what tallies a spectator — the contract this feature
  relies on.
